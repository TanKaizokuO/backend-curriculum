Scalability Fundamentals

  • 1. What is the difference between scalability and performance?

    Performance measures the speed of one request. Scalability measures how the system keeps that speed as load grows. A fast system at low load can still fail to scale.

  • 2. What is the difference between vertical scaling and horizontal scaling?

    Vertical scaling adds more CPU, memory, or disk to one machine. Horizontal scaling adds more machines and spreads the load across them. Horizontal scaling has a higher limit, but it needs a stateless design.

  • 3. What is a single point of failure, and how do you remove one?

    A single point of failure is a part of the system that stops the whole system when it fails. You remove it by adding a redundant copy and a way to fail over to that copy.

  • 4. What is the difference between throughput and latency?

    Throughput is the number of requests the system handles in a fixed time. Latency is the time one request takes from start to finish. A system can raise throughput and still keep latency high.

  • 5. How do you design a system to be stateless?

    You move session data out of the application server and into a shared store, such as a cache or a database. Any server instance can then handle any request.

  • 6. What is back-pressure, and why does a system need it?

    Back-pressure is a signal that tells an upstream sender to slow down when a downstream service cannot keep up. Without back-pressure, a slow service falls further behind and then crashes under a growing queue.

  • 7. What is the difference between scaling reads and scaling writes?

    You scale reads by adding read replicas or a cache, because many read requests can hit a copy of the data. You scale writes by sharding the data, because each shard owns a separate slice of the writes.

  • 8. What is a bottleneck, and how do you find one in a running system?

    A bottleneck is the single slowest component that limits the throughput of the whole system. You find it with metrics and tracing: you look for the component with the highest latency or the highest resource use under load.

  • 9. What is graceful degradation?

    Graceful degradation is a design where the system drops a non-critical feature under heavy load, but it keeps the core feature working. For example, a shop site can turn off product recommendations but still process checkout.

  • 10. What is the difference between scaling up and scaling out?

    Scaling up means the same as vertical scaling: you add resources to one machine. Scaling out means the same as horizontal scaling: you add more machines.

  • 11. What is capacity planning, and why does a design interview ask about it?

    Capacity planning is the estimate of the traffic, storage, and bandwidth a system needs. An interview asks about it because the estimate drives real design choices, such as the number of shards or the cache size.

  • 12. What is the difference between synchronous processing and asynchronous processing?

    Synchronous processing blocks the caller until the work finishes and returns a result right away. Asynchronous processing accepts the request, queues the work, and returns a result later, often through a callback or a poll.

  • 13. How do you scale a system that has a hot spot of traffic on one resource?

    You split the hot resource into smaller parts, such as shards or partitions, so that no single part takes all the traffic. You can also add a cache in front of the hot resource or replicate it.

Load Balancing

  • 14. What is a load balancer, and why does a system need one?

    A load balancer is a component that spreads incoming requests across many servers. A system needs one so that no single server takes all the traffic and fails.

  • 15. What is the difference between Layer 4 and Layer 7 load balancing?

    A Layer 4 load balancer routes traffic based on the IP address and the port, without reading the request content. A Layer 7 load balancer reads the HTTP request, such as the path or the header, and routes on that content.

  • 16. What is the round-robin algorithm, and when does it work poorly?

    Round robin sends each new request to the next server on a fixed list, in turn. It works poorly when servers have unequal capacity, because a weak server gets the same share of traffic as a strong server.

  • 17. What is the least-connections algorithm?

    The least-connections algorithm sends a new request to the server that currently holds the fewest active connections. It balances load better than round robin when requests take different amounts of time.

  • 18. What is a health check, and how does a load balancer use one?

    A health check is a periodic probe that asks a server if it can handle traffic. A load balancer removes a server from its rotation when the health check fails, and it adds the server back when the check passes again.

  • 19. What is session affinity, and what problem does it solve?

    Session affinity, also called sticky sessions, sends all requests from one client to the same server. It solves the problem of a server that holds session state in local memory.

  • 20. What is the difference between a hardware load balancer and a software load balancer?

    A hardware load balancer is a dedicated physical appliance built for high throughput. A software load balancer, such as NGINX or HAProxy, runs as a program on standard servers and costs less to scale.

  • 21. What is DNS-based load balancing, and what is a limit of this method?

    DNS-based load balancing returns a different server IP address for each DNS query, in a rotation. A limit is that clients and resolvers cache the DNS answer, so a failed server can still receive traffic until the cache expires.

  • 22. How does a load balancer handle a server that fails mid-request?

    The load balancer detects the failure through a timeout or a health check, marks the server as down, and retries the request on a healthy server.

  • 23. What is the difference between active-active and active-passive failover?

    In active-active failover, every replica serves traffic at the same time. In active-passive failover, one replica serves traffic and a standby replica waits idle until the active replica fails.

  • 24. What is consistent hashing, and why does a load balancer use it?

    Consistent hashing maps each request and each server to a position on a fixed ring, and it sends the request to the nearest server on that ring. A load balancer uses it because adding or removing one server moves only a small share of the traffic, not all of it.

  • 25. How do you scale the load balancer itself when it becomes a bottleneck?

    You place multiple load balancer instances behind a shared virtual IP address, or you use DNS to spread traffic across them. Each instance then load-balances its own share of traffic to the backend servers.

Caching

  • 26. What is a cache, and why does it lower latency?

    A cache is a fast storage layer that keeps a copy of data that a client needs often. It lowers latency because it answers a request from fast local storage instead of a slower source, such as a database.

  • 27. What is the difference between a write-through cache and a write-back cache?

    A write-through cache writes to the cache and to the source at the same time, so the two stay consistent. A write-back cache writes to the cache first and copies the data to the source later, which is faster but risks data loss on a crash.

  • 28. What is cache invalidation, and why is it hard?

    Cache invalidation is the removal or update of stale cache data after the source data changes. It is hard because the system must find every cache entry that depends on the changed data, across every server.

  • 29. What is the LRU eviction policy?

    LRU means least recently used. The cache removes the entry that no one has read for the longest time when it needs space for a new entry.

  • 30. What is the difference between LRU and LFU eviction?

    LRU evicts the entry with the oldest last access time. LFU, which means least frequently used, evicts the entry with the lowest total access count, regardless of when the last access happened.

  • 31. What is a cache stampede, and how do you prevent one?

    A cache stampede happens when many requests miss the cache at the same time and all hit the source at once, which overloads the source. You prevent it with a lock that lets only one request rebuild the cache entry, while other requests wait or use a stale value.

  • 32. Where can a system place a cache?

    A system can place a cache in the browser, on a CDN edge node, in front of the application server, inside the application process, or in front of the database.

  • 33. What is the difference between a local cache and a distributed cache?

    A local cache lives in the memory of one application instance and disappears when that instance restarts. A distributed cache, such as Redis, runs as a shared service that many instances read and write.

  • 34. How do you keep a cache consistent with the source of truth?

    You set a short time-to-live on each entry, and you actively invalidate or update the entry when the source data changes. No method removes every risk of a brief mismatch.

  • 35. What happens to a service when its cache goes down?

    Every request that the cache used to answer now falls through to the source, such as the database. The source load spikes, and the service can slow down or fail if it cannot absorb that spike.

  • 36. What is a TTL, and how do you choose a good value for it?

    A TTL, or time to live, is the length of time a cache entry stays valid before the cache treats it as stale. You choose a value that balances two costs: a short TTL raises source load, and a long TTL raises the risk of stale data.

  • 37. What is the difference between Redis and Memcached?

    Redis stores rich data types, such as lists and sets, and it can save data to disk. Memcached stores only simple key-value pairs in memory and does not persist data to disk.

  • 38. How do you cache the result of a paginated query?

    You build the cache key from the query parameters, such as the page number and the filter, so each distinct page gets its own cache entry. You invalidate the whole set of page keys when the underlying data changes.

Relational Databases and SQL for System Design

  • 39. What is the difference between vertical partitioning and horizontal partitioning of a table?

    Vertical partitioning splits a table by column and stores different columns in different tables. Horizontal partitioning splits a table by row and stores different rows in different tables or shards.

  • 40. What is a database index, and what is the cost of adding one?

    An index is a separate structure that lets the database find a row without a full table scan. The cost is extra disk space and slower writes, because the database must update the index on every insert, update, or delete.

  • 41. What are the ACID properties of a transaction?

    Atomicity means a transaction applies fully or not at all. Consistency means a transaction moves the database from one valid state to another valid state. Isolation means concurrent transactions do not see each other's partial work. Durability means a committed transaction survives a crash.

  • 42. What is database replication, and why does a system use it?

    Database replication is the copying of data from one database node to one or more other nodes. A system uses it to raise read capacity and to keep a standby copy ready for failover.

  • 43. What is the difference between synchronous replication and asynchronous replication?

    Synchronous replication waits for the replica to confirm the write before it tells the client the write succeeded, so it never loses data but it adds latency. Asynchronous replication tells the client the write succeeded right away and copies the data to the replica later, which is faster but can lose recent writes on a failure.

  • 44. What is connection pooling, and why does a backend service need it?

    Connection pooling is the reuse of a fixed set of open database connections across many requests. A service needs it because opening a new connection for each request is slow and a database allows only a limited number of open connections.

  • 45. How do you find and fix a slow query in a production system?

    You use the database's query plan tool to see which step of the query takes the most time. You then add a missing index, rewrite the query, or split the query into smaller steps.

  • 46. What is database sharding, and what is the hardest part of it?

    Database sharding is the split of one large dataset across multiple database instances, each called a shard. The hardest part is the choice of a shard key that spreads the data and the traffic evenly.

  • 47. What is a read replica, and what problem can it introduce?

    A read replica is a copy of a database that serves read traffic and does not accept writes. It can introduce replication lag, so a client can read stale data right after a write to the primary.

  • 48. What is the difference between optimistic locking and pessimistic locking?

    Optimistic locking lets two transactions proceed at the same time and checks for a conflict only at commit time. Pessimistic locking blocks other transactions from touching a row as soon as one transaction starts to use it.

  • 49. How do you design a database schema for a system with a very high write rate?

    You reduce the number of indexes, because each index adds write cost. You also batch writes, shard the data, and consider a write-optimized storage engine instead of a general-purpose relational database.

  • 50. What is a database transaction isolation level, and why does an interview ask about it?

    An isolation level controls how much one transaction sees of another transaction's uncommitted or concurrent work, and it ranges from read uncommitted to serializable. An interview asks about it because a stricter level gives more correctness but lower concurrency.

NoSQL and Data Modeling

  • 51. When do you choose a NoSQL database over a relational database?

    You choose NoSQL when the data has a flexible or changing shape, when the write volume is very high, or when the system needs to scale across many nodes with simple queries. You choose a relational database when the data needs strong consistency and complex joins.

  • 52. What is the difference between a document store, a key-value store, a wide-column store, and a graph database?

    A document store, such as MongoDB, saves each record as a self-contained document. A key-value store, such as DynamoDB, maps a single key to a value with no query on the value's fields. A wide-column store, such as Cassandra, organizes data into rows with dynamic columns across nodes. A graph database, such as Neo4j, stores nodes and the edges between them, and it answers relationship queries fast.

  • 53. What is denormalization, and why does a NoSQL data model favor it?

    Denormalization is the duplication of data across multiple records so a read needs only one lookup. A NoSQL data model favors it because most NoSQL stores lack a fast join operation, so the design moves the join cost to write time instead of read time.

  • 54. How do you model a one-to-many relationship in a document database?

    You embed the many-side records inside the one-side document when the many-side list stays small and reads together. You keep the many-side records in a separate collection with a reference to the one-side document when the list grows large or changes often.

  • 55. What is a partition key, and how do you choose a good one?

    A partition key is the field that a database uses to decide which physical node stores a given record. A good partition key spreads records and traffic evenly across nodes and avoids a hot spot on one value.

  • 56. What is a hot partition, and how does a database handle one?

    A hot partition is a single partition that receives far more traffic than the other partitions, which slows every request to that partition. A database handles it by splitting the partition further or by changing the partition key design to spread the load.

  • 57. What is eventual consistency?

    Eventual consistency means that after a write stops, every replica converges to the same value, but a read right after the write can still return an old value.

  • 58. What is the BASE model, and how does it differ from ACID?

    BASE stands for basically available, soft state, and eventual consistency. It differs from ACID because it trades strict, immediate consistency for higher availability and higher scalability.

  • 59. How do you model a many-to-many relationship in a NoSQL database?

    You store an array of related IDs on each side of the relationship, or you create a separate join-style collection or table that pairs the two IDs. The exact choice depends on which side the queries read from most.

  • 60. What is schema-on-read, and how does it differ from schema-on-write?

    Schema-on-read stores raw data without a fixed structure and applies structure only when the application reads the data. Schema-on-write enforces a fixed structure at insert time, before the database accepts the record.

  • 61. What is a secondary index in a NoSQL database, and what is its cost?

    A secondary index lets a query search on a field other than the partition key. The cost is extra storage and extra write latency, and in some systems the index update happens asynchronously, which can delay a new record's visibility in a query.

  • 62. How do you choose between a strongly consistent NoSQL configuration and an eventually consistent one for a given feature?

    You choose strong consistency for a feature where a stale read causes a real error, such as a bank balance. You choose eventual consistency for a feature that can tolerate a brief delay, such as a view counter or a social media like count.

  • 63. What is a wide-column store, and how does it store data differently from a relational table?

    A wide-column store organizes data by row key, and each row can hold a different set of columns from other rows in the same table. A relational table fixes the same columns for every row.

Sharding and Partitioning

  • 64. What is sharding, and why does a system shard its data?

    Sharding is the split of a dataset into smaller, independent parts, each stored on a separate node. A system shards data because a single node cannot hold or serve the full dataset once the data or the traffic grows past its limit.

  • 65. What is a shard key, and what makes a shard key good or bad?

    A shard key is the field that decides which shard stores a given record. A good shard key spreads records and traffic evenly. A bad shard key sends too many records or too much traffic to one shard, which creates a hot spot.

  • 66. What is range-based sharding, and what is its main weakness?

    Range-based sharding assigns each shard a contiguous range of key values, such as user IDs 1 to 1,000,000. Its main weakness is a hot spot, because new records with sequential keys all land on the same shard.

  • 67. What is hash-based sharding, and what trade-off does it make?

    Hash-based sharding applies a hash function to the shard key and uses the result to pick a shard, which spreads records evenly. The trade-off is that a range query, such as "all records between two dates," must scan every shard instead of one contiguous range.

  • 68. What is consistent hashing, and why does sharding use it?

    Consistent hashing places shards and keys on the same fixed ring by hash value, and each key belongs to the nearest shard on the ring. Sharding uses it because adding or removing one shard moves only a small share of the keys, not the whole dataset.

  • 69. What is resharding, and why is it a hard operation?

    Resharding is the process of moving data to a new set of shards, usually because the shard count changes. It is a hard operation because the system must move a large volume of data without downtime and without data loss, while requests keep arriving.

  • 70. How do you run a query that spans multiple shards?

    The application or a query router sends the query to every relevant shard, collects the partial results, and merges them. This method is called a scatter-gather query, and it costs more than a single-shard query.

  • 71. What is a hot shard, and how do you fix one?

    A hot shard is a shard that receives far more traffic than the other shards, which slows every request to that shard. You fix it by splitting the shard further, or by changing the shard key so it spreads the load more evenly.

  • 72. How do you handle a join across two shards?

    You avoid the join at the database level and instead fetch each side from its own shard and join the results in the application. Some designs also denormalize the data so the join is not needed at all.

  • 73. What is a directory-based sharding strategy?

    A directory-based strategy keeps a separate lookup service that maps each shard key to its shard. It adds an extra network hop for every lookup, but it lets the system move a key to a new shard without a hash change.

  • 74. What is the difference between partitioning and replication?

    Partitioning splits a dataset into disjoint parts, and each part lives on one node or one set of nodes. Replication copies the same full dataset, or the same partition, onto multiple nodes so more than one node holds an identical copy.

  • 75. How do you choose the number of shards for a new system?

    You estimate the total data size and the total write throughput, then divide by the safe capacity of one node, and you round up. You also leave headroom for growth, because resharding later is costly.

Replication and Consistency

  • 76. What is the difference between single-leader replication and multi-leader replication?

    In single-leader replication, only one node accepts writes and it sends the writes to every other node. In multi-leader replication, more than one node accepts writes, and the nodes must resolve any conflict between two writes to the same record.

  • 77. What is leaderless replication, and how does it handle conflicting writes?

    In leaderless replication, a client sends a write to several nodes at once and accepts the write once enough nodes confirm it. The system handles a conflict with a rule such as "last write wins" or with a vector clock that tracks the causal order of writes.

  • 78. What is replication lag, and what problem does it cause?

    Replication lag is the delay between a write on the primary node and the same write's arrival on a replica. It causes a stale read: a client can read old data from a replica right after it wrote new data to the primary.

  • 79. What is read-your-writes consistency?

    Read-your-writes consistency guarantees that a user always sees their own recent write, even if a replica has not caught up yet. A system reaches this by routing that user's next read to the primary node for a short window after their write.

  • 80. What is quorum-based consistency, and how does it work?

    Quorum-based consistency requires a write to succeed on W nodes and a read to check R nodes, where W plus R is greater than the total node count N. This overlap guarantees that a read always sees the most recent write.

  • 81. What is the difference between strong consistency and eventual consistency?

    Strong consistency guarantees that every read returns the most recent write, right after that write completes. Eventual consistency only guarantees that every replica converges to the same value if the system stops receiving new writes.

  • 82. What is a conflict-free replicated data type, and why does a system use one?

    A conflict-free replicated data type, or CRDT, is a data structure with a merge rule that produces the same result regardless of the order in which updates arrive. A system uses one in a multi-leader or leaderless design so that it can merge concurrent updates without manual conflict resolution.

  • 83. What is the difference between a primary-replica setup and a multi-primary setup for handling failover?

    A primary-replica setup promotes one replica to primary when the current primary fails, and only one node accepts writes at a time. A multi-primary setup already runs more than one write-accepting node, so a single node's failure does not stop writes, but it must resolve write conflicts continuously.

  • 84. What is a split-brain scenario in a replicated system?

    A split-brain scenario happens when a network partition isolates two groups of nodes, and each group elects its own primary and accepts writes. The system then holds two conflicting histories that it must reconcile once the network heals.

  • 85. How does a system detect and recover from a failed primary node?

    The system detects the failure through a missed heartbeat or a failed health check, and it promotes a replica to the new primary through an election or a fixed failover rule. Clients then redirect their writes to the new primary.

  • 86. What is causal consistency, and how does it differ from strong consistency?

    Causal consistency guarantees that if one write happens before another, every node sees them in that same order, but it lets unrelated writes appear in a different order on different nodes. Strong consistency orders every write the same way on every node, related or not.

  • 87. What is the difference between synchronous multi-node replication and asynchronous multi-node replication in terms of availability?

    Synchronous replication waits for every replica, or a quorum of replicas, to confirm before it accepts a write, so a slow or down replica can block writes. Asynchronous replication accepts a write once the primary confirms it, so a slow replica does not block writes, at the cost of possible data loss.

  • 88. What is anti-entropy, and why does a replicated system run it?

    Anti-entropy is a background process that compares replicas and repairs any difference between them. A replicated system runs it to fix data drift that a missed message or a temporary outage can cause between replicas.

CAP Theorem and Consistency Models

  • 89. What is the CAP theorem?

    The CAP theorem states that a distributed data store can give only two of three guarantees at the same time: consistency, availability, and partition tolerance. During a network partition, the system must choose between consistency and availability.

  • 90. Why must a distributed system choose partition tolerance in practice?

    A real network can always drop or delay a message between nodes, so a distributed system cannot assume the network never partitions. This leaves only a real choice between consistency and availability during a partition.

  • 91. What is the difference between a CP system and an AP system?

    A CP system stays consistent during a partition, but it rejects some requests so it does not return stale or conflicting data. An AP system stays available during a partition and answers every request, even if some answers are stale.

  • 92. Give an example of a CP system and explain the trade-off.

    A distributed configuration store such as ZooKeeper is a CP system. It refuses a write or a read on the minority side of a partition, which lowers availability but keeps every confirmed value correct.

  • 93. Give an example of an AP system and explain the trade-off.

    A DNS system and many NoSQL stores such as Cassandra, in their default mode, are AP systems. Every node keeps answering requests during a partition, but two nodes on different sides of the partition can return different values.

  • 94. What is the PACELC theorem, and how does it extend CAP?

    PACELC states that during a Partition, a system chooses between Availability and Consistency, and Else, when the network runs normally, it chooses between Latency and Consistency. It extends CAP because CAP only describes system behavior during a partition, not during normal operation.

  • 95. What is linearizability?

    Linearizability is a strong consistency model where every operation appears to take effect at one single instant, and that instant falls between the operation's start and its end. Every client sees operations in the same real-time order.

  • 96. What is the difference between consistency in the CAP theorem and consistency in the ACID properties?

    Consistency in the CAP theorem means every node returns the same, most recent value for a read. Consistency in the ACID properties means a transaction moves the database from one valid state to another valid state, according to defined rules and constraints.

  • 97. How do you decide whether a given feature needs a CP design or an AP design?

    You ask whether a stale or conflicting read causes real harm. A payment balance needs a CP design because a wrong balance causes harm. A product view count can use an AP design because a brief inconsistency causes no harm.

  • 98. What is a network partition, and how does a distributed system detect one?

    A network partition is a break in communication between two groups of nodes that otherwise form one cluster. A system detects a suspected partition through a missed heartbeat or a request timeout, though it cannot always tell a partition apart from a slow or crashed node.

  • 99. What is the difference between weak consistency and eventual consistency?

    Weak consistency gives no guarantee about when, or whether, every replica will converge to the same value. Eventual consistency is a stronger, specific promise within weak consistency: every replica converges to the same value once writes stop arriving.

  • 100. How does a system such as DynamoDB let a client choose its consistency level per request?

    DynamoDB lets a client request either an eventually consistent read, which is cheaper and faster, or a strongly consistent read, which always returns the most recent successful write, at a higher cost.

Message Queues and Event-Driven Architecture

  • 101. What is a message queue, and why does a system use one?

    A message queue is a component that stores messages sent by a producer until a consumer reads and processes them. A system uses one to decouple two services in time, so a slow or offline consumer does not block the producer.

  • 102. What is the difference between a message queue and a publish-subscribe system?

    In a plain message queue, one message goes to exactly one consumer, even when several consumers listen on the queue. In a publish-subscribe system, one message goes to every subscriber of the topic.

  • 103. What is the difference between at-most-once, at-least-once, and exactly-once delivery?

    At-most-once delivery can lose a message but never delivers it twice. At-least-once delivery never loses a message but can deliver it more than once. Exactly-once delivery guarantees a message arrives once, and it needs extra coordination to achieve.

  • 104. How do you make message processing idempotent?

    You give each message a unique ID and you record the IDs your system has already processed. When a duplicate message arrives, the consumer checks the record and skips the message instead of processing it again.

  • 105. What is a dead-letter queue, and why does a system need one?

    A dead-letter queue holds a message that a consumer failed to process after a set number of retries. A system needs one so that a single bad message does not block the whole queue or trigger endless retries.

  • 106. What is the difference between Kafka and a traditional message queue such as RabbitMQ?

    Kafka keeps every message on disk in an ordered log for a retention period, and multiple consumer groups can each read the full log independently. A traditional queue such as RabbitMQ removes a message once a consumer acknowledges it, so the message is not available for replay.

  • 107. What is a consumer group, and how does it help a system scale message processing?

    A consumer group is a set of consumers that split the partitions of a topic between them, so each partition goes to only one consumer in the group. A system scales processing by adding more consumers to the group, up to the number of partitions.

  • 108. What is backpressure in a message-driven system, and how does a queue provide it?

    Backpressure is a mechanism that slows a fast producer to match the speed of a slower consumer. A queue provides it by growing in size when the consumer falls behind, which the producer or an operator can detect and react to.

  • 109. What is event sourcing?

    Event sourcing is a design where the system stores every state change as an immutable event, instead of storing only the current state. The system rebuilds the current state at any time by replaying the events in order.

  • 110. What is the difference between choreography and orchestration in an event-driven system?

    In choreography, each service reacts to events on its own, and no central service directs the overall flow. In orchestration, one central service tells each other service what step to run next.

  • 111. What problem does the outbox pattern solve?

    The outbox pattern solves the problem of keeping a database write and a message publish consistent, since a service cannot commit a database transaction and publish a message as one atomic step. The service writes the message to an outbox table inside the same transaction, and a separate process reads that table and publishes the message.

  • 112. How does a message queue guarantee message order?

    A message queue guarantees order only within a single partition or a single queue, because it must serialize the delivery for that portion. It cannot guarantee a global order across multiple partitions without extra coordination.

  • 113. What is a poison message, and how does a consumer handle one?

    A poison message is a message that a consumer cannot process, no matter how many times it retries, often due to a bad format or a bug. The consumer detects the repeated failure and moves the message to a dead-letter queue instead of retrying forever.

Microservices Architecture

  • 114. What is a microservice, and how does it differ from a monolith?

    A microservice is a small, independently deployed service that owns one business capability and its own data. A monolith packages every capability into one deployable unit that shares one codebase and often one database.

  • 115. What are the main trade-offs of a microservices architecture compared to a monolith?

    Microservices give independent deployment and independent scaling for each service, at the cost of network latency between services and more operational complexity. A monolith is simpler to build and to debug, but it forces the whole system to deploy and scale together.

  • 116. How do microservices communicate with each other?

    Microservices communicate through synchronous calls, such as REST or gRPC, or through asynchronous messages on a queue or an event stream. The choice depends on whether the caller needs an immediate response.

  • 117. What is service discovery, and why does a microservices system need it?

    Service discovery is a mechanism that lets one service find the network address of another service at runtime. A microservices system needs it because service instances start, stop, and move addresses often, especially in a container environment.

  • 118. What is an API gateway, and what role does it play in a microservices system?

    An API gateway is a single entry point that receives every external request and routes it to the correct internal service. It also handles cross-cutting concerns, such as authentication, rate limiting, and request logging, in one place.

  • 119. What is the database-per-service pattern, and why do microservices favor it?

    The database-per-service pattern gives each microservice its own private database, which no other service accesses directly. Microservices favor it because a shared database couples services together and defeats independent deployment.

  • 120. How do you handle a transaction that spans multiple microservices?

    You use the saga pattern: each service commits its own local transaction and publishes an event, and the saga runs a compensating action on an earlier service if a later step fails. A distributed system avoids a single ACID transaction across services because it does not scale well.

  • 121. What is the circuit breaker pattern, and why does a microservices system use it?

    A circuit breaker pattern stops a service from calling a failing dependency for a cooldown period once the failure rate crosses a threshold. A microservices system uses it to stop one failing service from causing a cascading failure across its callers.

  • 122. What is service mesh, and what problem does it solve?

    A service mesh is an infrastructure layer that manages traffic, security, and observability between services, usually through a sidecar proxy next to each service. It solves the problem of repeating this cross-cutting logic in every service's own code.

  • 123. What is the strangler fig pattern for migrating a monolith to microservices?

    The strangler fig pattern moves one feature at a time out of the monolith and into a new microservice, while a router sends traffic for that feature to the new service. Over time, the new services replace the monolith, and the team removes the old code.

  • 124. How do you version an API between microservices without breaking existing consumers?

    You add a version identifier to the API, such as a path prefix or a header, and you keep the old version running until every consumer moves to the new version. You avoid a breaking change to a version that a consumer still depends on.

  • 125. What is the difference between orchestration and choreography when microservices coordinate a business process?

    Orchestration uses one central coordinator service that calls each other service in a defined sequence. Choreography lets each service listen for events and decide its own next action, with no central coordinator.

API Gateway, Rate Limiting and API Design for Scale

  • 126. What is rate limiting, and why does a public API need it?

    Rate limiting is a control that caps the number of requests a client can send in a fixed time window. A public API needs it to protect the backend from overload and to stop one client from starving other clients of capacity.

  • 127. What is the token bucket algorithm for rate limiting?

    The token bucket algorithm gives each client a bucket that refills with tokens at a fixed rate, up to a maximum size. Each request consumes one token, and the client's request fails or waits once the bucket is empty.

  • 128. What is the difference between the token bucket algorithm and the leaky bucket algorithm?

    The token bucket algorithm allows a burst of requests up to the bucket size, as long as tokens are available. The leaky bucket algorithm smooths traffic to a fixed output rate, regardless of how bursty the input is.

  • 129. What is the sliding window algorithm for rate limiting, and why is it more accurate than a fixed window?

    The sliding window algorithm counts requests in a moving time window that shifts continuously, rather than resetting at a fixed boundary. It is more accurate because a fixed window can let a client send double the intended limit near the window's edge.

  • 130. How do you rate-limit a distributed system with many API server instances?

    You store the rate-limit counters in a shared store, such as Redis, so that every API server instance reads and updates the same count for a given client. A local, per-instance counter would let a client exceed the limit by spreading requests across instances.

  • 131. What is API gateway throttling, and how does it differ from a per-client rate limit?

    API gateway throttling caps the total request rate the gateway forwards to a backend service, regardless of which client sent the request. A per-client rate limit caps the rate for one specific client or API key.

  • 132. How do you design pagination for a very large collection endpoint?

    You use a cursor, such as the ID or the timestamp of the last item on the page, instead of an offset. A cursor avoids the cost of skipping past a large offset and stays correct even if the underlying data changes between page loads.

  • 133. What is idempotency, and why does a payment API require an idempotency key?

    Idempotency means that repeating the same operation produces the same result as running it once. A payment API requires an idempotency key so that a client's retry after a network timeout does not charge the customer twice.

  • 134. What is the difference between REST, GraphQL, and gRPC, from a system design point of view?

    REST exposes fixed resources over HTTP and is simple to cache and to scale behind standard infrastructure. GraphQL lets a client ask for exactly the fields it needs in one request, which reduces over-fetching but complicates caching. gRPC uses a binary protocol over HTTP/2 for low-latency service-to-service calls.

  • 135. What is API versioning, and what are the common strategies for it?

    API versioning is the practice of marking a change to an API's contract so that old and new clients can both work. Common strategies include a version number in the URL path, a custom header, or a field in the request body.

  • 136. How does an API gateway help protect a backend from a denial-of-service attack?

    An API gateway sits in front of the backend and applies a rate limit, a request size limit, and an authentication check before it forwards a request. It absorbs and drops malicious or excess traffic before that traffic reaches the backend services.

  • 137. What is the difference between authentication and rate limiting at the API gateway layer?

    Authentication checks who the caller is and rejects a caller with no valid identity. Rate limiting checks how often a known caller sends requests and rejects a request that exceeds the allowed rate, regardless of identity.

  • 138. How do you design an API so that a slow downstream dependency does not block the whole request pipeline?

    You set a timeout on the call to the slow dependency, and you pair the timeout with a circuit breaker that stops further calls once the dependency fails repeatedly. You can also return a partial or cached response instead of a full failure.

CDN and Content Delivery

  • 139. What is a CDN, and why does a system use one?

    A CDN, or content delivery network, is a set of edge servers spread across many geographic locations that cache and serve content close to the user. A system uses one to lower latency and to reduce load on the origin server.

  • 140. What is the difference between a push CDN and a pull CDN?

    A push CDN requires the origin to upload content to the CDN ahead of time. A pull CDN fetches content from the origin automatically on the first request for that content, then caches it for later requests.

  • 141. How does a CDN decide which edge server serves a given user?

    A CDN routes the user to the edge server with the lowest network distance or the lowest latency, often through DNS-based routing or anycast routing at the network layer.

  • 142. What content is a good fit for CDN caching, and what content is not?

    Static content, such as images, video, CSS, and JavaScript files, is a good fit because it rarely changes and every user can share one cached copy. Highly personalized or fast-changing content, such as a user's private dashboard, is a poor fit.

  • 143. What is cache invalidation on a CDN, and why is it slower than invalidating a local cache?

    CDN cache invalidation is the removal of a cached object from every edge server that holds a copy. It is slower because the origin must send the invalidation request to potentially hundreds of geographically spread edge nodes.

  • 144. What is the origin shield pattern in a CDN setup?

    An origin shield is a single intermediate caching layer that sits between the CDN edge nodes and the origin server. It absorbs the combined cache-miss traffic from every edge node, so the origin server sees far fewer direct requests.

  • 145. How does a CDN help mitigate a distributed denial-of-service attack?

    A CDN spreads incoming traffic across many edge locations and absorbs a large volume of malicious traffic before it reaches the origin. Many CDNs also include a dedicated filtering layer that drops known attack patterns.

  • 146. What is the difference between edge caching and browser caching?

    Edge caching stores a copy of content on a CDN server that many different users share. Browser caching stores a copy of content on one specific user's device, and only that user benefits from it.

  • 147. How do you serve dynamic, per-user content through a CDN?

    You cache only the static parts of the page or the response at the edge, and you fetch the personalized parts from the origin on each request, often through a technique such as edge-side includes or a small dynamic API call.

  • 148. What is a signed URL, and why does a CDN use one for private content?

    A signed URL includes a cryptographic signature and an expiry time, and the CDN checks both before it serves the content. A CDN uses it to serve private content, such as a paid video, without exposing the content to any user who guesses the URL.

  • 149. What is TTL in the context of CDN caching, and how does it affect freshness?

    TTL, or time to live, is the length of time an edge server keeps a cached object before it checks the origin again. A short TTL keeps content fresh but raises origin load, and a long TTL lowers origin load but risks serving stale content.

  • 150. How do you handle a cache miss storm across many CDN edge nodes for a newly popular piece of content?

    You warm the cache by pushing the content to edge nodes ahead of a known traffic spike, or you rely on the origin shield to absorb the simultaneous miss traffic. Without one of these steps, every edge node's first request hits the origin at once.

Consensus, Coordination and Distributed Locking

  • 151. What is a consensus algorithm, and why does a distributed system need one?

    A consensus algorithm lets a group of nodes agree on a single value or a single order of operations, even when some nodes fail or messages arrive late. A distributed system needs one to keep replicas consistent, for example when it elects a leader.

  • 152. What is the Paxos algorithm, at a high level?

    Paxos is a consensus algorithm where a proposer suggests a value, a set of acceptors vote on it, and the algorithm commits the value once a majority of acceptors agree. It tolerates the failure of a minority of nodes and still reaches a correct, single decision.

  • 153. What is the Raft algorithm, and how does it differ from Paxos in goal?

    Raft is a consensus algorithm that elects a single leader, and only that leader accepts new log entries and replicates them to followers. It differs from Paxos in goal because the designers built Raft to be easier to understand and to implement correctly.

  • 154. What is a quorum, and why does a distributed system require one for a decision?

    A quorum is the minimum number of nodes that must agree before the system accepts a decision, typically a strict majority. A system requires one so that two conflicting decisions cannot both reach agreement at the same time, since two quorums out of the same node set must overlap.

  • 155. What is leader election, and why does a distributed system perform it?

    Leader election is the process by which a set of nodes choose one node to coordinate writes or decisions for a period of time. A distributed system performs it so that only one node makes a given class of decision, which avoids conflicting concurrent decisions.

  • 156. What is a distributed lock, and what problem does it solve?

    A distributed lock grants exclusive access to a resource to only one process at a time, across multiple machines. It solves the problem of two processes on different machines both modifying the same resource at the same time.

  • 157. What is the danger of a naive distributed lock implementation, and how does a system guard against it?

    A naive lock can expire while the holder still runs, for example after a long garbage-collection pause, which lets a second process acquire the same lock and both processes then act at once. A system guards against this with a fencing token, a number the lock service increases on each grant, which the protected resource checks and rejects if it sees an older token.

  • 158. What is ZooKeeper, and what role does it commonly play in a distributed system?

    ZooKeeper is a coordination service that stores small amounts of configuration data and provides primitives such as leader election, distributed locks, and service discovery. Systems commonly use it as a shared, strongly consistent source of coordination state.

  • 159. What is the difference between a two-phase commit protocol and a consensus algorithm such as Raft?

    A two-phase commit protocol coordinates a single, one-time transaction across multiple participants and blocks if the coordinator fails mid-protocol. A consensus algorithm such as Raft runs continuously to keep a replicated log in agreement and tolerates the failure of the leader through re-election.

  • 160. What is split-brain in the context of leader election, and how does a quorum-based system prevent it?

    Split-brain happens when a network partition lets two separate groups each believe they hold the leader role at the same time. A quorum-based system prevents it because only the group with a majority of nodes can elect a leader, so at most one side of any partition can ever have a quorum.

  • 161. What is a heartbeat, and how does a distributed system use it to detect a failed node?

    A heartbeat is a small, periodic message a node sends to signal that it is still alive and reachable. A distributed system marks a node as failed once it misses a set number of consecutive heartbeats.

  • 162. What is the FLP impossibility result, and what does it mean in practice?

    The FLP impossibility result proves that no algorithm can guarantee consensus in an asynchronous network where even one node can fail, within a bounded time. In practice, real consensus systems use timeouts and randomization to reach agreement with very high probability, instead of an absolute guarantee.

  • 163. What is etcd, and how do systems commonly use it?

    Etcd is a distributed, strongly consistent key-value store built on the Raft consensus algorithm. Systems commonly use it to store cluster configuration, to run leader election, and to coordinate service discovery, for example inside Kubernetes.

Storage Systems, Search and Indexing

  • 164. What is object storage, and how does it differ from a file system or a block storage volume?

    Object storage, such as Amazon S3, stores each item as an object with data, metadata, and a unique key, accessed over a simple HTTP API. A file system organizes data in a folder hierarchy, and block storage exposes raw, fixed-size blocks that an operating system formats into a file system.

  • 165. Why is object storage a common choice for storing large binary files, such as images or videos?

    Object storage scales to a very large number of objects and a very large total size without the operator managing individual servers. It also gives high durability through automatic replication across multiple locations.

  • 166. What is a content-addressable storage system, and what benefit does it give?

    A content-addressable storage system derives an object's key from a hash of its content, so identical content always produces the same key. This benefit lets the system detect and skip a duplicate upload, and it lets a client verify content integrity by recomputing the hash.

  • 167. What is an inverted index, and why does a search engine use one?

    An inverted index maps each word to the list of documents that contain that word. A search engine uses one because it lets the engine find every document that matches a search term without scanning every document.

  • 168. How does a full-text search system, such as Elasticsearch, handle a query with multiple terms?

    It looks up each term in the inverted index to get a list of matching documents, and it merges and ranks the lists by a relevance score, such as term frequency, to produce the final ordered result.

  • 169. What is the difference between a search index and a database index?

    A search index, such as an inverted index, ranks and retrieves documents by relevance to free-text terms. A database index, such as a B-tree index, retrieves exact matches or ranges on a structured field, without a relevance score.

  • 170. How do you keep a search index in sync with a source database?

    You stream every change from the database, often through change-data-capture or an event published on write, into an indexing pipeline that updates the search index. A periodic full re-index acts as a backup for any change that the stream misses.

  • 171. What is a Bloom filter, and how does a storage system use one?

    A Bloom filter is a compact, probabilistic data structure that answers whether an item is definitely absent or possibly present in a set. A storage system uses one to skip a costly disk lookup when the filter reports that a key is definitely absent.

  • 172. What is a log-structured merge tree, and why do some databases use it for writes?

    A log-structured merge tree, or LSM tree, buffers writes in memory and flushes them to disk in sorted, immutable segments, which it merges together over time. Databases use it because sequential disk writes are far faster than random writes, which suits a high write-throughput workload.

  • 173. What is tiered storage, and why does a large-scale system use it?

    Tiered storage keeps frequently accessed, or hot, data on fast and expensive storage, and it moves rarely accessed, or cold, data to slower and cheaper storage. A large-scale system uses it to control storage cost without sacrificing the performance of the hot data path.

  • 174. How would you design a system to store and serve billions of small files, such as user profile photos?

    You avoid storing each file directly in a general file system, since that approach runs into a limit on the number of files per directory and a high per-file overhead. You instead use an object storage service, and you generate a unique key per file, often placed behind a CDN for delivery.

  • 175. What is data compaction in a storage engine, and why does the engine run it?

    Data compaction merges multiple smaller data segments into fewer, larger segments and removes any entry that a later write or delete has made obsolete. The engine runs it to reclaim disk space and to keep read performance from degrading as the number of segments grows.

Reliability, Monitoring and Fault Tolerance

  • 176. What is the difference between availability and reliability in a system design context?

    Availability measures the fraction of time a system responds successfully to a request. Reliability measures how consistently a system performs its intended function correctly over time, including under failure conditions.

  • 177. What does "five nines" of availability mean, and how much downtime does it allow per year?

    Five nines means 99.999 percent availability. It allows about five minutes of downtime per year.

  • 178. What is redundancy, and how does it raise a system's availability?

    Redundancy is the duplication of a critical component so a backup can take over when the primary component fails. It raises availability because the system keeps working as long as at least one redundant copy stays healthy.

  • 179. What is the difference between fault tolerance and fault prevention?

    Fault prevention tries to stop a fault from happening at all, for example through code review and testing. Fault tolerance accepts that a fault will happen and designs the system to keep working correctly despite that fault.

  • 180. What is a circuit breaker, and how does it protect a system during a partial outage?

    A circuit breaker tracks the failure rate of calls to a dependency and stops sending new calls to that dependency once the failure rate crosses a threshold. It protects the system because it stops a failing dependency from consuming resources and causing further failures elsewhere.

  • 181. What is the difference between a retry with a fixed delay and a retry with exponential backoff?

    A retry with a fixed delay waits the same amount of time before each retry attempt. A retry with exponential backoff doubles, or otherwise increases, the wait time after each failed attempt, which reduces load on a struggling dependency.

  • 182. What is a timeout, and why does every network call need one?

    A timeout is a maximum time a caller waits for a response before it gives up and treats the call as failed. Every network call needs one because, without a timeout, a caller can wait forever on a dependency that never responds.

  • 183. What is chaos engineering, and why do teams practice it?

    Chaos engineering is the practice of intentionally injecting failures, such as a killed server or a network delay, into a running system to observe how it responds. Teams practice it to find a weakness before a real, unplanned outage exposes it.

  • 184. What is the difference between a metric, a log, and a trace, in observability?

    A metric is a numeric measurement over time, such as request count or latency. A log is a timestamped record of a discrete event. A trace follows one request across every service it touches and records the time each step took.

  • 185. What is a service level objective, and how does it differ from a service level agreement?

    A service level objective, or SLO, is an internal target for a metric, such as 99.9 percent of requests under 200 milliseconds. A service level agreement, or SLA, is an external, often contractual, promise to a customer, and it usually includes a penalty for missing the target.

  • 186. What is a runbook, and why does an on-call engineer rely on one during an incident?

    A runbook is a written, step-by-step guide for how to diagnose and fix a known type of incident. An on-call engineer relies on one to resolve a familiar incident quickly and correctly, without depending on memory alone under pressure.

  • 187. How do you design a system to survive the failure of an entire data center?

    You deploy the system across at least two geographically separate data centers, and you replicate data between them. You also route traffic away from the failed data center automatically, through a health check and a failover mechanism at the load balancer or the DNS layer.

  • 188. What is a post-incident review, and what should it produce?

    A post-incident review is a structured discussion held after an outage to establish the timeline, the root cause, and the contributing factors. It should produce a small set of concrete action items that reduce the chance or the impact of a similar future incident.

Case-Study Design Prompts and Capacity Estimation

  • 189. How do you design a URL shortener?

    You generate a short, unique key for each long URL, for example by encoding an incrementing ID in base 62, and you store the key-to-URL mapping in a key-value store. On a redirect request, you look up the key and return an HTTP redirect to the original URL, and you place a cache in front of the store for the most popular keys.

  • 190. How do you design a rate limiter as a standalone system?

    You pick an algorithm, such as the sliding window or the token bucket, and you store each client's counter in a shared, fast store like Redis so every API server instance shares the same count. You return a clear error and a retry-after header once a client exceeds its limit.

  • 191. How do you design a news feed system, such as the feed on a social media app?

    For a small following count, you generate the feed at read time by fetching recent posts from every followed account and merging them. For a very large following count, you generate the feed at write time by pushing a new post into each follower's precomputed feed, and you handle a very popular account as a special case to avoid a huge fan-out.

  • 192. How do you design a URL-based web crawler?

    You keep a queue of URLs to visit and a separate store of visited URLs to avoid a repeat crawl. You run many worker processes that pull a URL from the queue, fetch the page, extract new links, and push the new links back onto the queue, while you respect each site's crawl rate limit.

  • 193. How do you design a chat application that supports one-to-one and group messaging?

    You use a persistent connection, such as a WebSocket, between each online client and a chat server, and you route a message through that server to the recipient's connection or store it for later delivery if the recipient is offline. You store message history in a database partitioned by conversation, and you notify group members through a fan-out to their active connections.

  • 194. How do you design a system that shortens and tracks click analytics for a URL, at a scale of billions of clicks per day?

    You separate the redirect path, which must stay fast, from the analytics path, which can run asynchronously. The redirect service looks up the URL and responds immediately, while it also emits a click event to a message queue, and a separate analytics pipeline consumes that queue and aggregates the data.

  • 195. How do you design a distributed file storage service, such as Google Drive or Dropbox?

    You split each file into fixed-size chunks, store the chunks in a distributed object store, and keep file and chunk metadata in a separate database. You sync only the changed chunks between the client and the server to save bandwidth, and you version each file to support history and conflict resolution.

  • 196. How do you design a notification system that sends push, email, and SMS notifications?

    You accept a notification request and place it on a queue instead of sending it inline, so a slow provider does not block the caller. A set of workers, one per channel, consume the queue and call the correct external provider, with a retry policy and a dead-letter queue for a failed send.

  • 197. How do you design a ticket-booking system, such as one for movie or airline seats, that avoids double booking?

    You use a database transaction with a row-level lock, or a conditional update, on the specific seat, so only one request can reserve it. You also add a short-lived hold with an expiry, so a seat a user selected but did not pay for returns to availability.

  • 198. How do you design a distributed unique ID generator?

    You avoid a single auto-increment counter, since it becomes a bottleneck and a single point of failure at scale. You instead use a scheme such as Snowflake, which combines a timestamp, a machine ID, and a per-machine sequence number into one unique, roughly sortable ID, generated locally without coordination.

  • 199. How do you estimate the storage a system needs for a feature, given a rough usage figure?

    You estimate the size of one record, multiply it by the expected number of records per day, and multiply that by the retention period. You add a safety margin, often 20 to 50 percent, for growth and for index or replication overhead.

  • 200. How do you estimate the number of servers a system needs to handle a given request rate?

    You measure, or estimate, how many requests a single server instance can handle per second under realistic load, then divide the total expected request rate by that per-server figure. You round up and add headroom for a traffic spike and for one server's planned or unplanned downtime.
