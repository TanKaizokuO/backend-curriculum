A Server Is Bytes On A Socket Twenty lines of Python, no framework, and the last time HTTP is ever mysterious.

You can already program. The only thing standing between you and a backend job is that you have never made a program that other machines talk to. That turns out to be a much smaller step than it looks — and today you take all of it.

This lesson is deliberately framework-free. You will use FastAPI from Lesson 3 onwards, but a framework you adopt before you understand what it replaced is a framework you can never debug. See MISSION.md for why Python is the anchor language here.

The one idea

The whole lesson in one sentence

An HTTP server is a program that accepts a TCP connection, reads some text off it, and writes some text back in an agreed shape. That is all. Everything else — routing, JSON, auth, ORMs — is convenience built on top of those two moves.

Web servers feel magical because we only ever meet them through browsers. Strip the browser away and the protocol is startlingly plain: it is a text format with a blank line in the middle. MDN calls HTTP "a client-server protocol", and the word to take seriously there is protocol — an agreement about what bytes mean, nothing more.

The shape of a request

Four parts, in this order. The blank line is load-bearing — you will prove that yourself in a few minutes.

┌─ start-line: method, target, version ─────────────┐
GET /hello?name=world HTTP/1.1
┌─ headers: Name: value, one per line ──────────────┐
Host: 127.0.0.1:8080
User-Agent: curl/8.5.0
Accept: */*
┌─ a blank line. this is the separator ─────────────┐

┌─ body: optional. absent on a typical GET ─────────┐

Every line ends with \r\n (carriage return, then line feed) — not just \n. This is a genuine tripwire when you hand-write bytes. RFC 9110 is the arbiter if you ever need to settle a detail.

The shape of a response

Identical structure. Only the first line differs: instead of a method and a target, it carries a status code.

HTTP/1.1 200 OK
Content-Type: text/plain; charset=utf-8
Content-Length: 21

Hello from a socket.

Full tables of methods, status codes and the headers that matter live in the HTTP anatomy reference — that is the document to keep open, not this one.

Practice 1 · Be the client

Before writing a server, become a browser. This program opens a raw TCP socket, types an HTTP request into it by hand, and prints whatever comes back.

client.py

import socket

with socket.create_connection(("example.com", 80), timeout=10) as sock:
    sock.sendall(
        b"GET / HTTP/1.1\r\n"
        b"Host: example.com\r\n"
        b"Connection: close\r\n"
        b"\r\n"
    )
    chunks = []
    while True:
        chunk = sock.recv(4096)
        if not chunk:          # empty bytes == the server hung up
            break
        chunks.append(chunk)

print(b"".join(chunks).decode("utf-8", "replace")[:400])
$ python3 client.py
What you should see

A status line, a pile of headers, a blank line, then HTML. Port 80 is plain HTTP, so the bytes travel unencrypted and you can read them — which is precisely why everything real uses port 443 and TLS.

You will probably see a stray number such as 22f just before the HTML, and a header saying Transfer-Encoding: chunked. That is the body arriving in length-prefixed chunks (22f is hexadecimal for 559 bytes) because the server did not know the total size up front. Chunked encoding is the third answer to the framing problem you are about to meet in Practice 3. Not a bug — note it and move on.

Three details in those four lines earn their place:

  • Host: is mandatory in HTTP/1.1. One IP address serves thousands of sites; this header is how the server knows which one you meant.
  • Connection: close asks the server to hang up when done, which is what ends our while loop. Without it the connection stays open and we wait forever.
  • The final \r\n produces the blank line. Omit it and the server keeps waiting for more headers.

Practice 2 · Be the server

Now the other side. This is a complete, working HTTP server. No framework, no imports beyond the standard library.

server.py

import socket

listener = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
listener.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)
listener.bind(("127.0.0.1", 8080))
listener.listen(5)
print("listening on http://127.0.0.1:8080")

while True:
    conn, addr = listener.accept()      # blocks until someone connects
    with conn:
        request = conn.recv(65536)
        print("--- request from", addr[0], "---")
        print(request.decode("utf-8", "replace"))

        body = b"Hello from a socket.\n"
        head = (
            "HTTP/1.1 200 OK\r\n"
            "Content-Type: text/plain; charset=utf-8\r\n"
            f"Content-Length: {len(body)}\r\n"
            "Connection: close\r\n"
            "\r\n"
        ).encode("ascii")
        conn.sendall(head + body)

SO_REUSEADDR lets you restart the server immediately instead of hitting "Address already in use" for a minute or two after each stop. You will be restarting a lot today.

  1. Run it: python3 server.py
  2. In a second terminal: curl -i http://127.0.0.1:8080/hello?name=world
    The -i flag prints the response headers, not just the body.
  3. Look at the server terminal. The request you just made is printed there as plain text. This is the moment the lesson is aiming at: you are reading, in full, what a client sends.
  4. Now open http://127.0.0.1:8080 in a browser and read the server terminal again. Same protocol — but count the headers a browser sends compared with curl.
Two honest caveats

You may see an occasional empty request logged, especially from a browser. That is a connection opened speculatively and closed without sending anything. Harmless.

A single recv() is not guaranteed to return the whole request — TCP is a byte stream, not a message queue, so a large request can arrive in pieces. Real servers loop until they see the blank line. This is the central warning in the Python Socket Programming HOWTO, and it is one of the things a framework buys you.

Practice 3 · Break it on purpose

Two edits. Each one fails in a way that teaches a rule you will otherwise re-learn painfully at 2am, three years into your career.

Experiment A — delete the blank line

Remove the final "\r\n" from head, restart, and curl it again.

curl: (8) Header without colon

Curl read Hello from a socket. and tried to parse it as a header, because nothing told it the headers had ended. The blank line is not formatting. It is the delimiter between metadata and payload.

Experiment B — delete Content-Length and keep the connection open

Remove the Content-Length line, and after sendall add time.sleep(30) so the socket stays open. Then curl it.

$ curl -i http://127.0.0.1:8080/
(nothing. it just sits there.)

Deleting Content-Length without the sleep appears to work fine — because closing the connection is itself a legal way to end a body. The bug only shows when the connection is reused, which is the default in HTTP/1.1. Bugs that hide behind a fast local close are a recurring theme in backend work.

The rule this teaches

HTTP runs over a byte stream with no built-in message boundaries. A client must be told where the body ends, and there are exactly three ways to do it: Content-Length, chunked transfer encoding (the 22f you saw from example.com), or closing the connection. Give it none of the three and the client waits forever. This is framing, and it is the single most common cause of a request that "just hangs".

Where this goes

You now have the mental model that everything else hangs from. Next session: rewriting this server to actually parse the request — a real start-line parser, a routing table, and correct status codes — and then meeting WSGI/ASGI, the contracts that let a framework take over from you. Only then does FastAPI appear, and by that point you will be able to say precisely what it is doing on your behalf. That sentence, in an interview, is worth more than a certificate.

Optional, high value: keep server.py. In two sessions it becomes the "before" half of a portfolio piece — a from-scratch HTTP server with tests. That is a far more distinctive first repository than another todo app.
