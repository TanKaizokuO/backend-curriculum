A Server Without A Framework Parse the request. Route it. Answer correctly. Then hand it to something better.

In Lesson 1 you wrote a server that ignored what the client asked for. Every request got 200 OK and the same string. That is not a server — it is a greeting card taped to a socket. Today you make it actually read the request and respond differently depending on what was asked.

By the end of this lesson you will have a server that parses the start line, pulls out headers and query strings, routes to different functions, and answers with correct status codes. Then you will meet the contract that lets you hand all of that work to a framework — and understand exactly what that framework is doing for you.

The one idea

The whole lesson in one sentence

A framework is a standard calling convention between a server program and your application code — nothing more. You can write that convention yourself, and once you have, the framework is no longer magic; it is a labour-saving device whose cost you can measure.

Step 1 · Parse the start line

Lesson 1's server.py read the request bytes and threw them away. The first real work is to split the start line into its three parts: method, target, and version.

server.py — start-line parser

def parse_request_line(raw: bytes) -> tuple[str, str, str]:
    """Return (method, target, version) or raise ValueError."""
    # Split the raw bytes at the first \r\n — that is the request line.
    request_line, _rest = raw.split(b"\r\n", 1)
    parts = request_line.decode("ascii").split(" ")
    if len(parts) != 3:
        raise ValueError(f"Malformed request line: {request_line!r}")
    method, target, version = parts
    return method, target, version

Three things to notice:

  • ASCII, not UTF-8. The start line and headers are defined as ASCII. Bodies can be anything — the Content-Type header tells you what.
  • Exactly three parts. If split(" ") does not produce three items, the request is malformed and the server must answer 400 Bad Request. This is not pedantry — a missing version field once crashed a production proxy at Cloudflare (their engineering blog regularly post-mortems such bugs).
  • You will throw this code away. Every line of parsing you write here is a line a framework will write for you. The point is to know what that line does — not to maintain it.

Step 2 · Parse headers and the query string

After the request line, every line until the blank line is a header. Each header is Name: value. The name is case-insensitive — the RFC is explicit about this (RFC 9110 §5.1: "Each field name … is case-insensitive").

server.py — header + query parser

from urllib.parse import urlparse, parse_qs

def parse_headers(raw: bytes) -> dict[str, str]:
    """Return headers as a lower-cased dict."""
    _request_line, rest = raw.split(b"\r\n", 1)
    header_block, _body = rest.split(b"\r\n\r\n", 1)
    headers = {}
    for line in header_block.split(b"\r\n"):
        name, _sep, value = line.decode("ascii").partition(":")
        headers[name.strip().lower()] = value.strip()
    return headers

def parse_query(target: str) -> tuple[str, dict]:
    """Split '/hello?name=world' → ('/hello', {'name': ['world']})."""
    parsed = urlparse(target)
    return parsed.path, parse_qs(parsed.query)
Why lower-case the header names?

HTTP headers are case-insensitive by spec. A client can send Content-Type, content-type, or CONTENT-TYPE — all mean the same thing. Normalising to lower-case on arrival means the rest of your code never has to think about it. Every production server does this, and so does every framework. In PEP 3333, header names in the WSGI environ dict are upper-cased and prefixed with HTTP_ — a different normalisation, but the same principle: pick a canonical form once.

urlparse and parse_qs are from the standard library. The query string ?name=world&lang=en is just URL-encoded key-value pairs. parse_qs returns lists because a key can appear more than once: ?tag=python&tag=http is legal and common.

Step 3 · A routing table

Lesson 1's server ran the same code for every request. A real server maps a (method, path) pair to a function. The simplest version of this is a dictionary.

server.py — routing

def handle_index(method, path, query, headers):
    return 200, "text/plain", b"Welcome.\n"

def handle_hello(method, path, query, headers):
    name = query.get("name", ["stranger"])[0]
    body = f"Hello, {name}!\n".encode()
    return 200, "text/plain", body

ROUTES = {
    ("GET", "/"):      handle_index,
    ("GET", "/hello"): handle_hello,
}

Look at what the key is: both method and path. This is why a server can tell you "that path exists but you used the wrong method" — the distinction between 404 Not Found and 405 Method Not Allowed falls out of how you look the route up.

Step 4 · Correct status codes

A server that answers 200 OK to everything is lying. HTTP defines a vocabulary of status codes for a reason: they tell the client what to do next. The ones that matter today (RFC 9110 §15):

CodeMeaningWhen your server sends it
200OKThe handler ran and produced a body.
400Bad RequestThe request line could not be parsed.
404Not FoundNo route matches the path at all.
405Method Not AllowedThe path exists, but not for that method.
405 has a requirement most beginners miss

When you send 405 Method Not Allowed, you must include an Allow header listing the methods that are allowed for that path (RFC 9110 §10.2.1). Without it, the client has no way to know what would work. This is the kind of detail that separates a server that technically runs from a server that a colleague can integrate against.

Step 5 · Put it all together

Here is the complete server. It is still one file, still no imports beyond the standard library, but now it actually reads the request and answers correctly.

server.py

import socket
from urllib.parse import urlparse, parse_qs

# ── Parsing ─────────────────────────────────────────────

def parse_request_line(raw):
    request_line, _rest = raw.split(b"\r\n", 1)
    parts = request_line.decode("ascii").split(" ")
    if len(parts) != 3:
        raise ValueError(f"Malformed request line: {request_line!r}")
    return parts[0], parts[1], parts[2]

def parse_headers(raw):
    _request_line, rest = raw.split(b"\r\n", 1)
    header_block, _body = rest.split(b"\r\n\r\n", 1)
    headers = {}
    for line in header_block.split(b"\r\n"):
        name, _sep, value = line.decode("ascii").partition(":")
        headers[name.strip().lower()] = value.strip()
    return headers

def parse_query(target):
    parsed = urlparse(target)
    return parsed.path, parse_qs(parsed.query)

# ── Handlers ────────────────────────────────────────────

def handle_index(method, path, query, headers):
    return 200, "text/plain", b"Welcome.\n"

def handle_hello(method, path, query, headers):
    name = query.get("name", ["stranger"])[0]
    body = f"Hello, {name}!\n".encode()
    return 200, "text/plain", body

ROUTES = {
    ("GET", "/"):      handle_index,
    ("GET", "/hello"): handle_hello,
}

STATUS_PHRASES = {200: "OK", 400: "Bad Request",
                  404: "Not Found", 405: "Method Not Allowed"}

# ── Response helpers ─────────────────────────────────────

def build_response(status, content_type, body, extra_headers=None):
    phrase = STATUS_PHRASES.get(status, "Unknown")
    lines = [f"HTTP/1.1 {status} {phrase}"]
    lines.append(f"Content-Type: {content_type}; charset=utf-8")
    lines.append(f"Content-Length: {len(body)}")
    lines.append("Connection: close")
    for h in (extra_headers or []):
        lines.append(h)
    lines.append("")  # blank line
    head = "\r\n".join(lines).encode("ascii") + b"\r\n"
    return head + body

def allowed_methods(path):
    """Which methods are registered for this path?"""
    return [m for (m, p) in ROUTES if p == path]

# ── Main loop ────────────────────────────────────────────

def serve(host="127.0.0.1", port=8080):
    listener = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
    listener.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)
    listener.bind((host, port))
    listener.listen(5)
    print(f"listening on http://{host}:{port}")

    while True:
        conn, addr = listener.accept()
        with conn:
            raw = conn.recv(65536)
            if not raw:
                continue

            try:
                method, target, version = parse_request_line(raw)
            except ValueError:
                conn.sendall(build_response(
                    400, "text/plain", b"Bad Request.\n"))
                continue

            path, query = parse_query(target)
            headers = parse_headers(raw)

            print(f"{method} {path} from {addr[0]}")

            handler = ROUTES.get((method, path))
            if handler:
                status, ctype, body = handler(method, path, query, headers)
                conn.sendall(build_response(status, ctype, body))
            else:
                allowed = allowed_methods(path)
                if allowed:
                    # Path exists, wrong method → 405
                    conn.sendall(build_response(
                        405, "text/plain",
                        b"Method Not Allowed.\n",
                        [f"Allow: {', '.join(allowed)}"]))
                else:
                    # No route at all → 404
                    conn.sendall(build_response(
                        404, "text/plain",
                        b"Not Found.\n"))

if __name__ == "__main__":
    serve()

Practice · Run it and prove the status codes

Save the file, start the server, and run each of these in a second terminal. Read both the response and the server log — the pair is the full picture.

  1. 200 OK: curl -i http://127.0.0.1:8080/hello?name=world
    You should see Hello, world! and status 200.
  2. 404 Not Found: curl -i http://127.0.0.1:8080/nope
    No route for /nope, so the server answers 404.
  3. 405 Method Not Allowed: curl -i -X POST http://127.0.0.1:8080/hello
    The path exists but only for GET. Check that the response includes an Allow: GET header — that is the RFC requirement.
  4. 400 Bad Request: printf 'garbage\r\n\r\n' | nc 127.0.0.1 8080
    Send malformed bytes. The parser fails and the server answers 400 instead of crashing.
What you just built

A server that parses an HTTP request from raw bytes, routes it through a table, and answers with the correct status code, headers, and body. No framework. One file, ~80 lines. This is the skeleton that every framework in every language replaces — and now you know what that skeleton looks like.

What a framework replaces

Look at how much of that file is plumbing: the socket setup, the recv loop, splitting \r\n, lower-casing header names, building the response string, getting Content-Length right. None of that changes between applications. If you wrote a second app on the same server, you would copy-paste all of it.

That observation is the entire reason WSGI and ASGI exist. They define a contract — a calling convention — so that the plumbing lives in one program (the server) and your application logic lives in another (the app). The server does the parsing; your code receives a clean dictionary and returns a response. You never write recv again.

WSGI — the synchronous contract

PEP 3333 (final since 2010) defines WSGI. The entire contract is one callable:

def application(environ, start_response):
    """environ: a dict of request data. start_response: you call it to set
    the status and headers. Return an iterable of body chunks."""
    start_response("200 OK", [("Content-Type", "text/plain")])
    return [b"Hello from WSGI.\n"]

That is a complete WSGI application. The server (Gunicorn, uWSGI, mod_wsgi, or Python's own wsgiref) handles the socket, the parsing, the headers, the framing. Your function receives environ — a dictionary with keys like REQUEST_METHOD, PATH_INFO, QUERY_STRING, and every header prefixed with HTTP_ — and calls start_response to set the status line and headers.

Flask is a WSGI framework. When you write @app.route("/hello"), Flask builds the routing table and the handler calling convention on top of this contract. Django is the same — its WSGIHandler is the callable that Gunicorn invokes.

You can run the application above right now, with zero installs, using the standard library:

wsgi_demo.py

from wsgiref.simple_server import make_server

def application(environ, start_response):
    method  = environ["REQUEST_METHOD"]
    path    = environ["PATH_INFO"]
    qs      = environ["QUERY_STRING"]
    print(f"{method} {path}?{qs}")

    start_response("200 OK", [("Content-Type", "text/plain")])
    return [f"You asked: {method} {path}?{qs}\n".encode()]

server = make_server("127.0.0.1", 9000, application)
print("WSGI listening on http://127.0.0.1:9000")
server.serve_forever()
$ python3 wsgi_demo.py
$ curl http://127.0.0.1:9000/hello?name=world
Compare to your socket server

The WSGI version has no socket import, no recv, no header splitting, no Content-Length arithmetic. That is exactly the plumbing the contract is designed to absorb. What you wrote by hand in server.py is what wsgiref.simple_server now does for you — and Gunicorn does it with worker processes, graceful restarts, and proper error handling.

ASGI — the async contract

WSGI's contract is synchronous. Your function runs, it returns, and the request is over. WSGI cannot hold a WebSocket, because a WebSocket is a long-lived connection that carries many messages in both directions. WSGI also blocks one worker for each open client, so a stream of server-sent events is expensive. ASGI (v3.0, 2019) replaces the contract with an async callable:

async def application(scope, receive, send):
    """scope: a dict describing the connection.
    receive: await it to get the next event from the client.
    send:    await it to push an event back."""
    assert scope["type"] == "http"
    body = b"Hello from ASGI.\n"
    await send({
        "type": "http.response.start",
        "status": 200,
        "headers": [
            [b"content-type", b"text/plain"],
        ],
    })
    await send({
        "type": "http.response.body",
        "body": body,
    })

Three differences from WSGI:

  • async def — the function is a coroutine, run inside an event loop (asyncio).
  • Events, not return values. Instead of returning a body iterable, you await send() with structured dicts. This allows streaming, WebSockets, and anything that is not a single request → single response.
  • scope["type"] tells you the protocol — "http", "websocket", or "lifespan". One callable handles all of them.
Where FastAPI sits

FastAPI is an ASGI framework. Uvicorn is the ASGI server — it does the socket work. FastAPI is the application — it builds a routing table, validates input with Pydantic, and calls your @app.get("/hello") function. The scope → receive → send contract is the seam between them. When you run uvicorn main:app, you are telling Uvicorn "call this ASGI callable for every connection." That is the entire relationship.

Primary sources

PEP 3333 — Python Web Server Gateway Interface v1.0.1

The full WSGI spec. Read the "Specification Overview" and "The Application/Framework Side" sections — they are short and the code examples are runnable. Skip the thread-support and middleware sections for now; they matter later.

ASGI Specification v3.0

The async successor. Read "Overview" and "Applications". The key insight: ASGI generalises to any protocol (HTTP, WebSocket, lifespan events) via the scope["type"] dispatch.

RFC 9110 — HTTP Semantics §9 (Methods), §10.2.1 (Allow), §15 (Status Codes)

The normative reference for "what does 405 mean and what must the server include?" These sections are readable and settle arguments that blog posts leave ambiguous.

MDN — HTTP messages

The same reference from Lesson 1, now with more depth: request-target forms, HTTP/2 pseudo-headers, and body framing. Fifteen minutes.
