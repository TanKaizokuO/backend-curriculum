FastAPI The framework does the plumbing. You do the thinking.

In Lesson 2 you built a server that parses raw bytes, routes requests through a dictionary, and answers with correct status codes — all in ~80 lines with no dependencies. Then you met WSGI and ASGI, the contracts that let a framework take over the plumbing. Today you hand it over. FastAPI is the framework this curriculum anchors on, and by the end of this lesson you will have a running JSON API with routing, path parameters, query parameters, request-body validation, automatic error responses, and live interactive documentation — all of which you can explain in terms of the layers you already understand.

By the end of this lesson you will have a main.py you can curl, open in a browser at /docs, and extend into your first portfolio project. Every feature maps to something you wrote by hand in Lessons 1–2.

The one idea

The whole lesson in one sentence

FastAPI is an ASGI application that turns Python type annotations into routing, validation, serialisation, error responses, and OpenAPI documentation — replacing every line of plumbing you wrote by hand, while adding things you could not easily build yourself.

Step 0 · Install and run

Create a project directory and install FastAPI:

$ mkdir bookmarks-api && cd bookmarks-api
$ python3 -m venv .venv && source .venv/bin/activate
$ pip install "fastapi[standard]"

fastapi[standard] pulls in Uvicorn (the ASGI server from Lesson 2's stack diagram) and a few other defaults. If you prefer uv: uv init --bare && uv add "fastapi[standard]".

Create main.py with the smallest possible FastAPI app:

main.py — hello world

from fastapi import FastAPI

app = FastAPI()

@app.get("/")
async def root():
    return {"message": "Hello, world"}

Run it:

$ uvicorn main:app --reload
INFO:     Uvicorn running on http://127.0.0.1:8000
What just happened — mapped to the stack

uvicorn main:app means: "import app from main.py and call it as an ASGI application for every connection." That is the exact contract from Lesson 2: async def application(scope, receive, send). Uvicorn is the server layer — sockets, recv, parsing. FastAPI is the application layer — routing, validation, your handler functions. The --reload flag watches the file and restarts on save, so you can iterate without restarting the process.

Step 1 · Routing — from a dictionary to decorators

In Lesson 2 your routing table was a plain dictionary:

ROUTES = {
    ("GET", "/"):      handle_index,
    ("GET", "/hello"): handle_hello,
}

FastAPI replaces this with decorator-based routing. The decorator @app.get("/") registers the function for GET /. There are matching decorators for every HTTP method: @app.post, @app.put, @app.delete, @app.patch.

You wrote this by hand; FastAPI does it here

Your Lesson 2 ROUTES dict keyed on (method, path). FastAPI does the same thing internally — it builds a routing table from your decorated functions. The difference: FastAPI's router handles path parameters (/items/{item_id}), supports middleware, and returns 405 Method Not Allowed with an Allow header when the path exists but the method does not. You wrote that logic by hand in allowed_methods(). FastAPI does it for you.

A place the framework is not quite right — verify it yourself

Lesson 2 drilled that 405 must carry an Allow header listing the methods the resource supports (RFC 9110 §10.2.1). FastAPI sends one — but when you register the same path with separate decorators, the header is incomplete.

In the finished app below, /bookmarks/{bookmark_id} has both a @app.get and a @app.delete. Send it a PUT and you get:

$ curl -i -X PUT http://127.0.0.1:8000/bookmarks/1
HTTP/1.1 405 Method Not Allowed
allow: GET

DELETE is missing. Each decorator creates its own route object, and the router reports the methods of the first one whose path matched. Declaring both methods on a single route fixes it — @app.api_route("/bookmarks/{bookmark_id}", methods=["GET", "DELETE"]) yields allow: GET, DELETE.

Run both versions and compare. The lesson is not "FastAPI is buggy" — it is that a framework is code someone else wrote, with its own trade-offs. You can only see this because you built the 405 logic by hand in Lesson 2 and know what the header is supposed to contain. That is the whole argument for learning the mechanism before the abstraction.

Step 2 · Path parameters — no more parse_query

In Lesson 2 you wrote parse_query(target) to split the URL into a path and query parameters. Every handler received the full query dict and had to fish out the values it needed. FastAPI replaces all of that with function signatures.

Let us build a bookmarks API. Each bookmark has an integer ID, a URL, and an optional title.

main.py — path parameters

from fastapi import FastAPI

app = FastAPI()

# In-memory store (a real API uses a database — that is Lesson 4).
BOOKMARKS: dict[int, dict] = {}
next_id = 1

@app.get("/bookmarks/{bookmark_id}")
async def get_bookmark(bookmark_id: int):
    if bookmark_id not in BOOKMARKS:
        raise HTTPException(status_code=404, detail="Bookmark not found")
    return BOOKMARKS[bookmark_id]

Three things happened with zero extra code:

  • Extraction: {bookmark_id} in the path string tells FastAPI to pull that segment from the URL and pass it to the function as the argument bookmark_id.
  • Conversion: The type annotation : int tells FastAPI to convert the string from the URL into a Python int. /bookmarks/3 arrives as the integer 3, not the string "3".
  • Validation: If someone requests /bookmarks/abc, FastAPI automatically returns a 422 Unprocessable Entity response with a JSON body explaining exactly what went wrong — no try/except ValueError needed.
Compare to Lesson 2

In your hand-built server, the path /bookmarks/3 would not match the route ("/bookmarks") — your dictionary used exact string matches. Supporting path parameters would have meant writing a regex or a trie. FastAPI's router does this for you, and every path parameter is documented in the OpenAPI schema automatically.

Step 3 · Query parameters — declared in the function signature

In Lesson 2 you used parse_qs from the standard library to turn ?name=world into {'name': ['world']}, then pulled values out with query.get("name", ["stranger"])[0]. FastAPI replaces that entire pattern: any function parameter that is not in the path is automatically treated as a query parameter.

main.py — query parameters

@app.get("/bookmarks")
async def list_bookmarks(skip: int = 0, limit: int = 10):
    all_bookmarks = list(BOOKMARKS.values())
    return all_bookmarks[skip : skip + limit]
  • skip and limit are not in the path string, so FastAPI treats them as query parameters.
  • Default values make them optional: /bookmarks works; /bookmarks?skip=5&limit=2 also works.
  • Type annotations (int) mean FastAPI validates and converts them. ?skip=abc → 422 error, automatically.
You wrote this by hand; FastAPI does it here

Lesson 2: parse_qs(parsed.query) plus manual .get() with fallbacks. FastAPI: declare the parameter with a type and a default in the function signature. The framework handles parsing, validation, default values, and documents every parameter in OpenAPI.

Step 4 · Request bodies and Pydantic — validation you could not build easily

Lesson 2's handlers received the raw body as bytes. If you wanted to accept JSON, you would have written json.loads(body), then manually checked that every field existed and had the right type. FastAPI replaces that with Pydantic models.

main.py — Pydantic model + POST endpoint

from fastapi import FastAPI, HTTPException
from pydantic import BaseModel

app = FastAPI()

BOOKMARKS: dict[int, dict] = {}
next_id = 1

class BookmarkCreate(BaseModel):
    url: str
    title: str | None = None

@app.post("/bookmarks", status_code=201)
async def create_bookmark(bookmark: BookmarkCreate):
    global next_id
    entry = {"id": next_id, "url": bookmark.url, "title": bookmark.title}
    BOOKMARKS[next_id] = entry
    next_id += 1
    return entry

What BookmarkCreate(BaseModel) buys you:

  • Automatic JSON parsing. FastAPI reads the request body as JSON and hands it to Pydantic.
  • Type validation. url must be a string. title is optional (defaults to None). Send {"url": 42} and Pydantic rejects it with a clear error message, returned as a 422 response.
  • Editor support. Inside the handler, bookmark.url autocompletes and type-checks — because the parameter is typed as BookmarkCreate, not a generic dict.
  • Documentation. The model's fields and types appear in the OpenAPI schema and in /docs as a fillable form.
422, not 400

FastAPI returns 422 Unprocessable Entity for validation errors, not 400 Bad Request. This is intentional: 400 means the request is syntactically broken (like the malformed bytes you sent with nc in Lesson 2). 422 means the request is well-formed HTTP but the content fails validation — a meaningful distinction when debugging.

Step 5 · Error responses — HTTPException replaces build_response

In Lesson 2 you built error responses manually:

conn.sendall(build_response(
    404, "text/plain", b"Not Found.\n"))

FastAPI provides HTTPException:

from fastapi import HTTPException

raise HTTPException(status_code=404, detail="Bookmark not found")

This produces a JSON response:

HTTP/1.1 404 Not Found
content-type: application/json

{"detail": "Bookmark not found"}
You wrote this by hand; FastAPI does it here

Your Lesson 2 build_response() assembled the status line, Content-Type, Content-Length, and the blank line separating headers from body — every time. FastAPI does all of that for every response. HTTPException is a Python exception; when you raise it, FastAPI catches it and builds the correct HTTP response, including serialising the detail field to JSON.

Step 6 · OpenAPI and /docs — documentation for free

Start the server and open http://127.0.0.1:8000/docs in a browser. You will see an interactive page listing every endpoint, its path parameters, query parameters, request body schema, and response codes — all generated automatically from your code.

This is powered by the OpenAPI specification (v3.1.0). FastAPI generates an OpenAPI JSON document at /openapi.json and serves it through Swagger UI at /docs. There is also an alternative viewer at /redoc.

This is something you could never get from the hand-built server. Documentation that stays in sync with the code is a major selling point in an interview — and a daily convenience when a frontend developer needs to integrate against your API.

Where the docs come from

Every piece of information in /docs comes from your Python code: the decorator (@app.get) provides the method and path, the function signature provides the parameters and their types, the Pydantic model provides the request body schema, and the status_code argument provides the default response code. FastAPI reads all of this and builds the OpenAPI document. There is no separate config file. The code is the documentation.

Step 7 · The complete app

Here is the full bookmarks API with all the pieces assembled: two endpoints, path parameters, query parameters, request body validation, error handling, and correct status codes.

main.py

from fastapi import FastAPI, HTTPException
from pydantic import BaseModel

app = FastAPI()

# ── Data ─────────────────────────────────────────────────

BOOKMARKS: dict[int, dict] = {}
next_id: int = 1

class BookmarkCreate(BaseModel):
    url: str
    title: str | None = None

# ── Endpoints ────────────────────────────────────────────

@app.get("/bookmarks")
async def list_bookmarks(skip: int = 0, limit: int = 10):
    """Return all bookmarks, paginated."""
    all_bookmarks = list(BOOKMARKS.values())
    return all_bookmarks[skip : skip + limit]

@app.get("/bookmarks/{bookmark_id}")
async def get_bookmark(bookmark_id: int):
    """Return a single bookmark by ID."""
    if bookmark_id not in BOOKMARKS:
        raise HTTPException(status_code=404, detail="Bookmark not found")
    return BOOKMARKS[bookmark_id]

@app.post("/bookmarks", status_code=201)
async def create_bookmark(bookmark: BookmarkCreate):
    """Create a new bookmark. Returns the created resource."""
    global next_id
    entry = {"id": next_id, "url": bookmark.url, "title": bookmark.title}
    BOOKMARKS[next_id] = entry
    next_id += 1
    return entry

@app.delete("/bookmarks/{bookmark_id}", status_code=204)
async def delete_bookmark(bookmark_id: int):
    """Delete a bookmark by ID."""
    if bookmark_id not in BOOKMARKS:
        raise HTTPException(status_code=404, detail="Bookmark not found")
    del BOOKMARKS[bookmark_id]

That is ~30 lines of application code. Compare it to the ~80-line server from Lesson 2 that handled only two GET routes and returned plain text. This version handles four operations (list, get, create, delete), validates input, returns JSON, documents itself, and produces correct status codes — 201 Created, 204 No Content, 404 Not Found, 422 Unprocessable Entity.

Practice · Run it and prove each feature

Save main.py, start the server with uvicorn main:app --reload, and run each of these in a second terminal. Read the response status code and the body.

  1. List (empty): curl -i http://127.0.0.1:8000/bookmarks
    You should see 200 OK and an empty JSON array [].
  2. Create: curl -i -X POST http://127.0.0.1:8000/bookmarks -H "Content-Type: application/json" -d '{"url": "https://fastapi.tiangolo.com", "title": "FastAPI docs"}'
    You should see 201 Created and the bookmark with "id": 1.
  3. Get by ID: curl -i http://127.0.0.1:8000/bookmarks/1
    You should see 200 OK and the bookmark you just created.
  4. 404 — not found: curl -i http://127.0.0.1:8000/bookmarks/999
    You should see 404 Not Found and {"detail":"Bookmark not found"}.
  5. 422 — validation error (wrong type): curl -i http://127.0.0.1:8000/bookmarks/abc
    FastAPI rejects "abc" because bookmark_id is typed as int. You should see 422 and a JSON error body telling you exactly where the validation failed.
  6. 422 — validation error (bad body): curl -i -X POST http://127.0.0.1:8000/bookmarks -H "Content-Type: application/json" -d '{"title": "no url"}'
    The url field is required. FastAPI returns 422 with "msg": "Field required".
  7. Delete: curl -i -X DELETE http://127.0.0.1:8000/bookmarks/1
    You should see 204 No Content and an empty body.
  8. Query parameters: Create three more bookmarks, then curl -s "http://127.0.0.1:8000/bookmarks?skip=1&limit=1"
    You should get exactly one bookmark — the second one. Then try curl -i "http://127.0.0.1:8000/bookmarks?skip=abc" and watch the same 422 machinery reject a bad query parameter, with "loc": ["query","skip"] instead of ["path",...].
  9. 405 — check the Allow header yourself: curl -i -X PUT http://127.0.0.1:8000/bookmarks/1
    You get 405 Method Not Allowed. Now read the Allow header. It says GET — even though DELETE is also registered for that path. Go back to the warning box in Step 1, then rewrite the two decorators as a single @app.api_route(..., methods=["GET", "DELETE"]) and run the same curl again. The header becomes GET, DELETE. You just found and fixed a spec-conformance gap in a framework used by thousands of companies — because Lesson 2 taught you what the header should say.
  10. Interactive docs: Open http://127.0.0.1:8000/docs in a browser. Click "Try it out" on any endpoint and execute a request from the browser. This is the OpenAPI documentation, generated entirely from your code.

The map — updated

Three lessons in, here is where every piece fits. Lesson 3 filled in the top layer:

    ┌─────────────────────────────────────────────────────────────┐
    │  Your application code    (BookmarkCreate, handlers)        │ ← Lesson 3
    ├─────────────────────────────────────────────────────────────┤
    │  Framework (FastAPI)                                        │ ← Lesson 3
    │    @app.get / @app.post  →  routing table                   │
    │    Pydantic models       →  validation + serialisation      │
    │    HTTPException         →  error responses                 │
    │    OpenAPI generation    →  /docs, /openapi.json            │
    ├─────────────────────────────────────────────────────────────┤
    │  Gateway contract: ASGI                                     │
    │    async application(scope, receive, send)   ← Lesson 2     │
    ├─────────────────────────────────────────────────────────────┤
    │  Server (Uvicorn)                                           │
    │    socket, recv, parse, Content-Length        ← Lessons 1–2  │
    ├─────────────────────────────────────────────────────────────┤
    │  TCP / the operating system                  ← Lesson 1     │
    └─────────────────────────────────────────────────────────────┘

When a request arrives at GET /bookmarks/3:

  1. Uvicorn accepts the TCP connection, reads bytes from the socket (Lesson 1), parses the HTTP request (Lesson 2), and calls FastAPI via the ASGI contract.
  2. FastAPI matches the path /bookmarks/{bookmark_id}, extracts 3, converts it to int, validates it, and calls your get_bookmark function.
  3. Your handler looks up the bookmark, raises HTTPException(404) if missing, or returns the dict.
  4. FastAPI serialises the return value to JSON, builds the response headers (Content-Type: application/json, Content-Length), and sends it back through the ASGI contract.
  5. Uvicorn writes the bytes to the socket.

Every step is a layer you can name. That is the point.
