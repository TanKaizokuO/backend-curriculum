Relational modelling + SQL Your data lives longer than your process.

Your bookmarks API works. But every bookmark dies when you press Ctrl-C. Today you give the API permanent storage. You will do these tasks: design a normalised schema; write the SQL by hand on a real PostgreSQL server; make the database reject bad data before your Python sees it; write a migration runner yourself, to learn what a migration is; and connect the whole thing to main.py. At the end you restart the server. The data is still there. At that moment the project stops being an exercise and becomes a service.

Before you start — reading to do first

Open reference-pdfs/http-messages-reference.pdf. This is the MDN HTTP Messages guide, printed for offline reading. You have now written HTTP by hand. You have parsed HTTP by hand. You have also let a framework do it. This is the correct time to read the systematic version. Read it for twenty minutes, before or after this lesson. But read it this week.

The one idea

The whole lesson, in short

A relational schema is a set of rules that your data must not break. You store each fact exactly once. Keys and constraints make the illegal states impossible to represent. SQL does two things: it declares these rules, and it asks questions about the data that remains.

Everything else is machinery that supports this idea — normal forms, foreign keys, joins, and transactions. Keep the main idea in view. The database is not a place to dump Python dictionaries. It is the last defence for correctness. It is also the only component in your stack that still holds correct data after your process crashes.

Do not use SQLite for this lesson. You are training for jobs that run Postgres. The important differences are types, constraints, and concurrency behaviour. SQLite hides these differences. The fastest correct setup uses Docker:

Step 1 · Do it the wrong way first

The obvious method is to translate your in-memory dict into one table. Bookmarks have tags, so you give the table a tags column:

the wrong table

CREATE TABLE bookmarks_bad (
    id     SERIAL PRIMARY KEY,
    url    TEXT,
    title  TEXT,
    tags   TEXT
);

INSERT INTO bookmarks_bad (url, title, tags) VALUES
  ('https://fastapi.tiangolo.com/',      'FastAPI',       'python, web, api'),
  ('https://www.postgresql.org/docs/',   'Postgres docs', 'sql, database'),
  ('https://peps.python.org/pep-3333/',  'PEP 3333',      'python, wsgi'),
  ('https://webassembly.org/',           'WebAssembly',   'webassembly, spec');

Now answer the first question that a bookmarks app must answer — show me everything with the tag web:

bookmarks=# SELECT title, tags FROM bookmarks_bad WHERE tags LIKE '%web%';
    title    |       tags
-------------+-------------------
 FastAPI     | python, web, api
 WebAssembly | webassembly, spec
(2 rows)
This is a wrong answer, and the database cannot help you

WebAssembly does not have the tag web. It has the tag webassembly. LIKE '%web%' finds a substring in a string, and the string contains commas. You could correct it with LIKE '%, web,%' OR tags LIKE 'web,%'. But then you write a parser, not a query. The problem is not the WHERE clause. The problem is that the column holds a list, and SQL does not know it.

This table cannot do three more things. Each thing is a real feature request that will happen:

  • Rename a tag. To change python to python3, you must change every row that contains it. You must do it with string edits, correctly, in one transaction. One mistake makes your data inconsistent, with no warning.
  • List all tags. There is no query for this. You must read every row into Python, split the string on commas, remove the spaces, and remove the duplicates. This moves work into Python. But the database is built to do this work.
  • Count the bookmarks for each tag. This has the same problem, and you must also write the aggregation yourself.
First normal form, in practical terms

One cell holds one value. A column must not contain a list — a comma-separated list, a JSON array, or a pipe-delimited list. A list is a structure that the database understands. But you hide the structure in a text type, and the database sees that type as opaque. Then every query becomes string manipulation. You also lose every guarantee that you wanted: uniqueness, referential integrity, and indexes.

Step 2 · Model it properly

Ask the modelling question: what are the things, and how do they relate? There are two things — a bookmark and a tag. The relationship between them is many-to-many: a bookmark has many tags, and a tag labels many bookmarks. A many-to-many relationship is also a thing, and so it gets its own table.

  bookmarks                bookmark_tags                 tags
  ─────────                ─────────────                 ────
  id        ◀──────────────  bookmark_id
  url                        tag_id       ──────────────▶  id
  title                                                    name
  created_at                 PK (bookmark_id, tag_id)

the right schema

CREATE TABLE bookmarks (
    id          BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    url         TEXT        NOT NULL UNIQUE,
    title       TEXT,
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE tags (
    id    BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    name  TEXT NOT NULL UNIQUE
);

CREATE TABLE bookmark_tags (
    bookmark_id  BIGINT NOT NULL REFERENCES bookmarks(id) ON DELETE CASCADE,
    tag_id       BIGINT NOT NULL REFERENCES tags(id)      ON DELETE CASCADE,
    PRIMARY KEY (bookmark_id, tag_id)
);

Every clause in the schema has a purpose. Read them one at a time:

  • BIGINT GENERATED ALWAYS AS IDENTITY — this is the modern, SQL-standard replacement for SERIAL. It does the same job: it makes an auto-increment surrogate key. ALWAYS gives more safety: the application cannot supply its own id by mistake and desynchronise the sequence. Use it for new tables. Also recognise SERIAL in old ones.
  • PRIMARY KEY — this is the identity of the row. It is unique, it is never null, and other tables point at it. id is a surrogate key: it has no meaning by design, so it never has to change when the real-world data changes.
  • url TEXT NOT NULL UNIQUE — this is the natural key. A bookmark without a URL is not a bookmark, and the same URL twice is a duplicate. This one line is your complete method to prevent duplicates. It works even when two requests arrive in the same millisecond. A Python check, if url in BOOKMARKS, does not work then.
  • REFERENCES bookmarks(id) — this is a foreign key. Now the database refuses to store a link to a bookmark that does not exist. This is referential integrity, and this guarantee lets you trust a join.
  • ON DELETE CASCADE — when the bookmark is deleted, its links are deleted also. Without this clause, a delete of a bookmark fails with a foreign key error, because rows in bookmark_tags still point at it. You choose a policy here. The other policies are RESTRICT (refuse) and SET NULL.
  • PRIMARY KEY (bookmark_id, tag_id) — this is a composite key. The identity of a link is the pair itself, so you cannot attach the same tag to the same bookmark twice. Note that there is no id column: this table has no independent identity to name.
Normal forms, in short

1NF: one value in each cell (the failure in Step 1). 2NF: every non-key column depends on the whole key, not part of it. 3NF: non-key columns depend on the key and nothing else — no column comes from a different non-key column. One practical rule gives you all three forms: store every fact exactly once. If you must write to more than one place to change one real-world fact, the model is wrong. The fact "the tag has the name python" is now in exactly one row of tags.

Denormalisation is a real technique. But it is an optimisation that you apply later, with a measurement, and you accept the update problems on purpose. To start with a denormalised model is not a shortcut. It is a bug that you have not found yet.

Step 3 · Let the database say no

Constraints are not documentation. The database enforces them, on every write. The database is the only component that sees all of them. Try to break each one:

bookmarks=# INSERT INTO bookmarks (url, title)
            VALUES ('https://fastapi.tiangolo.com/', 'FastAPI again');
ERROR:  duplicate key value violates unique constraint "bookmarks_url_key"
DETAIL:  Key (url)=(https://fastapi.tiangolo.com/) already exists.

bookmarks=# INSERT INTO bookmarks (title) VALUES ('no url');
ERROR:  null value in column "url" of relation "bookmarks"
        violates not-null constraint
DETAIL:  Failing row contains (6, null, no url, 2026-08-02 22:09:37.253002+00).

bookmarks=# INSERT INTO bookmark_tags (bookmark_id, tag_id) VALUES (999, 1);
ERROR:  insert or update on table "bookmark_tags" violates foreign key
        constraint "bookmark_tags_bookmark_id_fkey"
DETAIL:  Key (bookmark_id)=(999) is not present in table "bookmarks".

These are three classes of bug that your Python no longer has to prevent. More importantly, a second client also cannot introduce them — a cron job, a script from a colleague, or you in psql at night. Validation in your API is a courtesy to the caller. Constraints in the database are the real guarantee.

Look at the second error again

Failing row contains (6, null, ...) — the id is 6, but only four rows were inserted with success. Identity sequences are not transactional: a failed insert still uses a number. Gaps in your IDs are normal and permanent. You may one day need gapless numbers (invoice numbers, for example). That is a separate design problem, not a sequence.

Step 4 · Ask questions — the join

The data is now in three tables. To answer "everything with the tag web", you must combine them again. A join does this: it matches rows from two tables on a condition, and it makes the combined rows.

bookmarks=# SELECT b.id, b.title
            FROM bookmarks b
            JOIN bookmark_tags bt ON bt.bookmark_id = b.id
            JOIN tags t           ON t.id = bt.tag_id
            WHERE t.name = 'web';
 id |  title
----+---------
  1 | FastAPI
(1 row)

One row. This is correct. WebAssembly is gone. The query is not more clever than LIKE. The reason is that web and webassembly are now different rows, not different substrings. The model did the work.

To go the other way, you get every bookmark with its tags in one row. For this you need LEFT JOIN and an aggregate:

bookmarks=# SELECT b.id, b.title,
                   string_agg(t.name, ', ' ORDER BY t.name) AS tags
            FROM bookmarks b
            LEFT JOIN bookmark_tags bt ON bt.bookmark_id = b.id
            LEFT JOIN tags t           ON t.id = bt.tag_id
            GROUP BY b.id, b.title
            ORDER BY b.id;
 id |     title     |       tags
----+---------------+------------------
  1 | FastAPI       | api, python, web
  2 | Postgres docs | sql
  3 | PEP 3333      | python, wsgi
  4 | WebAssembly   | webassembly
(4 rows)
JOIN and LEFT JOIN — an important difference

A plain JOIN (an inner join) keeps only the rows that matched. A LEFT JOIN keeps every row from the left table, and it fills NULL where nothing matched. Use the first query's JOIN here instead, and any bookmark with no tags disappears from your API response, with no warning. This is one of the most common real bugs in list endpoints: the join, not the filter, dropped the row.

Aggregation the other way: how many bookmarks have each tag, including the unused ones:

bookmarks=# SELECT t.name, count(bt.bookmark_id) AS n
            FROM tags t
            LEFT JOIN bookmark_tags bt ON bt.tag_id = t.id
            GROUP BY t.name
            ORDER BY n DESC, t.name;
    name     | n
-------------+---
 python      | 2
 api         | 1
 sql         | 1
 web         | 1
 webassembly | 1
 wsgi        | 1
(6 rows)

Why count(bt.bookmark_id) and not count(*)? count(*) counts rows, and a LEFT JOIN with no match still makes one row — so an unused tag would report 1. count(column) does not count NULLs, so it correctly reports 0. Try both.

And the operation that was string editing in Step 1:

bookmarks=# UPDATE tags SET name = 'python3' WHERE name = 'python';
UPDATE 1

One row changed. Now both bookmarks have the tag python3. This is the benefit of "store every fact exactly once".

Deletion is now the database's task also:

bookmarks=# SELECT count(*) FROM bookmark_tags WHERE bookmark_id = 1;
 count
-------
     3

bookmarks=# DELETE FROM bookmarks WHERE id = 1;
DELETE 1

bookmarks=# SELECT count(*) FROM bookmark_tags WHERE bookmark_id = 1;
 count
-------
     0

bookmarks=# SELECT count(*) FROM tags;
 count
-------
     6

The three link rows cascaded away. The tags themselves stayed. A delete of a bookmark must not delete the concept "python". Read the cascade rules again with this in mind: they hold a domain decision, not a technicality.

Step 5 · Transactions — the A in ACID

An API request that writes to two tables can fail in the middle. See what Postgres does about it:

bookmarks=# BEGIN;
BEGIN
bookmarks=# INSERT INTO bookmarks (url, title)
            VALUES ('https://example.com/', 'Example') RETURNING id;
 id
----
  7
INSERT 0 1
bookmarks=# INSERT INTO bookmark_tags (bookmark_id, tag_id) VALUES (7, 999);
ERROR:  insert or update on table "bookmark_tags" violates foreign key
        constraint "bookmark_tags_tag_id_fkey"
DETAIL:  Key (tag_id)=(999) is not present in table "tags".
bookmarks=# COMMIT;
ROLLBACK
bookmarks=# SELECT count(*) FROM bookmarks WHERE url = 'https://example.com/';
 count
-------
     0
Read the output again — psql answered COMMIT with ROLLBACK

The first insert succeeded. Then the second insert failed, which put the transaction in a failed state, so the COMMIT became a rollback and the bookmark never existed. Atomicity: a transaction is all or nothing. Without it you could have a bookmark with half its tags, and no way to know. Every multi-statement write in your API belongs in one transaction. Note the evidence that stays: id 7 was used and is gone forever.

Here are the other three letters, in short, so the interview question is not new to you. Consistency: a transaction moves the database from one valid state to another valid state, and your constraints define "valid". Isolation: concurrent transactions do not see each other's unfinished work. Durability: after COMMIT returns, the data survives a power failure. You have now seen A and C enforced with your own eyes.

Step 6 · Migrations — write the runner, then use the tool

Your schema is now a thing that you typed into psql. This is not shippable: your laptop and production must reach the same schema, by the same repeatable path, and so must the next person who clones the repo. A migration is a change to the schema. It is versioned, ordered, and applied once. You check it into git, beside the code that depends on it.

Convention #2 of this curriculum says: build the mechanism before the tool. The mechanism is about forty lines. Start with the schema as numbered files:

migrations/0001_create_bookmarks.sql

CREATE TABLE bookmarks (
    id          BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    url         TEXT        NOT NULL UNIQUE,
    title       TEXT,
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);

migrations/0002_create_tags.sql

CREATE TABLE tags (
    id    BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    name  TEXT NOT NULL UNIQUE
);

CREATE TABLE bookmark_tags (
    bookmark_id  BIGINT NOT NULL REFERENCES bookmarks(id) ON DELETE CASCADE,
    tag_id       BIGINT NOT NULL REFERENCES tags(id)      ON DELETE CASCADE,
    PRIMARY KEY (bookmark_id, tag_id)
);

CREATE INDEX bookmark_tags_tag_id_idx ON bookmark_tags (tag_id);

Why the extra index? The composite primary key already indexes (bookmark_id, tag_id). But you can search a B-tree on two columns efficiently only from the left. The question "which bookmarks have tag 42?" searches by the second column, so it needs its own index. Indexes are the subject of Lesson 5. Use The Index, Luke! is the reference for that lesson.

Now write the runner. The main trick is a table that records which files are already applied:

migrate.py

"""Apply every .sql file in migrations/ that has not been applied yet."""
import os
import pathlib
import psycopg

DSN = os.environ["DATABASE_URL"]
MIGRATIONS = pathlib.Path(__file__).parent / "migrations"

with psycopg.connect(DSN) as conn:
    conn.execute("""
        CREATE TABLE IF NOT EXISTS schema_migrations (
            version     TEXT PRIMARY KEY,
            applied_at  TIMESTAMPTZ NOT NULL DEFAULT now()
        )
    """)
    conn.commit()

    rows = conn.execute("SELECT version FROM schema_migrations")
    applied = {v for (v,) in rows}

    for path in sorted(MIGRATIONS.glob("*.sql")):
        version = path.stem
        if version in applied:
            print(f"skip    {version}")
            continue
        with conn.transaction():                     # all-or-nothing
            conn.execute(path.read_text())
            conn.execute("INSERT INTO schema_migrations (version) VALUES (%s)",
                         (version,))
        print(f"applied {version}")
$ pip install "psycopg[binary,pool]"
$ python migrate.py
applied 0001_create_bookmarks
applied 0002_create_tags

$ python migrate.py
skip    0001_create_bookmarks
skip    0002_create_tags

Run it twice. The second run does nothing. This property is idempotence, the same word you learned for HTTP methods in Lesson 1, and it is the whole point. Deployment can run the runner on every boot, without a condition.

Why the DDL is inside a transaction

PostgreSQL has transactional DDL: you can roll back CREATE TABLE. MySQL and Oracle cannot do this. So a migration that fails on its third statement leaves the database exactly as it was, and schema_migrations is not updated — you fix the file and run it again. This is one of the strongest practical reasons to use Postgres, and it is worth saying out loud in an interview.

The rule to keep in production

Never edit an applied migration. Once a file has run somewhere that is not your laptop, it is history. Every change is a new numbered file. If you edit 0002, your machine and the server now disagree about the meaning of 0002, and nothing will tell you.

In a real project you would use Alembic (SQLAlchemy's migration tool, and the default in the Python ecosystem). It adds more features: autogeneration from model definitions, downgrade scripts, and branched histories for teams. But it runs the same loop that you wrote — a version table, ordered scripts, applied once — and now you can debug it when it fails.

Step 7 · Wire it into the API

Now replace the dictionary in main.py. There are three new pieces: a connection pool that opens at startup, parameterised queries, and a map from database errors to HTTP status codes.

main.py — connection pool via lifespan

import os
from contextlib import asynccontextmanager

from fastapi import FastAPI, HTTPException
from psycopg import errors
from psycopg.rows import dict_row
from psycopg_pool import AsyncConnectionPool
from pydantic import BaseModel

DSN = os.environ["DATABASE_URL"]

@asynccontextmanager
async def lifespan(app: FastAPI):
    async with AsyncConnectionPool(DSN, open=False) as pool:
        await pool.wait()
        app.state.pool = pool
        yield

app = FastAPI(lifespan=lifespan)
Why a pool, and why lifespan

To open a PostgreSQL connection costs a TCP handshake, authentication, and a new backend process on the server — a few milliseconds, on every request, forever. A pool opens a few connections at startup and hands them out. lifespan is FastAPI's startup and shutdown hook: the code before yield runs once when Uvicorn boots, and the code after yield runs on shutdown. Some objects have a connection lifetime — pools, HTTP clients, and caches. They belong here. They do not belong at import time, and they never belong in each request.

main.py — the list endpoint

LIST_SQL = """
    SELECT b.id, b.url, b.title, b.created_at,
           coalesce(array_agg(t.name ORDER BY t.name)
                    FILTER (WHERE t.name IS NOT NULL), '{}') AS tags
    FROM bookmarks b
    LEFT JOIN bookmark_tags bt ON bt.bookmark_id = b.id
    LEFT JOIN tags t           ON t.id = bt.tag_id
    GROUP BY b.id
    ORDER BY b.id
    LIMIT %(limit)s OFFSET %(skip)s
"""

@app.get("/bookmarks")
async def list_bookmarks(skip: int = 0, limit: int = 10):
    async with app.state.pool.connection() as conn:
        cur = await conn.cursor(row_factory=dict_row).execute(
            LIST_SQL, {"limit": limit, "skip": skip}
        )
        return await cur.fetchall()

Your Lesson 3 skip/limit loaded everything, then sliced a Python list. LIMIT/OFFSET pushes that work into the database, which is the only version that still works at a million rows. FILTER (WHERE t.name IS NOT NULL) is the array version of the count() point above: without it, an untagged bookmark comes back as [null], not [].

main.py — create, with the duplicate-URL case

class BookmarkCreate(BaseModel):
    url: str
    title: str | None = None
    tags: list[str] = []

@app.post("/bookmarks", status_code=201)
async def create_bookmark(bookmark: BookmarkCreate):
    async with app.state.pool.connection() as conn:  # one transaction
        cur = conn.cursor(row_factory=dict_row)
        try:
            await cur.execute(
                "INSERT INTO bookmarks (url, title) VALUES (%s, %s)"
                " RETURNING id, url, title, created_at",
                (bookmark.url, bookmark.title),
            )
        except errors.UniqueViolation:
            raise HTTPException(status_code=409,
                                detail="URL already bookmarked")
        row = await cur.fetchone()

        for name in bookmark.tags:
            await cur.execute(
                "INSERT INTO tags (name) VALUES (%s)"
                " ON CONFLICT (name) DO UPDATE SET name = EXCLUDED.name"
                " RETURNING id",
                (name,),
            )
            tag = await cur.fetchone()
            await cur.execute(
                "INSERT INTO bookmark_tags (bookmark_id, tag_id)"
                " VALUES (%s, %s)",
                (row["id"], tag["id"]),
            )
    return row | {"tags": bookmark.tags}

Notice three things. RETURNING gets the generated id and created_at back in the same round trip — there is no second SELECT. ON CONFLICT (name) DO UPDATE ... RETURNING id is an upsert: it reuses the tag if it exists, it creates the tag if it does not, and it returns the id in both cases (a bare DO NOTHING returns no row — a trap worth knowing). And psycopg's async with conn commits when the block exits without an error, and it rolls back on any exception, so a failure in the middle of the tag loop leaves no half-tagged bookmark.

The one mistake to always prevent — try it yourself

Those %s placeholders are not string formatting. Prove the difference:

user_input = "' OR '1'='1"

# NEVER do this
naive = f"SELECT id, title FROM bookmarks WHERE title = '{user_input}'"
print(conn.execute(naive).fetchall())

# do this
print(conn.execute("SELECT id, title FROM bookmarks WHERE title = %s",
                   (user_input,)).fetchall())
naive SQL : SELECT id, title FROM bookmarks WHERE title = '' OR '1'='1'
naive rows: [(2, 'Postgres docs')]
safe  rows: []

The f-string leaked the quote, and the WHERE clause became always-true — you get the whole table, from a search box. The parameterised version sends the SQL and the values to the server separately, so the input is data and can never become syntax. Never build SQL with f-strings, %, or +. Do not "sanitise it first" — parameterise, always.

main.py — get and delete

@app.get("/bookmarks/{bookmark_id}")
async def get_bookmark(bookmark_id: int):
    async with app.state.pool.connection() as conn:
        cur = await conn.cursor(row_factory=dict_row).execute(
            "SELECT id, url, title, created_at FROM bookmarks WHERE id = %s",
            (bookmark_id,),
        )
        row = await cur.fetchone()
    if row is None:
        raise HTTPException(status_code=404, detail="Bookmark not found")
    return row

@app.delete("/bookmarks/{bookmark_id}", status_code=204)
async def delete_bookmark(bookmark_id: int):
    async with app.state.pool.connection() as conn:
        cur = await conn.execute("DELETE FROM bookmarks WHERE id = %s",
                                 (bookmark_id,))
    if cur.rowcount == 0:
        raise HTTPException(status_code=404, detail="Bookmark not found")

cur.rowcount is how you tell "deleted it" from "it was never there" — a DELETE against a missing id is not an error, and it affects zero rows. That difference is the difference between 204 and 404.

  PostgreSQL — constraints, transactions, storage
       │
       ▼
  disk (survives everything above it)

Note the shape of that stack: the bottom layer is the only one that keeps anything. Every layer above it is disposable, which is exactly why deploys, crashes, and restarts are survivable — and why a bug that corrupts the bottom layer is in a different category from one that crashes the top.

Where this goes

You now have a persistent API, and with persistence come the questions that matter only once data is real. Lesson 5 is persistence under pressure — indexes and EXPLAIN (why is this query slow?), the N+1 problem (why is this endpoint slow when every query is fast?), isolation levels and concurrent writes, and the ORM question — SQLAlchemy, what it gives you, and what it hides. You wrote the SQL first, so you will see exactly what the ORM generates for you.
