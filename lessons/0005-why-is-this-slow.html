Why is this slow? Measure first. The database will tell you the truth if you ask it.

Your API works and your data survives a restart. It also has about forty rows in it, which is why everything feels fast. Today you put 200 000 rows in the database and watch the same code become slow. Then you learn the one tool that tells you why — EXPLAIN — and use it to fix two different kinds of slowness: a query that reads the whole table, and an endpoint where every single query is fast and the endpoint is still slow. At the end you have a measured before-and-after, which is a much better thing to put in a README than another CRUD endpoint.

The whole lesson in one sentence

You cannot fix slowness you have not measured, and the database will hand you the measurement — so the skill is not "know which things are slow", it is ask the database what it did, and read the answer.

This matters beyond speed. "Why is this endpoint slow?" is the most common real task a backend engineer is handed, and it is a standard interview question in two forms: what is an index and what is the N+1 problem. By the end of this lesson both are things you have done, not things you have read.

Step 0 · Give the database enough data to be slow

Forty rows fit in memory and every plan looks the same. Load 200 000. Save this as seed.sql next to your migrations:

-- seed.sql — replaces the table contents with 200 000 bookmarks
TRUNCATE bookmark_tags, tags, bookmarks RESTART IDENTITY;

INSERT INTO bookmarks (url, title, created_at)
SELECT
    'https://example.com/article/' || n,
    'Article number ' || n,
    now() - (n || ' minutes')::interval
FROM generate_series(1, 200000) AS n;

INSERT INTO tags (name)
SELECT 'tag-' || n FROM generate_series(1, 40) AS n;

-- every bookmark gets 3 tags
INSERT INTO bookmark_tags (bookmark_id, tag_id)
SELECT b.id, 1 + ((b.id * k) % 40)
FROM bookmarks b, generate_series(1, 3) AS k
ON CONFLICT DO NOTHING;

ANALYZE bookmarks;
ANALYZE tags;
ANALYZE bookmark_tags;
$ docker cp seed.sql pg-bookmarks:/seed.sql
$ docker exec pg-bookmarks psql -U learner -d bookmarks -f /seed.sql
INSERT 0 200000
INSERT 0 40
INSERT 0 585000
Do not skip the ANALYZE

ANALYZE updates the statistics that PostgreSQL uses to choose a plan. After a bulk load the old statistics say the table is empty, so the planner makes decisions for an empty table and every measurement you take is a lie. Run ANALYZE after any large load, and any time a plan surprises you.

Step 1 · Make the failure observable

Look up one bookmark by its title. This is an ordinary thing an API does.

bookmarks=# EXPLAIN (ANALYZE, BUFFERS)
bookmarks-# SELECT id, url FROM bookmarks WHERE title = 'Article number 137000';

 Seq Scan on bookmarks  (cost=0.00..5068.00 rows=1 width=42)
                        (actual time=6.759..9.797 rows=1 loops=1)
   Filter: (title = 'Article number 137000'::text)
   Rows Removed by Filter: 199999
   Buffers: shared hit=2568
 Planning Time: 0.348 ms
 Execution Time: 9.846 ms

Read the Rows Removed by Filter line again. To return one row, PostgreSQL examined all 200 000 rows and discarded 199 999 of them. The Buffers line counts the 8 kB pages it touched: 2568 of them. shared hit means the server found every page in its own memory cache, so this run read nothing from the disk. A cold cache reports shared read instead, and the same plan is much slower. This is a sequential scan: read everything, keep what matches.

Ten milliseconds sounds survivable. It is not. The shape of the growth matters more than the size of the number: a sequential scan costs time in direct proportion to the row count. Ten times more rows cost about ten times more time. The query also runs on every request, and it holds a connection from your pool for the whole time.

Step 2 · Read the plan

What you just ran is a query plan — the list of steps PostgreSQL chose in order to answer your question. EXPLAIN shows the plan; EXPLAIN ANALYZE runs the query and shows the plan annotated with what really happened.1 The difference matters, because the planner's guesses can be wrong, and the gap between guess and reality is usually the bug.

 Seq Scan on bookmarks  (cost=0.00..5068.00 rows=1 width=42)
 └ what it did          └ the planner's GUESS ─────────────┘
                        (actual time=6.759..9.797 rows=1 loops=1)
                        └ what really happened ───────────────────┘
   Rows Removed by Filter: 199999   ← work done for nothing
   Buffers: shared hit=2568         ← 8 kB pages touched
 Execution Time: 9.846 ms           ← the number you report
  • cost is not milliseconds. It is an arbitrary unit the planner uses to compare its own options, where 1.0 is roughly the cost of reading one page in sequence.1 Never quote it as a duration. Use it only to compare two plans for the same query.
  • rows=1 in each pair is the estimate on the left and the truth on the right. When these differ by a large factor, the planner is working from bad statistics and may have chosen a bad plan. That is your cue to run ANALYZE.
  • Rows Removed by Filter is the line that finds most problems. It is the amount of work the database did and then threw away.
  • Buffers counts 8 kB pages touched. hit came from cache, read came from disk. This is the most honest measure of work, because it does not change when your laptop is busy.
  • Read the plan from the inside out. The deepest, most indented node runs first and passes its rows upward.

Always use EXPLAIN (ANALYZE, BUFFERS), not bare EXPLAIN. Bare EXPLAIN shows you what the planner intends, which is exactly the thing you are trying to check. Careful: ANALYZE really executes the query, so on an UPDATE or DELETE it really changes your data. Wrap those in BEGIN; … ROLLBACK;.

Step 3 · The fix, and the two you already had

An index is a second, sorted copy of one or more columns, kept up to date by the database, that lets it jump straight to the rows you want instead of reading every row. It is the same idea as the index at the back of a book.

bookmarks=# CREATE INDEX bookmarks_title_idx ON bookmarks (title);
bookmarks=# ANALYZE bookmarks;
bookmarks=# EXPLAIN (ANALYZE, BUFFERS)
bookmarks-# SELECT id, url FROM bookmarks WHERE title = 'Article number 137000';

 Index Scan using bookmarks_title_idx on bookmarks
        (cost=0.42..8.44 rows=1 width=42) (actual time=0.054..0.056 rows=1 loops=1)
   Index Cond: (title = 'Article number 137000'::text)
   Buffers: shared hit=1 read=3
 Execution Time: 0.085 ms
The measurement

9.846 ms → 0.085 ms. 116 times faster. More telling: 2568 pages → 4 pages. Rows Removed by Filter is gone from the plan entirely, because no row was examined and rejected. The page count is the number to trust — it does not move when your machine is busy.

Now look at what was already there before you created anything:

bookmarks=# \d bookmarks
Indexes:
    "bookmarks_pkey" PRIMARY KEY, btree (id)
    "bookmarks_url_key" UNIQUE CONSTRAINT, btree (url)

You have had two indexes since Lesson 4 without writing the word INDEX once. This is how PostgreSQL enforces those two constraints: to check that an id or a url is unique it needs to find the existing value fast, and an index is how it does that. So GET /bookmarks/{id} was always fast, and lookups by url were always fast, and lookups by title were not — and nothing in your Python said so. \d is where you look first when something is slow.

Step 4 · The index that does nothing

Now build the feature this was all for: search. Prefix search on the title, newest first. The index on title is still in place from Step 3.

bookmarks=# EXPLAIN (ANALYZE, BUFFERS)
bookmarks-# SELECT id, title FROM bookmarks WHERE title LIKE 'Article number 1370%';

 Seq Scan on bookmarks  (cost=0.00..5068.00 rows=2020 width=29)
                        (actual time=0.098..11.767 rows=111 loops=1)
   Filter: (title ~~ 'Article number 1370%'::text)
   Rows Removed by Filter: 199889
   Buffers: shared hit=2568
 Execution Time: 11.810 ms
Stop and notice what just happened

The index on title exists. The query filters on title. PostgreSQL ignored the index and read all 200 000 rows. If you had trusted "I added an index, so it is fast now" you would have shipped this and been wrong — and nothing would have told you.

The reason is sorting order. Your database sorts text by the rules of its collation, which here is en_US.utf8 — the order a dictionary uses, where case and punctuation are handled the way a human expects. A prefix search needs the other kind of order: strict character-by-character comparison. In dictionary order the rows starting with a given prefix are not stored next to each other, so the index cannot hand back a contiguous range, so it is useless for this query. The PostgreSQL manual is explicit about it:

"The operator classes text_pattern_ops, varchar_pattern_ops, and bpchar_pattern_ops support B-tree indexes on the types text, varchar, and char respectively. The difference from the default operator classes is that the values are compared strictly character by character rather than according to the locale-specific collation rules. This makes these operator classes suitable for use by queries involving pattern matching expressions (LIKE or POSIX regular expressions) when the database does not use the standard C locale."

— PostgreSQL, Operator Classes and Operator Families

So you ask for an index sorted the other way. Write it as a migration — migration 0003, beside the two from Lesson 4:

-- migrations/0003_add_title_search_index.sql
CREATE INDEX bookmarks_title_pattern_idx
    ON bookmarks (title text_pattern_ops);
 Index Scan using bookmarks_title_pattern_idx on bookmarks
        (cost=0.42..8.44 rows=20 width=29) (actual time=0.051..0.095 rows=111 loops=1)
   Index Cond: ((title ~>=~ 'Article number 1370'::text)
            AND (title ~<~ 'Article number 1371'::text))
   Filter: (title ~~ 'Article number 1370%'::text)
   Buffers: shared hit=23 read=4
 Execution Time: 0.128 ms
The measurement

11.810 ms → 0.128 ms. 92 times faster, and 2568 pages → 27. Look at Index Cond: PostgreSQL rewrote your LIKE into a range — everything from 'Article number 1370' up to but not including 'Article number 1371'. That rewrite is the whole trick, and it is only correct in character-by-character order.

One useful detail: this single index serves both queries. Exact match on title also uses bookmarks_title_pattern_idx, so you can drop bookmarks_title_idx and keep one index instead of two. It will not help an ORDER BY title that needs dictionary order — that still wants the default index. Two indexes on one column is a legitimate choice; just make it deliberately.

Prefix search only. LIKE '%middle%' — a leading wildcard — cannot use a B-tree at all, in any operator class, because there is no prefix to jump to. That is a full-text search or a trigram index, and it is a different lesson.

Step 5 · Which column comes first

Open Lesson 4's migration 0002. There is a line in it you copied without a reason:

CREATE TABLE bookmark_tags (
    bookmark_id  BIGINT NOT NULL REFERENCES bookmarks(id) ON DELETE CASCADE,
    tag_id       BIGINT NOT NULL REFERENCES tags(id)      ON DELETE CASCADE,
    PRIMARY KEY (bookmark_id, tag_id)
);

CREATE INDEX bookmark_tags_tag_id_idx ON bookmark_tags (tag_id);  ← why?

The primary key already indexes both columns. So why a second index on a column the primary key covers? Take it away and ask.

-- "which tags does this bookmark have?" — filters on bookmark_id
 Index Only Scan using bookmark_tags_pkey on bookmark_tags
        (actual time=0.096..0.098 rows=1 loops=1)
   Index Cond: (bookmark_id = 137000)
 Execution Time: 0.162 ms

-- "which bookmarks have this tag?" — filters on tag_id, index dropped
 Parallel Seq Scan on bookmark_tags  (actual time=0.019..13.256 rows=6667 loops=3)
   Filter: (tag_id = 7)
   Rows Removed by Filter: 188333
 Execution Time: 21.895 ms

A multi-column index is sorted by its first column, then by its second inside each group of equal first values — exactly like a phone book sorted by surname, then first name. A phone book finds every "Okonkwo" instantly and cannot find every "Amara" without reading the whole thing. So an index on (bookmark_id, tag_id) answers questions about bookmark_id, and about both together, and is no help at all for tag_id alone.3

The rule

A multi-column index can be used for a query that filters on its leftmost columns, in order. Index (a, b, c) serves a, and a, b, and a, b, c. It does not serve b, or c, or b, c.

Put the index back and the same query becomes:

 Bitmap Heap Scan on bookmark_tags  (actual time=0.566..4.989 rows=20000 loops=1)
   Recheck Cond: (tag_id = 7)
   Heap Blocks: exact=3162
   ->  Bitmap Index Scan on bookmark_tags_tag_id_idx (actual time=0.353..0.353 rows=20000 loops=1)
         Index Cond: (tag_id = 7)
 Execution Time: 5.312 ms

21.9 ms → 5.3 ms. Four times faster, not a hundred — and the reason is worth as much as the fix. Tag 7 is on 20 000 of the 585 000 rows. An index earns its keep in proportion to how much it lets the database skip, and this one only skips 97%. That is also why the plan is a bitmap scan: with that many matches, PostgreSQL collects the row locations first, sorts them, and then reads the table in physical order, because 20 000 random single-row reads would cost more than the scan it replaced. An index on a column with few distinct values — a boolean, a status with three states — often earns nothing at all.

Step 6 · Indexes are not free

Every index is a second structure the database must update on every INSERT, UPDATE, and DELETE. Two identical tables, one with just its primary key, one with three more indexes; the same 200 000 rows into each:

bookmarks=# -- 1 index (the primary key)
INSERT 0 200000
Time: 250.825 ms

bookmarks=# -- 4 indexes
INSERT 0 200000
Time: 1533.350 ms

 one_index | four_indexes
-----------+--------------
 22 MB     | 50 MB

Six times slower to write, and more than twice the disk. So the answer to "should I add an index?" is never automatically yes. Add one when you have a measured slow query, add the one that plan asks for, and measure again. An index nobody's query uses is pure cost — and pg_stat_user_indexes will tell you which ones those are.

Step 7 · Every query is fast and the endpoint is slow

This is the other kind of slowness, and it does not show up in any single EXPLAIN, which is exactly why it survives so long in real code.

Listing bookmarks with their tags. The obvious way: fetch the page of bookmarks, then for each one fetch its tags.

def with_n_plus_1(conn):
    cur = conn.cursor(row_factory=dict_row)
    cur.execute("SELECT id, url, title FROM bookmarks ORDER BY id LIMIT %s", (PAGE,))
    rows = cur.fetchall()
    for row in rows:                      # <- the bug is this loop
        cur.execute(
            "SELECT t.name FROM tags t"
            " JOIN bookmark_tags bt ON bt.tag_id = t.id"
            " WHERE bt.bookmark_id = %s ORDER BY t.name",
            (row["id"],),
        )
        row["tags"] = [r["name"] for r in cur.fetchall()]
    return rows

Every one of those queries is indexed and takes well under a millisecond. There is nothing to find in any individual plan. But for a page of 100 bookmarks the code runs 1 + 100 = 101 queries where 1 would do. This is the N+1 problem: one query to get N things, then N more queries, one per thing.

Run n_plus_1.py, which does it both ways and times them:

$ python n_plus_1.py
N+1                9.5 ms    101 queries   100 rows
single query       1.3 ms      1 queries   100 rows

the join is 7x faster

Seven times. Real, but not alarming — and that is the trap. Your database is on localhost. The 100 extra queries add 8.2 ms in total, so one round trip costs about 80 microseconds here. In production the database sits on another machine, and one round trip costs about a millisecond. The N+1 version pays that cost 101 times. The join pays it once.

You do not have to imagine this. slow_link.py is a small TCP proxy that forwards to PostgreSQL and adds one millisecond in each direction — production latency, on your laptop. Run it, point DATABASE_URL at port 55433, and run exactly the same script:

$ python slow_link.py &
slow link: localhost:55433 -> localhost:55432  (+1 ms each way)

$ export DATABASE_URL="postgresql://learner:lesson4@localhost:55433/bookmarks"
$ python n_plus_1.py
N+1              329.5 ms    101 queries   100 rows
single query       6.5 ms      1 queries   100 rows

the join is 51x faster
Why this one is worth remembering

The code did not change. The database did not change. Only the distance changed, and a 7× problem became a 51× problem. N+1 is the bug that behaves on your laptop and fails in production, and it is the single most common performance defect in web applications — which is why interviewers ask about it.

The fix is to make the database do the joining, once — the query you already wrote in Lesson 4, with its LEFT JOIN and array_agg ... FILTER. The rule to carry: a query inside a loop over rows is the bug. Learn to see that shape. In Lesson 6 you will meet an ORM, which produces this shape by default and hides it behind attribute access — bookmark.tags looks free and is a network round trip.

Measure at the layer your claim lives in

Timing this through curl would have been the natural move, and it would have misled you: at this scale an HTTP round trip on localhost is dominated by TCP behaviour that has nothing to do with your database, and the noise is larger than the effect you are measuring. A claim about query cost is measured in EXPLAIN. A claim about round trips is measured around the database calls. A claim about the endpoint needs many requests and a median, not one curl. One measurement is never a measurement.

Practice

  1. Seed and confirm the slow query. Load seed.sql, then run the Step 1 EXPLAIN. Find Rows Removed by Filter in your own output and say the number out loud. Your timings will differ from the ones above; the page counts will not.
  2. Fix it and prove it. Create the index, re-run the same EXPLAIN, and write down four numbers: execution time before and after, buffers before and after. Those four numbers are your README line.
  3. Break the assumption. With the index on title in place, run the LIKE 'Article number 1370%' query. Confirm you get a Seq Scan before you read the explanation again. This is the step that teaches you not to trust "I added an index".
  4. Ship migration 0003. Write 0003_add_title_search_index.sql, run your migrate.py from Lesson 4, and confirm it says applied 0003_add_title_search_index. Then add the /bookmarks/search endpoint from main.py and search for something.
  5. Test the leftmost-columns rule yourself. Drop bookmark_tags_tag_id_idx, run EXPLAIN (ANALYZE, BUFFERS) SELECT bookmark_id FROM bookmark_tags WHERE tag_id = 7;, then create it again and re-run. Predict the plan before each run. Being wrong here is the useful part.
  6. Feel the latency. Run n_plus_1.py against localhost, then start slow_link.py and run it against port 55433. Then change PAGE from 100 to 500 and predict both numbers before you run it.
  7. Find one in the wild. Open your own bookmarks-api/main.py and look for any query inside a loop. If there is not one yet, there will be — this is a shape to keep checking for.
  8. Write the README section. Three or four lines: the query, the plan before, the plan after, the numbers. This is the single most employer-legible thing in your repository so far, because almost no junior candidate has one.

Check yourself

Answer before you scroll back. Getting one wrong now is worth more than getting it right by re-reading.
