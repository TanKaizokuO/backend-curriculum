Concurrency and the ORM Two requests arrive at the same moment. One of the two writes disappears.

Every measurement in Lesson 5 came from one client. Real servers answer many clients at the same instant. Today you make two writers fight over one row. One write vanishes, and no error message appears. You fix the defect three ways, and you measure which fix costs the least. Then you meet an ORM, and you find that it writes both of Lesson 5's defects and today's defect for you — in code that looks correct.

The whole lesson in one sentence

A transaction protects you from a crash, but it does not protect you from another transaction — so the rule is never compute a new value in Python from a value you read a moment ago. Let the database read and write in one step, or lock the row first.

This defect is called the lost update. It hides well. Your tests pass, because one test client makes one request at a time. The interview question is "what are isolation levels, and what is optimistic locking?". By the end of this lesson both answers are things you measured.

Step 0 · Give the row something to fight over

Your bookmarks table has no counter. Add one. Write migration 0004 beside the three you already have:

-- migrations/0004_add_visit_count.sql
ALTER TABLE bookmarks
    ADD COLUMN visit_count BIGINT NOT NULL DEFAULT 0;
$ python migrate.py
skip    0001_create_bookmarks
skip    0002_create_tags
skip    0003_add_title_search_index
applied 0004_add_visit_count

This ALTER TABLE is instant on 200 000 rows. PostgreSQL 11 and later store the new default in the catalogue, so the server rewrites no row. A default that calls a function, such as now(), does rewrite the table — and that statement holds an ACCESS EXCLUSIVE lock while it runs.

Step 1 · Make the failure observable

Open two terminal windows. Start psql in each one. Call them session A and session B. Both sessions count a visit to bookmark 1. Each session reads the counter, adds one in its own head, and writes the answer back.

Both sessions read 0. Both sessions now write 1.

-- session A
bookmarks=*# UPDATE bookmarks SET visit_count = 1 WHERE id = 1;
UPDATE 1

-- session B
bookmarks=*# UPDATE bookmarks SET visit_count = 1 WHERE id = 1;

Two visits. The counter says one.

Read the four outputs again. Both transactions succeeded. Both UPDATE statements report UPDATE 1. Both COMMIT statements report COMMIT. PostgreSQL raised no error, because neither transaction broke a rule. Session B simply wrote a value that it computed from data that was already out of date.

Nothing here is a PostgreSQL defect. Both transactions kept every ACID promise from Lesson 4. The defect is in the shape of the code: a read, then a decision in Python, then a write. Between the read and the write the world moved.

Step 2 · Measure the loss

Two sessions lose one write. Twenty threads lose most of them. Run lost_update.py. Twenty threads each add one to the counter, ten times. The correct answer is always 200.

$ python lost_update.py
20 threads, 10 increments each, expected 200

read-modify-write         12 / 200     194.8 ms     0 retries   LOST 188

The code kept 12 of the 200 visits. It threw away 188 of them. Your log file shows 200 successful requests and your counter shows 12. This is the reason the defect survives so long in real systems: the number is wrong, and it is plausible.

Your numbers differ from these

The lost count and the times change on each run. The threads race, and the operating system picks the order. Run the script three times and you get three different wrong numbers. That is the invariant, and it is the point: the first strategy loses writes, and it never reports an error.

The Python that produces it is the shape you must learn to see:

def read_modify_write(conn):
    with conn.transaction():
        row = conn.execute(
            "SELECT visit_count FROM bookmarks WHERE id = %s", (BOOKMARK_ID,)
        ).fetchone()
        conn.execute(                          # row[0] is already stale
            "UPDATE bookmarks SET visit_count = %s WHERE id = %s",
            (row[0] + 1, BOOKMARK_ID),
        )

Step 3 · Why the database allows it

PostgreSQL runs your transaction at an isolation level. The level decides what your transaction sees of other transactions. The default level is READ COMMITTED. The manual states the rule in one sentence:

"In effect, a SELECT query sees a snapshot of the database as of the instant the query begins to run."

— PostgreSQL, Transaction Isolation, §13.2.1

Read that as each query, not each transaction. Two queries in one transaction take two snapshots. So a value can change under you inside a single transaction. Watch it happen. Session B stays inside one transaction and reads twice. Session A commits a change between the two reads:

-- session B
bookmarks=# BEGIN;
BEGIN
bookmarks=*# SELECT visit_count FROM bookmarks WHERE id = 1;
 visit_count
-------------
           0
(1 row)

-- session A, in the other window:
--     UPDATE bookmarks SET visit_count = 5 WHERE id = 1;

bookmarks=*# SELECT visit_count FROM bookmarks WHERE id = 1;
 visit_count
-------------
           5
(1 row)

The same query in the same transaction returned two answers. The standard name for this is a non-repeatable read. It is permitted at READ COMMITTED, and PostgreSQL chooses that level by default because it is cheap and it never blocks a reader.

So the database is not going to stop you. Three tools stop you instead. Use them in this order.

Step 4 · Fix 1 · Let the database do the arithmetic

The best fix removes the read. Write one statement, and put the addition inside it:

UPDATE bookmarks SET visit_count = visit_count + 1 WHERE id = 1;

One statement is atomic against other statements. PostgreSQL takes a row lock, reads the current value, adds one, and writes the result. No other transaction can read the old value and win the race, because no window exists between the read and the write.

one statement            200 / 200     178.3 ms     0 retries   correct
The measurement

200 of 200, and it is the fastest of the four. Correct code is cheaper than the defect here, because the defect makes two round trips and this makes one. Prefer this fix whenever the new value is a function of the old value: a counter, a balance, a stock level, a flag you flip.

Step 5 · Fix 2 · Lock the row first

Some decisions need Python. You must read the row, apply a rule, and then write. In that case, take a lock on the read. Add FOR UPDATE:

SELECT visit_count FROM bookmarks WHERE id = 1 FOR UPDATE;

"FOR UPDATE causes the rows retrieved by the SELECT statement to be locked as though for update. This prevents them from being locked, modified or deleted by other transactions until the current transaction ends."

— PostgreSQL, Explicit Locking, §13.3.2

Do it in the two windows. Session A takes the lock and holds it:

-- session A
bookmarks=# BEGIN;
BEGIN
bookmarks=*# SELECT visit_count FROM bookmarks WHERE id = 1 FOR UPDATE;
 visit_count
-------------
           0
(1 row)
-- session B: this prints nothing. It waits.
bookmarks=# BEGIN;
BEGIN
bookmarks=*# SELECT visit_count FROM bookmarks WHERE id = 1 FOR UPDATE;
-- no prompt comes back

A blocked session is invisible, so learn where to look. A third window shows you who waits and what for:

bookmarks=# SELECT pid, state, wait_event_type, wait_event
bookmarks-#   FROM pg_stat_activity WHERE state <> 'idle';

 pid |        state        | wait_event_type |  wait_event
-----+---------------------+-----------------+---------------
  98 | idle in transaction | Client          | ClientRead
 104 | active              | Lock            | transactionid

Session A is idle in transaction: it holds a lock and it waits for a human. Session B is active with wait_event_type = Lock: it waits for session A. Now session A finishes, and session B wakes up:

-- session A
bookmarks=*# UPDATE bookmarks SET visit_count = 1 WHERE id = 1;
bookmarks=*# COMMIT;
COMMIT

-- session B, which was blocked, now returns
 visit_count
-------------
           1
(1 row)

bookmarks=*# UPDATE bookmarks SET visit_count = 2 WHERE id = 1;
UPDATE 1
bookmarks=*# COMMIT;
COMMIT

Session B read 1, not 0. The lock made the second reader wait, and the wait made it read the fresh value. Two visits, and the counter says 2.

SELECT FOR UPDATE        200 / 200     247.9 ms     0 retries   correct
Keep a locked transaction short

A lock lasts until the transaction ends. Never hold one across a call to another service, and never hold one while you wait for a user. Two transactions that take two locks in opposite orders produce a deadlock. PostgreSQL detects the deadlock and aborts one transaction. Always lock rows in the same order in every code path.

Step 6 · Fix 3 · Let the database refuse, then retry

The third tool changes the isolation level instead of the code. Ask for REPEATABLE READ. At that level your transaction takes one snapshot at its first statement and keeps it. Repeat the Step 3 experiment at the new level:

bookmarks=# BEGIN TRANSACTION ISOLATION LEVEL REPEATABLE READ;
BEGIN
bookmarks=*# SELECT visit_count FROM bookmarks WHERE id = 1;
 visit_count
-------------
           5
(1 row)

-- session A commits:  UPDATE bookmarks SET visit_count = 9 WHERE id = 1;

bookmarks=*# SELECT visit_count FROM bookmarks WHERE id = 1;
 visit_count
-------------
           5
(1 row)

The second read returned 5 again. The non-repeatable read is gone. Now try to write:

bookmarks=*# UPDATE bookmarks SET visit_count = 6 WHERE id = 1;
ERROR:  could not serialize access due to concurrent update
bookmarks=!#
This error is the feature

PostgreSQL refused the write. Your transaction read version 5 and another transaction has already replaced it, so the write would be based on a value that no longer exists. The database cannot guess what you meant, so it aborts your transaction. Note the prompt: bookmarks=!# means the transaction failed and accepts only ROLLBACK.

The manual is direct about your duty here:

"Applications using this level must be prepared to retry transactions due to serialization failures."

— PostgreSQL, Transaction Isolation, §13.2.2

So you catch the error and you run the whole transaction again. This is optimistic locking: take no lock, assume no conflict, and pay for the conflict when it happens.

while True:
    try:
        with conn.transaction():
            conn.execute("SET TRANSACTION ISOLATION LEVEL REPEATABLE READ")
            row = conn.execute(
                "SELECT visit_count FROM bookmarks WHERE id = %s", (ID,)
            ).fetchone()
            conn.execute(
                "UPDATE bookmarks SET visit_count = %s WHERE id = %s",
                (row[0] + 1, ID),
            )
        return
    except errors.SerializationFailure:
        retries += 1                 # and go round again

The retry gives the correct answer. Look at the price:

read-modify-write         12 / 200     194.8 ms     0 retries   LOST 188
SELECT FOR UPDATE        200 / 200     247.9 ms     0 retries   correct
one statement            200 / 200     178.3 ms     0 retries   correct
REPEATABLE READ + retry  200 / 200     772.3 ms  1411 retries   correct

1411 retries for 200 increments. Twenty threads all want one row, so almost every attempt loses a race and starts again. Optimistic locking suits low contention. This row is the opposite of low contention, so the pessimistic lock in Step 5 wins, and the single statement in Step 4 wins outright.

Choose the fix from the contention, not from taste

Ask one question: how often do two requests touch the same row?

  • The new value comes from the old value. Use one statement. Step 4.
  • Python must decide, and the row is hot. Lock the row with FOR UPDATE. Step 5.
  • Python must decide, and conflicts are rare. Use REPEATABLE READ and a retry. Step 6.

Step 7 · The four levels, and the two you will use

The SQL standard names four isolation levels. It defines three of them by the problems they forbid. PostgreSQL implements three distinct levels, because READ UNCOMMITTED behaves the same as READ COMMITTED.1

LevelDirty readNon-repeatable readPhantom readSerialization anomaly
READ UNCOMMITTEDnopossiblepossiblepossible
READ COMMITTED (default)nopossiblepossiblepossible
REPEATABLE READnononopossible
SERIALIZABLEnononono

The four problem names are worth ten seconds each:

  • Dirty read — you read data that another transaction wrote and did not commit. PostgreSQL never permits this at any level.
  • Non-repeatable read — you read one row twice and get two values. You saw this in Step 3.
  • Phantom read — you run one query twice and the second run returns extra rows. PostgreSQL forbids it at REPEATABLE READ, although the standard permits it there.
  • Serialization anomaly — two transactions each read what the other one writes, and the result matches no order of running them one at a time. Only SERIALIZABLE forbids it.

Two transactions read each other's totals and each writes a sum. Both commit at REPEATABLE READ, and the two sums disagree with every serial order. SERIALIZABLE aborts one of them with could not serialize access due to read/write dependencies among transactions. You pay for the check, and you must still write the retry. Reach for it when a business rule spans several rows.

Step 8 · Put the fix in the API

Add one endpoint to main.py. It counts a visit and returns the new total:

@app.post("/bookmarks/{bookmark_id}/visit")
async def record_visit(bookmark_id: int):
    async with app.state.pool.connection() as conn:
        cur = await conn.cursor(row_factory=dict_row).execute(
            "UPDATE bookmarks SET visit_count = visit_count + 1"
            " WHERE id = %s RETURNING id, visit_count",
            (bookmark_id,),
        )
        row = await cur.fetchone()
    if row is None:
        raise HTTPException(status_code=404, detail="Bookmark not found")
    return row

One statement does four jobs. It locks the row, it adds one, it hands back the new value with RETURNING, and it returns no row for an id that does not exist — which is your 404. Now prove it under load. Send 300 requests with 30 in flight at once:

$ seq 1 300 | xargs -P 30 -I{} \
      curl -s -o /dev/null -X POST localhost:8000/bookmarks/1/visit
$ curl -s localhost:8000/bookmarks/1
{"id":1,"url":"https://example.com/article/1","title":"Article number 1",
 "created_at":"2026-08-09T19:43:53.001140+00:00","visit_count":300}
300 requests, 300 visits

This is the demonstrable artifact for today. Run the same 300 requests against a read-modify-write version of the endpoint and record the number you get. Two numbers from the same load, one of them wrong, is a very strong README section.

Step 9 · The ORM, and the SQL it writes for you

An ORM maps table rows onto Python objects. SQLAlchemy is the standard choice in Python, and most job adverts that name Python name it or name Django's ORM. You now know SQL, so you can do the only thing that makes an ORM safe: read the SQL it sends.

Describe the schema the migrations already built. Note what is absent:

# orm_models.py
class Base(DeclarativeBase):
    pass

bookmark_tags = Table(
    "bookmark_tags", Base.metadata,
    Column("bookmark_id", ForeignKey("bookmarks.id", ondelete="CASCADE"), primary_key=True),
    Column("tag_id", ForeignKey("tags.id", ondelete="CASCADE"), primary_key=True),
)

class Bookmark(Base):
    __tablename__ = "bookmarks"

    id: Mapped[int] = mapped_column(primary_key=True)
    url: Mapped[str]
    title: Mapped[str | None]
    created_at: Mapped[datetime.datetime]
    visit_count: Mapped[int]

    # This attribute is a query. Read that sentence again.
    tags: Mapped[list["Tag"]] = relationship(
        secondary=bookmark_tags, order_by="Tag.name"
    )

There is no Base.metadata.create_all() in that file. The migrations own the schema, and these classes only describe it. Keep it that way. An ORM that creates your tables gives you no version history, no review, and no way to change a live database safely. Alembic is SQLAlchemy's migration tool, and it does the job your migrate.py does by hand.

Now turn on echo=True and list ten bookmarks with their tags:

rows = session.scalars(select(Bookmark).order_by(Bookmark.id).limit(10)).all()
return [(b.title, [t.name for t in b.tags]) for b in rows]

You have seen this before

This is Lesson 5's N+1 problem, and the ORM wrote it for you. The expression b.tags looks like an attribute access. It is a network round trip. Nothing in the Python says so, and no single EXPLAIN finds it. This is the exact reason Lesson 5 came before this lesson.

SQLAlchemy calls this the lazy loader strategy, and it is the default for every relationship.3 You change it for one query with .options(). Two options matter:

  • selectinload(Bookmark.tags) — one query for the bookmarks, then one more query with WHERE bookmarks_1.id IN (...) for every tag. Two queries, whatever the page size.
  • joinedload(Bookmark.tags) — one query with a LEFT OUTER JOIN. Add .unique() to the result, because the join returns one row for each pair.
$ python orm_n_plus_1.py
page of 100 bookmarks

lazy (default)      69.3 ms    101 queries   100 rows   first tags: ['tag-2', 'tag-3', 'tag-4']
selectinload         5.0 ms      2 queries   100 rows   first tags: ['tag-2', 'tag-3', 'tag-4']
joinedload           3.1 ms      1 queries   100 rows   first tags: ['tag-2', 'tag-3', 'tag-4']

selectinload is 14x faster than the default

The multiplier moves with the state of the cache, so your run shows a different one. The query counts do not move: 101, 2 and 1 are exact.

Look at the SQL that joinedload produced, because you have written it before:

SELECT anon_1.id, anon_1.url, anon_1.title, anon_1.created_at, anon_1.visit_count,
       tags_1.id AS id_1, tags_1.name
FROM (SELECT bookmarks.id AS id, ... FROM bookmarks ORDER BY bookmarks.id
      LIMIT %(param_1)s::INTEGER) AS anon_1
LEFT OUTER JOIN (bookmark_tags AS bookmark_tags_1
                 JOIN tags AS tags_1 ON tags_1.id = bookmark_tags_1.tag_id)
             ON anon_1.id = bookmark_tags_1.bookmark_id
ORDER BY anon_1.id, tags_1.name

That is the Lesson 4 query: put the LIMIT in a subquery, then LEFT JOIN the tags. The ORM did not invent a technique. It typed for you, and only after you told it which technique to use.

Step 10 · The ORM writes today's defect too

Count a visit through the ORM. This is the idiomatic line, and every tutorial shows it:

bookmark = session.get(Bookmark, 1)
bookmark.visit_count += 1
session.commit()

Read the echo output:

BEGIN (implicit)
SELECT bookmarks.id, ..., bookmarks.visit_count FROM bookmarks
WHERE bookmarks.id = %(pk_1)s::INTEGER
{'pk_1': 1}
UPDATE bookmarks SET visit_count=%(visit_count)s::INTEGER WHERE bookmarks.id = ...
{'visit_count': 201, 'bookmarks_id': 1}
COMMIT

A SELECT, then an UPDATE with a number that Python computed. That is Step 1, in two lines of Python, with no SQL in sight. Twenty threads confirm it:

$ python orm_increment.py
20 threads, 10 increments each, expected 200

attribute assignment      27 / 200     275.9 ms   LOST 173
with_for_update          200 / 200     400.2 ms   correct
core update              200 / 200     287.5 ms   correct

The two fixes look like this. Both are Step 5 and Step 4, said in SQLAlchemy:

# lock the row: the SELECT carries FOR UPDATE
bookmark = session.scalars(
    select(Bookmark).where(Bookmark.id == ID).with_for_update()
).one()
bookmark.visit_count += 1

# or remove the read: the addition happens in PostgreSQL
session.execute(
    update(Bookmark).where(Bookmark.id == ID)
                    .values(visit_count=Bookmark.visit_count + 1)
)
-- the SQL the second one sends
UPDATE bookmarks SET visit_count=(bookmarks.visit_count + %(visit_count_1)s::INTEGER)
WHERE bookmarks.id = %(id_1)s::INTEGER
What an ORM buys, and what it hides

It buys real things: one place for the schema in Python, an identity map, a unit of work that batches your writes into one transaction, relationship navigation, and Alembic migrations.

It hides exactly one thing, and that thing is the cost. An attribute access can be a query. An assignment can be a read-modify-write. The skill is not "avoid the ORM". The skill is echo=True, and the habit of counting the statements.

Practice

  1. Ship migration 0004. Write 0004_add_visit_count.sql, run migrate.py, and confirm the output says applied 0004_add_visit_count and skip for the other three.
  2. Lose a write by hand. Open two psql windows and reproduce Step 1. Do not read ahead. Say the final number out loud before you run the last SELECT.
  3. Measure the loss. Run lost_update.py. Then change WORKERS from 20 to 2 and predict the four lines before you run it again. Low contention hides this defect, and that is why it reaches production.
  4. Watch a session block. Reproduce Step 5. While session B waits, run the pg_stat_activity query in a third window and find wait_event_type = Lock. This query is how you diagnose a stuck production API.
  5. Earn a serialization failure. Reproduce Step 6 until you see could not serialize access due to concurrent update and the bookmarks=!# prompt. Then run ROLLBACK and check that the prompt returns to bookmarks=#.
  6. Ship the endpoint and prove it. Add POST /bookmarks/{id}/visit. Reset the counter to 0, send the 300 requests from Step 8, and check the total. Then write the broken version, run the same load, and write down both numbers.
  7. Read the ORM's SQL. Run python orm_n_plus_1.py --echo. Count the SELECT statements in the lazy case. Then add selectinload and count again.
  8. Find the hidden write. Run python orm_increment.py --echo and find the line SET visit_count=%(visit_count)s. Explain to yourself, in one sentence, why that statement loses writes and why SET visit_count=(bookmarks.visit_count + 1) does not.
  9. Add to the README. Four lines: the 300-request load, the wrong total, the right total, and the one-line reason. Almost no junior candidate can show a measured concurrency defect and its fix.
