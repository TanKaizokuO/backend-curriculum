Deployment The API works on your laptop. No reviewer can reach your laptop.

Lessons 3 to 6 built one project. It has a JSON API, a normalised schema, migrations, an index that you measured, and a counter that survives 300 concurrent requests. It runs on localhost. A recruiter cannot open localhost. Today you move the same code to a public URL, and you keep every property that you proved. You also deploy it badly first, because each bad deploy fails in a different way, and each failure names one rule.

The whole lesson in one sentence

A deploy is one image plus one set of environment variables — so the image must hold no secret and no data, and the process must read every value that changes from the environment.

You already know the vocabulary for this. A container is a process with its own filesystem. A managed database is somebody else's PostgreSQL server with a connection string. A release step is your migrate.py from Lesson 4, run at the right moment. The new part is the order of the steps, and the failures that a wrong order produces.

Step 0 · Three stages, not one

The Twelve-Factor App splits a deploy into three stages. Learn the three words. Interviewers use them, and platforms name their settings after them.

StageInputOutputYours
Build A commit An image docker build from the Dockerfile
Release An image plus the config A release with an id The environment variables, plus python migrate.py
Run A release A running process uvicorn main:app

"The twelve-factor app uses strict separation between the build, release, and run stages. For example, it is impossible to make changes to the code at runtime, since there is no way to propagate those changes back to the build stage."

— The Twelve-Factor App, factor V

Two rules follow from the table.

  1. The image holds no config. One image runs in staging and in production. Only the environment differs. If you bake a value into the image, you need a new build for every deploy, and you leak the value to everyone who can pull the image.
  2. The release step runs between the build and the run. The schema change must land before the new code starts. It must not run inside the web process, because a platform starts many web processes.

Step 1 · Deploy it badly, and watch it fail

Four defects hide in seven lines. Find each one in the output above.

Defect 1 · localhost means this container

The database runs. It runs in another container. Inside a container, localhost is that container's own network stack, and nothing listens on port 55432 there. A container reaches another container by service name, not by localhost.

Set the variable at run time instead, and the same image starts:

$ docker run -d --name naive-2 -p 8080:8000 \
    -e DATABASE_URL=postgresql://learner:...@naive-db:5432/bookmarks bookmarks-naive
$ docker logs naive-2
INFO:     Will watch for changes in these directories: ['/app']
INFO:     Uvicorn running on http://127.0.0.1:8000 (Press CTRL+C to quit)
INFO:     Started reloader process [1] using WatchFiles
INFO:     Started server process [8]
INFO:     Waiting for application startup.
INFO:     Application startup complete.

Defect 2 · You publish the port, and it reaches nothing

The log says Application startup complete. Now request the endpoint from the host:

$ curl -sS --max-time 5 http://localhost:8080/bookmarks
curl: (56) Recv failure: Connection reset by peer

The same request from inside the container succeeds:

$ docker exec naive-2 python -c \
    "import urllib.request;print(urllib.request.urlopen('http://127.0.0.1:8000/bookmarks').read().decode())"
[[1,"https://example.com"]]
Read the second line of the log again

Uvicorn running on http://127.0.0.1:8000. The default host is 127.0.0.1. That address belongs to the container. Docker forwards the published port to the container's external address, and no socket listens there. Pass --host 0.0.0.0 and the same command works.

This failure has a signature: the container looks healthy, the log looks clean, and every request from outside dies. Learn the signature. It costs people a full afternoon.

Defect 3 · --reload costs you two processes and buys nothing

Count the processes inside the container:

$ docker exec naive-2 python -c "..."   # print /proc/<pid>/cmdline for each pid
1 /usr/local/bin/python3.12 /usr/local/bin/uvicorn main:app --reload --port 8000
7 /usr/local/bin/python3.12 -c from multiprocessing.resource_tracker import main;main(4)
8 /usr/local/bin/python3.12 -c from multiprocessing.spawn import spawn_main; ... --multiprocessing-fork

$ docker stats --no-stream --format '{{.Name}}  {{.MemUsage}}' naive-2
naive-2  66.45MiB / 30.84GiB

Three processes serve one application. PID 1 is the reloader, not the server. The reloader watches /app for source edits. The files in an image never change, so the watcher finds nothing for the whole life of the container. It also puts an extra process between the platform and your server. Use --reload on your laptop. Never use it in an image.

Defect 4 · The password is in the image

The ENV line put the credential inside the build. Anybody who can pull the image can read it. You do not need a running container:

$ docker image history --no-trunc bookmarks-naive | grep DATABASE_URL
<missing>   5 minutes ago   ENV DATABASE_URL=postgresql://learner:lesson4@localhost:55432/bookmarks

$ docker image inspect bookmarks-naive --format '{{range .Config.Env}}{{println .}}{{end}}' | grep -i database
DATABASE_URL=postgresql://learner:lesson4@localhost:55432/bookmarks
A layer is permanent

Do not fix this with a second ENV line, and do not fix it with RUN rm. An image is a stack of layers. A later layer hides a file, and the earlier layer still holds it. The only fix is to never put the secret in the build.

The rest of the lesson removes these four defects one at a time. The code that you deploy is the Lesson 6 API, with three changes and nothing else.

Step 2 · Every setting in one typed object

The Twelve-Factor App states the rule and gives you a test for it:

"A litmus test for whether an app has all config correctly factored out of the code is whether the codebase could be made open source at any moment, without compromising any credentials."

— The Twelve-Factor App, factor III

Lesson 6 read os.environ["DATABASE_URL"] at import. That works, and it fails badly. A typo in the variable name raises KeyError with no advice. A malformed URL raises inside the pool, 30 seconds later. Put every setting in one place, and validate it:

Code/Lesson_7_code/config.py

from pydantic import Field, PostgresDsn, ValidationError
from pydantic_settings import BaseSettings, SettingsConfigDict


class Settings(BaseSettings):
    model_config = SettingsConfigDict(
        env_file=".env",            # local development only; never committed
        env_file_encoding="utf-8",
        extra="ignore",
    )

    database_url: PostgresDsn
    app_env: str = "development"
    log_level: str = "info"
    pool_min_size: int = Field(default=1, ge=1)
    pool_max_size: int = Field(default=10, ge=1)

    @property
    def dsn(self) -> str:
        """psycopg wants a string, not a PostgresDsn object."""
        return str(self.database_url)


try:
    settings = Settings()
except ValidationError as exc:
    raise SystemExit(f"Bad configuration.\n{exc}") from exc

Four properties come from those 25 lines.

  1. The names are a contract. The field database_url reads the variable DATABASE_URL. The class is the list of everything the deploy needs.
  2. A bad value stops the process at once. PostgresDsn rejects a URL with the wrong scheme. The message names the field. A container that refuses to start is better than a container that starts and writes to the wrong database.
  3. Types are real. POOL_MAX_SIZE=ten fails at import, not at the first request.
  4. The repository stays public-safe. The file names variables. It holds no value.

Commit an example file. It documents the contract, and it holds no secret.

Code/Lesson_7_code/.env.example

# Copy this file to .env and fill in a real value.
#
#     cp .env.example .env
#
# Commit this file. Never commit .env.

POSTGRES_PASSWORD=change-me

APP_ENV=development
LOG_LEVEL=info
POOL_MIN_SIZE=1
POOL_MAX_SIZE=10

Put .env in .gitignore and in .dockerignore. The first keeps it out of the repository. The second keeps it out of the build context, so COPY . . cannot copy it into a layer.

Step 3 · The image

Here is the whole Dockerfile. Compare each line against the naive version.

Code/Lesson_7_code/Dockerfile

FROM python:3.12-slim

ENV PYTHONDONTWRITEBYTECODE=1 \
    PYTHONUNBUFFERED=1

WORKDIR /app

# Copy the dependency list alone, so Docker reuses the install layer while
# only the code changes.
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

COPY . .

RUN useradd --create-home --uid 10001 appuser && chown -R appuser /app
USER appuser

EXPOSE 8000

CMD ["sh", "-c", "exec uvicorn main:app --host 0.0.0.0 --port ${PORT:-8000} --forwarded-allow-ips '*'"]

Six decisions live in that file.

PYTHONUNBUFFERED=1

A platform collects your log from standard output. Python buffers standard output when it is not a terminal. A crash then loses the last lines, which are the lines that explain the crash. Turn the buffer off.

Two COPY statements, not one

Docker caches each layer. The naive file copies the source first, so any edit to main.py invalidates the pip install layer and the install runs again. Copy requirements.txt first. Then an edit to the code reuses the install layer, and the build takes seconds.

Pinned versions

Code/Lesson_7_code/requirements.txt

fastapi==0.141.1
uvicorn[standard]==0.52.1
psycopg[binary,pool]==3.3.4
pydantic-settings==2.14.2

An unpinned dependency makes the build a lottery. The image that you test today must equal the image that runs next month. The [standard] extra brings uvloop and httptools, which are the fast event loop and the fast HTTP parser.

USER appuser

The default user in a container is root. A defect in your code then runs as root inside the container, which is a much better position for an attacker. Create a normal user and switch to it. Prove it:

$ docker compose exec api id
uid=10001(appuser) gid=10001(appuser) groups=10001(appuser)

--host 0.0.0.0 and ${PORT:-8000}

Render states the requirement in one line:

"Every Render web service must bind to a port on host 0.0.0.0 to serve HTTP requests. […] The default value of PORT is 10000 for all Render web services."

— Render — Web Services

So the port is not yours to choose. Read it from the environment, and keep a default for a local run. ${PORT:-8000} does both.

sh -c and exec

Two rules fight here. The exec form of CMD does not expand a variable, so ${PORT:-8000} needs a shell. A shell then becomes PID 1, and the platform sends SIGTERM to PID 1 at every redeploy. A shell that waits on a child may not pass the signal on. The keyword exec settles it: the shell replaces itself with uvicorn, so uvicorn is PID 1 and receives the signal.

$ docker compose exec api python -c "..."   # print /proc/<pid>/cmdline for each pid
1 /usr/local/bin/python3.12 /usr/local/bin/uvicorn main:app --host 0.0.0.0 --port 8000 --forwarded-allow-ips *

One process. PID 1. Compare that with the three processes of Step 1.

Read this before you copy the flag

--forwarded-allow-ips '*' tells uvicorn to trust the X-Forwarded-For and X-Forwarded-Proto headers on every request. Use it only when a proxy that you control sits in front of the container and overwrites those headers. A platform that terminates TLS for you meets that condition. A container that the internet reaches directly does not: a client can then claim any address it likes.

Uvicorn 0.52.1 enables --proxy-headers by default, so that switch changes nothing. The switch that decides the question is --forwarded-allow-ips, and its default is 127.0.0.1.

Step 4 · The release step

Your schema lives in four SQL files, and migrate.py applies the ones that a database has not seen. Lesson 4 wrote it. Lesson 7 changes one thing: the runner now travels inside the image, and the platform calls it between the build and the run.

Code/Lesson_7_code/migrate.py

import pathlib

import psycopg

from config import settings

MIGRATIONS = pathlib.Path(__file__).parent / "migrations"

with psycopg.connect(settings.dsn) as conn:
    conn.execute("""
        CREATE TABLE IF NOT EXISTS schema_migrations (
            version     TEXT PRIMARY KEY,
            applied_at  TIMESTAMPTZ NOT NULL DEFAULT now()
        )
    """)
    conn.commit()

    rows = conn.execute("SELECT version FROM schema_migrations")
    applied = {v for (v,) in rows}

    for path in sorted(MIGRATIONS.glob("*.sql")):
        version = path.stem
        if version in applied:
            print(f"skip    {version}")
            continue
        with conn.transaction():                     # all-or-nothing
            conn.execute(path.read_text())
            conn.execute("INSERT INTO schema_migrations (version) VALUES (%s)",
                         (version,))
        print(f"applied {version}")

Two properties make this safe on a platform.

  1. It is idempotent. A second run applies nothing. That matters, because a platform may run the step twice, and because two instances may start at the same moment.
  2. Each migration runs in one transaction. A failure in the middle of a file leaves the database unchanged, and schema_migrations gets no row.

The first run applies all four files. The second run applies none:

$ docker compose logs migrate --no-log-prefix
applied 0001_create_bookmarks
applied 0002_create_tags
applied 0003_add_title_search_index
applied 0004_add_visit_count

$ docker compose run --rm migrate
skip    0001_create_bookmarks
skip    0002_create_tags
skip    0003_add_title_search_index
skip    0004_add_visit_count
Never migrate from the web process

Do not call migrate.py from the FastAPI lifespan, and do not call create_all() there. A platform runs several instances of a web service. Each instance would then run the schema change at the same instant, against the same database. Keep the schema change in its own step, and let it finish before the API starts.

Step 5 · A health check that checks something

A platform sends a request to your service every few seconds. It uses the answer for two decisions: whether a new deploy may take traffic, and whether a running instance needs a restart.

"Whenever all of the new instances are passing their health checks at the same time, Render considers the deploy successful and starts routing traffic to the new instances."

— Render — Health Checks

A route that returns {"status": "ok"} and touches nothing tells you that Python runs. You already knew that. Query the database instead:

Code/Lesson_7_code/main.py

@app.get("/healthz")
async def healthz():
    try:
        async with app.state.pool.connection() as conn:
            await conn.execute("SELECT 1")
    except Exception as exc:
        raise HTTPException(status_code=503, detail=f"database: {exc}") from exc
    return {"status": "ok", "env": settings.app_env}

Test both answers. Stop the database, ask again, then start the database and ask a third time:

$ curl -s -w '\nHTTP %{http_code}\n' localhost:8007/healthz
{"status":"ok","env":"production"}
HTTP 200

$ docker compose stop db
$ curl -s -w '\nHTTP %{http_code}\n' localhost:8007/healthz
{"detail":"database: couldn't get a connection after 30.00 sec"}
HTTP 503

$ docker compose start db
$ curl -s -w '\nHTTP %{http_code}\n' localhost:8007/healthz
{"status":"ok","env":"production"}
HTTP 200

The 503 took 30 seconds, because the pool waits for a connection for 30 seconds. Render treats a health check as failed after five seconds, so a slow 503 and a fast 503 both work for the platform. If you want a fast answer for a human, pass a short timeout to pool.connection().

Keep the endpoint cheap. It runs every few seconds, forever. One SELECT 1 is the right size. A health check that counts rows in a large table is a scheduled load test against your own database.

Step 6 · The data must outlive the container

A container's filesystem dies with the container. That is a feature, and it is also the most expensive lesson in this file if you learn it in production. The database needs storage that survives.

On one machine, a named volume gives you that:

  db:
    image: postgres:17
    volumes:
      # Warning: remove this line and a `docker compose down` destroys the
      # database. The named volume outlives the container.
      - bookmarks-data:/var/lib/postgresql/data

volumes:
  bookmarks-data:

Prove that it works. Write a row. Destroy the containers. Read the row again.

$ curl -s 'localhost:8007/bookmarks?limit=5' | python3 -c 'import sys,json;print(len(json.load(sys.stdin)),"row(s)")'
1 row(s)

$ docker compose down
 Container lesson_7_code-db-1 Removed
 Network lesson_7_code_default Removed
$ docker volume ls --filter name=lesson_7_code_bookmarks-data --format '{{.Name}}'
lesson_7_code_bookmarks-data

$ docker compose up -d
$ curl -s 'localhost:8007/bookmarks?limit=5'
[{"id":1,"url":"https://12factor.net/config","title":"Twelve-Factor: Config","created_at":"2026-08-09T20:39:05.166119+00:00","visit_count":0,"tags":["deploy","reference"]}]
$ docker compose logs migrate --no-log-prefix | tail -4
skip    0001_create_bookmarks
skip    0002_create_tags
skip    0003_add_title_search_index
skip    0004_add_visit_count

The containers are new. The row is old. The release step found the schema already in place and applied nothing.

One flag deletes the database

Run docker compose down -v only when you want an empty database. The flag removes the named volume with the containers.

$ docker compose down -v
 Volume lesson_7_code_bookmarks-data Removed
$ docker compose up -d
$ curl -s 'localhost:8007/bookmarks?limit=5'
[]

The same rule holds on a platform, in a harsher form. Render says it plainly:

"Like all Render services, Free web services have an ephemeral filesystem. This means that any changes to your web service's filesystem (uploaded images, local SQLite databases, etc.) are lost every time the service redeploys, restarts, or spins down."

— Render — Deploy for Free

So a SQLite file next to your code is not a database on a platform. It is a cache that disappears at the next deploy. Relational data goes in a managed database.

Step 7 · The whole stack on one machine

Rehearse the deploy locally. One file starts the database, runs the release step, then starts the API in that order.

Code/Lesson_7_code/compose.yaml

services:
  db:
    image: postgres:17
    environment:
      POSTGRES_USER: learner
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD:?set POSTGRES_PASSWORD in .env}
      POSTGRES_DB: bookmarks
    volumes:
      - bookmarks-data:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U learner -d bookmarks"]
      interval: 2s
      timeout: 3s
      retries: 15

  # The release step. It runs to completion, then the API starts.
  migrate:
    build: .
    command: ["python", "migrate.py"]
    environment:
      DATABASE_URL: postgresql://learner:${POSTGRES_PASSWORD}@db:5432/bookmarks
    depends_on:
      db:
        condition: service_healthy

  api:
    build: .
    ports:
      - "8007:8000"
    environment:
      # `db` is the service name. Inside the network, `localhost` is this
      # container, so `localhost` here finds no database.
      DATABASE_URL: postgresql://learner:${POSTGRES_PASSWORD}@db:5432/bookmarks
      APP_ENV: production
    depends_on:
      migrate:
        condition: service_completed_successfully

volumes:
  bookmarks-data:

Three details carry the order.

  1. condition: service_healthy holds the release step until pg_isready succeeds. A started container is not a ready database.
  2. condition: service_completed_successfully holds the API until the release step exits with status 0. A failed migration stops the API.
  3. ${POSTGRES_PASSWORD:?...} stops Compose with a message when the variable is missing. Compose reads .env for it.

Step 8 · Somebody else's PostgreSQL

You ran PostgreSQL in a container for four lessons. On a platform you buy the database instead. You get a connection string. You do not get a server.

JobYour containerManaged database
Minor version upgradesYouThe platform
BackupsYouThe platform, on a paid plan
Point-in-time recoveryYou write itA setting
Disk growthYou watch itA setting
FailoverYou build itA paid plan
Connection limitYours to raiseFixed by the plan
CostYour timeMoney each month

Read the free plan before you rely on it. Render publishes three limits that change how you use it:

  • A free database expires 30 days after you create it. A grace period of 14 days follows. Then Render deletes it and its data.
  • A free database has no backup and no managed connection pooling.
  • A free web service spins down after 15 minutes without traffic. The next request waits about one minute for the spin-up.
Say this in the interview

"The demo runs on a free plan, so the first request after an idle period takes about a minute, and the database expires after 30 days. For production I would take the cheapest paid plan, because it adds backups and a release step." That sentence shows that you read the limits. Most candidates do not.

Your connection pool needs a second look here. A free plan gives you a small connection limit, and each instance of your API opens pool_max_size connections. Two instances with POOL_MAX_SIZE=10 ask for 20 connections. That is why pool_max_size is a setting in config.py and not a constant in the code.

Step 9 · The deploy, as a file

You can create a service by hand in a dashboard. Do not. A dashboard leaves no record of what you did, and it invites you to paste a password into a form. Render reads a Blueprint from your repository instead.

Code/Lesson_7_code/render.yaml

databases:
  - name: bookmarks-db
    databaseName: bookmarks
    plan: free
    region: oregon

services:
  - type: web
    name: bookmarks-api
    runtime: docker
    plan: starter
    region: oregon          # the same region as the database
    rootDir: Code/Lesson_7_code
    dockerfilePath: ./Dockerfile

    preDeployCommand: python migrate.py
    healthCheckPath: /healthz

    envVars:
      - key: DATABASE_URL
        fromDatabase:
          name: bookmarks-db
          property: connectionString

      - key: APP_ENV
        value: production

      - key: LOG_LEVEL
        value: info

Read the fromDatabase block again. It is the best line in the file. The database writes its own connection string into the service. The password never appears in the repository, in the image, in your terminal, or in your clipboard. Nobody types it, so nobody can leak it.

preDeployCommand is the release step from Step 4. Render runs it after the build and before the new version takes traffic. If it fails, the deploy fails, and the previous version keeps the traffic.

The release step needs a paid plan

Render offers preDeployCommand for paid instance types only. On a free instance you have no separate release step, so chain the migration into the start command:

dockerCommand: sh -c "python migrate.py && exec uvicorn main:app --host 0.0.0.0 --port $PORT"

Two instances can then run the migration at the same time. The runner is idempotent, so a repeat prints skip and changes nothing. State the compromise in your README. An interviewer who knows the platform asks about it.

Validate the file before you push it. Render serves the schema from SchemaStore, so an editor with the YAML extension checks it as you type. The CLI checks it in one command:

$ render blueprints validate render.yaml

The schema also lives at https://render.com/schema/render.yaml.json. The render.yaml in this lesson validates against that schema with zero errors.

The steps for the first deploy are short.

  1. Push the repository, with render.yaml in it, to GitHub.
  2. In the Render dashboard, create a Blueprint and point it at the repository.
  3. Read the plan that Render shows you. It lists one database and one web service. Apply it.
  4. Watch the events. The build runs, the pre-deploy command runs, then the health check runs.
  5. Request https://<name>.onrender.com/healthz. A 200 answer means that the process runs and the database answers.

Warning: check the first deploy log for a failed health check before you change anything else. A failed health check after a successful build almost always means one of two things: the process does not bind 0.0.0.0, or it does not read PORT. Those are defect 2 of Step 1, on a platform.

Step 10 · The README is the artifact

A URL alone proves little. A reviewer opens your repository first, and reads for 90 seconds. Those 90 seconds decide whether they read the code. So the README carries the evidence that you collected in Lessons 5 and 6.

The full file is in Code/Lesson_7_code/README.md. Its structure is the point:

  1. One paragraph. What the service does, and what it stores. No adjectives.
  2. The live URL, with the health endpoint next to it.
  3. The stack, with versions. A table of eight rows.
  4. A diagram of the request path. Client, load balancer, container, database, plus the release step.
  5. The endpoints. One table.
  6. The measurements. This is the part that other candidates do not have.
  7. The deployment properties, as repeatable checks. Seven lines, each one a command that a reader can run.
  8. How to run it on one machine. Three commands, and the output that they print.

Why this works

A junior CV says "built a REST API with FastAPI and PostgreSQL". Yours says "measured a 92× query improvement and proved a concurrency fix under 300 concurrent requests, then deployed the result with a release step and a health check". The second one gives an interviewer a question to ask, and you have the answer, because you ran it.

Practice

  1. Break the bind. Remove --host 0.0.0.0 from the CMD line, rebuild, and request the endpoint from the host. Read the second line of the log. Put it back.
  2. Break the config. Set DATABASE_URL=postgres-ql://x and start the container. Read the message from pydantic. Compare it with what os.environ["DATABASE_URL"] would have given you.
  3. Break the release step. Write migrations/0005_broken.sql with one invalid statement. Run docker compose up. Confirm two facts: the API never starts, and schema_migrations has no row for 0005. Delete the file.
  4. Prove the layer. Add ENV SECRET=hunter2 to a copy of the Dockerfile, then add ENV SECRET= on the next line. Build it, and run docker image history --no-trunc. Find hunter2.
  5. Deploy it. Push to GitHub, apply the Blueprint, and get a 200 from /healthz on a public host. Then request /bookmarks and /docs.
  6. Measure the spin-up. Leave a free service idle for 20 minutes. Then run curl -w '%{time_total}' against /healthz twice in a row. Write both numbers in your README, and name the cause.
  7. Finish the README. Fill in the live URL. Then read the whole file as a stranger, out loud. Cut every sentence that does not carry a fact.

Where this goes

Finish practice step 5 and you have three things: a public URL, a repository that a stranger can follow, and measurements that support every claim in it. That completes the project half of this curriculum. Lessons 1 to 7 take you from a socket to a deploy.

The next question is the language. We agreed on a trigger for it in Lesson 1, and this deploy is the trigger. You are fluent in Python, and your JavaScript is rusty. Almost every concept in Lessons 1 to 7 transfers. A socket is a socket. HTTP framing does not change. An index is an index. A lost update happens in every language. What changes is the vocabulary and the type system.

Two more lessons wait after that decision: authentication (sessions against tokens, and password hashing), then testing with CI. Both are stronger with a deployed service to point at, which is why they come after today.

Where do you put the log calls, so that a platform log stays readable?
