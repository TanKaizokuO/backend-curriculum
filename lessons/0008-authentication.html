Authentication Python and TypeScript, one idea at a time.

Your API is public. Anybody can write to it. Today you add accounts, and you keep two questions apart: who is this, and what may they do? This is also the first lesson in two languages. Each idea appears once. Then you write it in Python, and then you write it in TypeScript. The second version is recognition, not new material.

The whole lesson in one sentence

The server must never trust the client. It must only trust what it can verify — a hash that it computed, or a signature that it made with a key that only it holds.

How the two languages sit together

The Python project is Code/Lesson_8_code/. The TypeScript project is Code/js/Lesson_8_code/. The routes match, the status codes match, and both write the same version strings to schema_migrations. One PostgreSQL database serves both.

Node 22.6 and later run a .ts file directly. Node strips the types and runs the JavaScript. Node does not check the types. npm run typecheck is the only step that checks them. Remember this: at run time, a TypeScript server has exactly the same protection as a JavaScript server, which is none.

Step 0 · Three words that people mix up

Learn the three words now. An interviewer asks for them, and the HTTP status codes follow from them.

WordThe questionYour answer today
Identification Who do you say you are? An email address in the request body.
Authentication Can you prove it? A password, then a session cookie or a signed token.
Authorisation May you do this? The user_id column on the row that you want to delete.

Two status codes carry the difference, and RFC 9110 defines both. 401 Unauthorized means "I do not know who you are". The name is a mistake in the standard; the code is about authentication. 403 Forbidden means "I know who you are, and the answer is no". Send a WWW-Authenticate header with the 401. Send nothing extra with the 403, because a second attempt with the same credential fails again.

Step 1 · Do it wrong first: keep the password

Start with the naive design. The users table has a password column. Registration writes the password. Login compares two strings. The code is short and it works.

Then somebody copies your table. A leak is not a strange event. It is the event that every rule in this lesson prepares for. Assume the attacker holds your rows, then ask what those rows are worth.

The first answer is easy: a plain-text column is a breach of every other site that the user visits, because people reuse passwords. So you hash the password. The next question is the one that matters. Which hash?

Read Ada's row and Grace's row again. They are the same 64 characters. A hash is a function, so equal inputs give equal outputs. The attacker learns which accounts share a password, and one cracked account opens the other.

The fix for that is a salt: random bytes, different for each user, mixed into the hash and stored next to it. bcrypt does this for you. The salt sits inside the string that bcrypt returns.

=== The same leak, as bcrypt ======================================
ada@example.com        $2b$12$NdHHEprVU2agM0RXe0YpJ.csAYs9KHW7XrQfe9AZiOHoQsDR9SiSe

Read the string from the left. $2b$ names the algorithm. $12$ is the cost. The next 22 characters are the salt. The rest is the hash. One column holds all four parts, so you never manage a salt column yourself.

The second defect: speed

SHA-256 is a fast hash, and that is its purpose. A fast hash is the wrong tool here, because the attacker also runs it fast. The same program measures both functions on one core of this machine.

Node reports fewer SHA-256 guesses per second than Python because crypto.createHash() builds an object for each call. The absolute rate is a property of this benchmark. The ratio between the two functions is the property that matters, and it stays near one million.

Read the crack result again

bcrypt did not save the five accounts. The word list held every password, so the attacker got all five. bcrypt bought 27.3 seconds instead of 0.03 milliseconds. A slow hash buys time against a guess. It does not repair a password that is on the first page of the list.

The rule, and the two lines that apply it

Use a slow hash with a per-user salt and a tunable cost. bcrypt, scrypt, and Argon2id all qualify. Choose the cost so that one login takes about 250 ms on your own server, then raise the cost as hardware improves.

Code/Lesson_8_code/security.py

import bcrypt

def hash_password(password: str) -> str:
    raw = password.encode("utf-8")[:MAX_PASSWORD_BYTES]
    salt = bcrypt.gensalt(rounds=settings.bcrypt_rounds)
    return bcrypt.hashpw(raw, salt).decode("ascii")

def verify_password(password: str, password_hash: str) -> bool:
    raw = password.encode("utf-8")[:MAX_PASSWORD_BYTES]
    try:
        return bcrypt.checkpw(raw, password_hash.encode("ascii"))
    except ValueError:
        return False

Code/js/Lesson_8_code/src/security.ts

import bcrypt from 'bcrypt';

export async function hashPassword(password: string): Promise<string> {
  return bcrypt.hash(clamp(password), config.bcryptRounds);
}

export async function verifyPassword(password: string, hash: string): Promise<boolean> {
  try {
    return await bcrypt.compare(clamp(password), hash);
  } catch {
    return false;
  }
}

Two details hide in those blocks.

  1. bcrypt reads 72 bytes. It ignores the rest. Two long passwords with the same first 72 bytes are the same password. Declare the limit in the request model, so the API rejects a longer value instead of cutting it in silence.
  2. Never compare hashes yourself. Call checkpw or compare. The library reads the cost and the salt out of the stored string, hashes the candidate the same way, and compares in constant time.

Step 2 · The account, as a table

The schema states the rule, as it did in Lesson 4. There is no password column, and the database never learns a password.

migrations/0005_create_users.sql — the same file in both projects

CREATE TABLE users (
    id             INTEGER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    email          TEXT        NOT NULL UNIQUE,
    password_hash  TEXT        NOT NULL,
    created_at     TIMESTAMPTZ NOT NULL DEFAULT now(),

    CONSTRAINT users_email_is_lower CHECK (email = lower(email)),
    CONSTRAINT users_email_has_at   CHECK (position('@' IN email) > 1)
);

The UNIQUE index stops a second account with the same email. The CHECK keeps the column lower case, so Ada@Example.com cannot register after ada@example.com. Both routes write lower($1), and the constraint proves that every future route does the same.

Step 4 · Observable failure: the token that the client can edit

The password check is done. Now the API must remember it. A browser sends one request for each page, and the user does not retype the password each time. So the server gives the client something to send back.

The naive version of "something" is a JSON object in base64. Run the program and read the first section.

Code/Lesson_8_code/forge_token.py

$ python forge_token.py

=== Attack 1 · edit an unsigned token =============================
the server gave Mallory: eyJzdWIiOiAiMiIsICJlbWFpbCI6ICJtYWxsb3J5QGV4YW1wbGUuY29tIiwgImFkbWluIjogZmFsc2V9
the server reads       : {'sub': '2', 'email': 'mallory@example.com', 'admin': False}

the server reads      : {'sub': '1', 'email': 'ada@example.com', 'admin': True}

The server believes it. Mallory is now Ada, and Ada is an admin.
Nothing crashed. No log line looks wrong.

Base64 is an encoding, not a lock. Mallory decoded the value, changed three fields, and encoded it again. The attack needs three lines of Python and no key. This is the Lesson 6 shape again: a plausible wrong answer, a clean exit code, and a log that looks healthy.

The fix: sign the bytes

Add a third part. Compute HMAC-SHA256 over the first two parts with a secret key, and append the result. The client can still read the claims. The client cannot produce a new signature, because it does not hold the key.

Code/Lesson_8_code/security.py

def _sign(message: str) -> str:
    signature = hmac.new(
        settings.secret_key.encode("utf-8"),
        message.encode("ascii"),
        hashlib.sha256,
    ).digest()
    return b64url_encode(signature)

def verify_token(token: str) -> dict:
    part1, part2, part3 = token.split(".")

    # compare_digest, not ==. A plain comparison stops at the first
    # wrong byte, and the time it takes leaks the correct prefix.
    if not hmac.compare_digest(_sign(f"{part1}.{part2}"), part3):
        raise TokenError("bad signature")

    header = json.loads(b64url_decode(part1))
    payload = json.loads(b64url_decode(part2))

    # Read the algorithm from your own list, never from the token.
    if header.get("alg") != "HS256":
        raise TokenError("unexpected algorithm")

    if payload.get("exp", 0) < time.time():
        raise TokenError("expired")

    return payload

Code/js/Lesson_8_code/src/security.ts

function sign(message: string): string {
  return crypto.createHmac('sha256', config.secretKey).update(message).digest('base64url');
}

export function verifyToken(token: string): Claims {
  const parts = token.split('.');
  if (parts.length !== 3) throw new TokenError('a token has three parts');
  const [part1, part2, part3] = parts as [string, string, string];

  // timingSafeEqual, not ===. Same reason as compare_digest.
  const expected = Buffer.from(sign(`${part1}.${part2}`));
  const given = Buffer.from(part3);
  if (expected.length !== given.length || !crypto.timingSafeEqual(expected, given)) {
    throw new TokenError('bad signature');
  }
  // … the same algorithm check and the same expiry check follow
}

Three attacks now fail. The program prints each one.

=== Attack 2 · edit a signed token ================================
the server answers    : TokenError: bad signature

=== Attack 3 · tell the server that there is no algorithm =========
Mallory sends         : eyJhbGciOiAibm9uZSIsICJ0eXAiOiAiSldUIn0.eyJzdWIiOiAiMSIs...
a verifier that trusts the header reads: {'sub': '1', 'email': 'ada@example.com'}
our verifier answers  : TokenError: bad signature

=== Attack 4 · use a token after it expires =======================
now                   : mallory@example.com
1.1 seconds later     : TokenError: expired

Attack 3 deserves a sentence of its own. The header of a JWT names the algorithm. A verifier that reads that field and obeys it accepts "alg": "none", and then every token is valid. RFC 8725 states the rule: the server holds the list of algorithms that it accepts. Our verifier checks the signature first, so the forged header never reaches a decision.

A token is not a secret box

Anybody can read the claims. No key is needed for that, because base64url is an encoding. A signature proves who wrote the claims. It does not hide them. Never put a secret, a password, or a private note in a token.

You already wrote the library

Run python security.py and npm run security. Each one builds a token by hand, builds the same token with the library, and compares.

Step 5 · The other answer: a session

A token carries the facts. A session carries a pointer. The server stores the facts in a row, and the client holds the id of that row.

migrations/0006_create_sessions.sql

CREATE TABLE sessions (
    id          TEXT        PRIMARY KEY,   -- 32 random bytes, hex encoded
    user_id     INTEGER     NOT NULL REFERENCES users (id) ON DELETE CASCADE,
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
    expires_at  TIMESTAMPTZ NOT NULL
);
Use the cryptographic generator

Generate the id with secrets.token_hex(32) in Python and crypto.randomBytes(32) in Node. Never use random or Math.random(). Those generators are predictable, and a predictable session id is a login for a stranger.

The login route writes the row and sets the cookie. Read the four flags.

Code/Lesson_8_code/main.py

response.set_cookie(
    SESSION_COOKIE,
    session_id,
    max_age=settings.session_ttl_minutes * 60,
    httponly=True,                    # JavaScript cannot read it
    samesite="lax",                   # it does not travel with a cross-site POST
    secure=settings.cookie_secure,    # HTTPS only, outside development
    path="/",
)

Code/js/Lesson_8_code/src/server.ts

res.cookie(SESSION_COOKIE, sessionId, {
  maxAge: config.sessionTtlSeconds * 1000,
  httpOnly: true,
  sameSite: 'lax',
  secure: config.cookieSecure,
  path: '/',
});
FlagWhat it stops
HttpOnly A script on your page reads document.cookie and posts the session to an attacker. With this flag, the script sees nothing.
SameSite=Lax Another site posts a form to your API and the browser attaches your cookie. This is CSRF. Lax keeps the cookie off cross-site writes.
Secure The cookie travels over plain HTTP, where anybody on the network reads it.
Max-Age A stolen cookie works forever. The browser drops it at the deadline, and the expires_at column enforces the same deadline on the server.

The cookie holds 64 hex characters and nothing else. No name, no role, no expiry that the client controls. Every fact stays on the server side.

Step 6 · The measurement that decides between them

People argue about sessions and tokens. One command settles most of the argument. Sign in twice — once for a cookie, once for a token — then log out, then use both credentials again.

cookie before logout : 200
token  before logout : 200
POST /auth/logout    : 204
cookie after  logout : 401
token  after  logout : 200

The TypeScript server prints the same five lines. The result is not a bug. It is the definition of a signed token. The server keeps no record of it, so there is nothing to delete. The token stays valid until exp.

The trade in one line

A session costs one database read for each request and gives you an instant logout. A token costs no read and gives you no logout.

Question Session cookie Signed token
Where is the state?A row in your databaseIn the client
Cost for each requestOne indexed SELECTOne HMAC, no I/O
Logout nowYes. DELETE the rowNo. Wait for exp
Ban a user nowYes, with one DELETENo, unless you add a list to check
Works across servicesOnly where the database reachesAnywhere that holds the key
Browser attaches itYes, automaticallyNo. Your code sends the header
Needs CSRF careYes, because the browser attaches itNo, for the same reason reversed
Size on the wireAbout 64 bytes200 bytes and up

Choose from the requirement, not from fashion.

  1. A browser application with one backend. Use a session cookie. You get logout, and the browser does the work.
  2. A mobile client, or a script, or a service that calls another service. Use a token. There is no cookie jar, and the caller may not reach your database.
  3. Both, which is the common answer. Issue a short token, 15 minutes or less, and keep a long refresh session in the database. The short life bounds the damage; the row gives you the withdrawal.

A short expiry is the only defence that a plain token has. That is why TOKEN_TTL_MINUTES defaults to 15 and SESSION_TTL_MINUTES defaults to a week.

Step 7 · Close the clock channel

Step 3 gave the same message for an unknown email and for a wrong password. The message is one channel. Now measure the other one. Two routes exist for this measurement, and both are wrong on purpose.

Python, seven requests for each cell, mean:

RouteUnknown emailKnown email, wrong password
/auth/login-leaky6.8 ms190.6 ms
/auth/login186.6 ms187.3 ms

TypeScript, the same measurement:

RouteUnknown emailKnown email, wrong password
/auth/login-leaky13.6 ms174.8 ms
/auth/login168.6 ms168.8 ms

The leaky route answers an unknown email 28 times faster. An attacker sends a list of ten thousand addresses, sorts by response time, and keeps the slow ones. Those are your users.

The fix is three lines. When the email does not exist, hash a dummy password anyway, then give the same answer.

Code/Lesson_8_code/security.py and main.py

DUMMY_HASH = hash_password("this password belongs to nobody")

def waste_time_like_a_real_login() -> None:
    verify_password("wrong", DUMMY_HASH)

# in the login route
if row is None:
    await run_in_threadpool(waste_time_like_a_real_login)
    raise HTTPException(status_code=401, detail="wrong email or password")

The measured gap falls to 0.7 ms in Python and 0.2 ms in TypeScript. Both sit inside the noise of the network.

Step 8 · The 250 ms that stops your whole server

bcrypt is slow on purpose. That is the feature. It is also a problem, because both of your servers run one thread for application code.

Lesson 5 measured a query. Lesson 6 measured a counter. Measure this one the same way. Send ten logins at the same time, and ask /healthz twenty times while they run. /healthz costs one SELECT 1.

$ python event_loop_block.py
/healthz with nothing else running : 3.5 ms

login route               logins total  /healthz p50  /healthz max
/auth/login-blocking           1752 ms        4.4 ms     1727.8 ms
/auth/login                     227 ms        3.9 ms       13.7 ms

$ npm run block
/healthz with nothing else running : 3.3 ms

login route               logins total  /healthz p50  /healthz max
/auth/login-blocking           1567 ms        3.2 ms     1192.8 ms
/auth/login                     488 ms        2.6 ms        5.7 ms

Read the last column. A health check that costs 3 ms took 1.7 seconds in Python and 1.2 seconds in TypeScript. Nothing was wrong with the health check. Ten password hashes held the thread, and every other request waited in line. A platform that probes the health path every five seconds marks that instance unhealthy and restarts it, exactly when your users try to sign in.

Read the second column as well. The blocking route also serialises the logins. One thread runs one hash at a time.

The fix has a different name in each language and the same shape.

LanguageWrongRightWhere the work goes
Python verify_password(...) in an async def await run_in_threadpool(verify_password, ...) Starlette's thread pool
TypeScript bcrypt.compareSync(...) await bcrypt.compare(...) The libuv thread pool
A rule you can carry to any language

Find every function that costs more than a few milliseconds of CPU and runs on the request path. Move each one off the event loop. Password hashing, image work, and PDF generation are the usual three.

Step 9 · Protect the routes

Both frameworks answer the same question — is this request signed in? — at a different place in the file.

Code/Lesson_8_code/main.py — FastAPI uses a dependency

async def current_user(
    session: str | None = Cookie(default=None, alias=SESSION_COOKIE),
    authorization: str | None = Header(default=None),
) -> User:
    # the cookie wins, then the bearer token, then 401
    ...

@app.post("/bookmarks", status_code=201)
async def create_bookmark(bookmark: BookmarkCreate, user: User = Depends(current_user)):
    ...

Code/js/Lesson_8_code/src/server.ts — Express uses middleware

async function requireUser(req: Request, res: Response, next: NextFunction) {
  // the cookie wins, then the bearer token, then 401
}

app.post('/bookmarks', requireUser, route(async (req, res) => {
  ...
}));

The dependency returns a value, and the handler receives it as an argument. The middleware attaches the value to the request and calls next(). Both stop the request with a 401 before the handler runs. Pick the seam that your framework gives you, and use only that one.

Authentication, then authorisation

One difference between the two stacks that is not about auth

Read the Python row and the TypeScript row for the same bookmark.

Python     {"id":200001,...,"visit_count":0,"user_id":1}
TypeScript {"id":"200002",...,"visit_count":"0","user_id":4}

The bookmarks.id column is a bigint. A JavaScript number holds 53 bits of integer, and a bigint holds 64, so node-postgres returns the value as a string. It protects precision. The users.id column is an integer, so it arrives as a number. psycopg returns both as Python integers, because Python has no such limit. Check the type at the edge of each service. Do not assume that two clients of one database agree.

Step 10 · What this lesson does not give you

Say these limits in an interview. They show that you know the shape of the subject.

  1. No rate limit. An attacker may try passwords as fast as your server answers. Add a limit for each IP address and for each account, and add a lock after a number of failures.
  2. No password reset. The reset flow is a second authentication system, and most breaches enter through it.
  3. No CSRF token. SameSite=Lax covers the common case. A form that posts across sites needs a token as well.
  4. No refresh tokens, no OAuth, no multi-factor. Each one is a lesson.
  5. No HTTPS on your laptop. The Secure flag is off in development and on everywhere else. Every rule in this lesson assumes TLS. Lesson 7 gave you that on the platform.

Practice

Do these in order. Steps 1 to 5 use Python. Steps 6 to 8 repeat the work in TypeScript, and they go faster.

  1. Run the three programs before you read their output again. python hash_speed.py, python forge_token.py, python security.py. Write down your own numbers. They differ from mine, and the ratios do not.
  2. Apply the migrations and register an account. python migrate.py, then uvicorn main:app --port 8008, then register with a capital letter in the email. Read the row with psql. Confirm that the email is lower case and that no column holds your password.
  3. Prove the logout difference yourself. Get a cookie and a token for the same account. Call /auth/logout. Call /auth/me with each credential. Explain the two status codes in one sentence each.
  4. Measure the timing leak. Send seven requests to /auth/login-leaky with an unknown email, then seven with a real one. Repeat against /auth/login. Then delete both login-leaky routes from your project.
  5. Measure the blocked event loop. Run python event_loop_block.py. Then delete both login-blocking routes.
  6. Bring up the TypeScript project. npm install, npm run migrate, npm start. The migration runner must print skip seven times, because the Python runner already applied them.
  7. Run the same requests against port 8009. Register, log in, create a bookmark, and try to delete somebody else's. Confirm the same five status codes: 201, 409, 401, 403, 204.
  8. Break the type check on purpose. Change req.user!.id to req.user!.email in the delete route. Run npm start and watch the server accept the file. Then run npm run typecheck and watch tsc report the error. Explain in one sentence why the running server did not care.
  9. Write it up. Add an "Authentication" section to Code/Lesson_7_code/README.md with three rows: the hash and its cost, the credential that you chose and why, and the blocked-event-loop measurement. That table is interview material.

Lesson 9 is testing and CI. Authentication is the right thing to test first, because the failures are quiet: a route that forgets Depends(current_user) looks fine in a browser and hands your data to anybody. A test that calls the route with no credential and expects a 401 catches that in one second, on every push.

Ask me things. Four questions are worth asking now. When does Argon2id beat bcrypt, and what parameters does it need? How do you revoke one JWT before it expires, and what does that cost? Where does a refresh token live in a browser, given that localStorage is readable by any script? And how do you test a route that needs a login, without a real password hash in every test?
