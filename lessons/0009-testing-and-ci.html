Testing and CI Python and TypeScript, one idea at a time.

You wrote an API. Now you prove that it works. A test is a program that calls your API and checks the answer. It runs every time you change the code. If the code breaks the contract, the test fails.

The whole lesson in one sentence

A test that cannot fail proves nothing. Test the contract, not the plumbing.

How the two languages sit together

The Python project is Code/Lesson_9_code/. The TypeScript project is Code/js/Lesson_9_code/. Both test the authentication system from Lesson 8. Both use a real PostgreSQL container. Both run in GitHub Actions.

Step 1 · The database must be real

Do not use a mock database. Do not use SQLite to test a PostgreSQL server. SQLite does not enforce the same rules. It ignores the time zone, and it allows concurrent writes in a different way. If you test with SQLite, your tests pass, but your server fails in production.

Use a real PostgreSQL container. Start it before the tests run. The docker-compose.test.yml file gives you an isolated database on port 5432.

docker-compose.test.yml

services:
  db-test:
    image: postgres:16-alpine
    environment:
      POSTGRES_USER: testuser
      POSTGRES_PASSWORD: testpassword
      POSTGRES_DB: testdb
    ports:
      - "5432:5432"

Step 2 · Test the contract, not the plumbing

A unit test calls a function. An integration test calls the API over HTTP. Write integration tests first. The client needs only the HTTP response.

When you test the HTTP response, you test the contract. If you change the database driver, the contract stays the same. The test still passes. If you use a mock database driver, the test breaks when you change the driver.

Step 3 · Python: pytest and httpx

Use pytest to run the tests. Use httpx to send requests to the FastAPI application. The conftest.py file holds the setup code. It connects to the test database and runs the migrations.

Code/Lesson_9_code/conftest.py

import os
import pytest
from fastapi.testclient import TestClient
import runpy

# Set test configuration before you import the app
os.environ["DATABASE_URL"] = "postgresql://testuser:testpassword@127.0.0.1:5432/testdb"
os.environ["APP_ENV"] = "development"

from config import settings
from main import app

@pytest.fixture(scope="session", autouse=True)
def setup_test_db():
    import psycopg
    with psycopg.connect(settings.dsn, autocommit=True) as conn:
        conn.execute("DROP SCHEMA public CASCADE")
        conn.execute("CREATE SCHEMA public")
    runpy.run_path("migrate.py")
    yield

@pytest.fixture
def client():
    with TestClient(app) as test_client:
        yield test_client

Now write the test. The test calls the API, reads the response, and uses assert to check the status code.

Code/Lesson_9_code/test_auth.py

def test_login_wrong_password(client: TestClient):
    res = client.post("/auth/login", json={
        "email": "test@example.com",
        "password": "wrong password"
    })
    assert res.status_code == 401
    assert res.json()["detail"] == "wrong email or password"

Step 4 · TypeScript: vitest and supertest

Use vitest to run the tests. Use supertest to send requests to the Express application. The setup file drops the schema and runs the migrations.

Code/js/Lesson_9_code/tests/setup.ts

import { beforeAll } from 'vitest';
import { Client } from 'pg';
import { config } from '../src/config.ts';

beforeAll(async () => {
  const client = new Client({ connectionString: config.databaseUrl });
  await client.connect();
  await client.query("DROP SCHEMA public CASCADE");
  await client.query("CREATE SCHEMA public");
  await client.end();

  await import('../src/migrate.ts');
});

The test sends the request and checks the response.

Code/js/Lesson_9_code/tests/auth.test.ts

import { test, expect } from 'vitest';
import request from 'supertest';
import { app } from '../src/server.js';

test('login with wrong password', async () => {
  const res = await request(app)
    .post('/auth/login')
    .send({ email: 'test@example.com', password: 'wrong password' });
  
  expect(res.status).toBe(401);
  expect(res.body.detail).toBe('wrong email or password');
});

Step 5 · The observable failure

A test proves nothing until you see it fail. Open Code/Lesson_9_code/main.py or Code/js/Lesson_9_code/src/server.ts. Find the login route. Change the status code for a wrong password from 401 to 200. Run the test suite.

$ pytest
FAILED test_auth.py::test_login_wrong_password - assert 200 == 401

$ npx vitest run
FAIL  tests/auth.test.ts > login with wrong password
AssertionError: expected 200 to be 401 // Object.is equality

The test failed. The contract broke, and the test caught it. Change the status code back to 401.

Step 6 · Continuous Integration

A test on your laptop does not protect the production server. You must run the tests in the cloud. A Continuous Integration (CI) service runs your tests on every push. If a test fails, the CI service rejects the code.

GitHub Actions uses a YAML file. Put the file in .github/workflows/ci.yml. The file tells GitHub to start a PostgreSQL service, install the dependencies, and run the tests.

Code/Lesson_9_code/.github/workflows/ci.yml

name: CI

on:
  push:
    branches: [ "main" ]

jobs:
  test:
    runs-on: ubuntu-latest
    services:
      postgres:
        image: postgres:16-alpine
        env:
          POSTGRES_USER: testuser
          POSTGRES_PASSWORD: testpassword
          POSTGRES_DB: testdb
        ports:
          - 5432:5432

    env:
      DATABASE_URL: postgresql://testuser:testpassword@127.0.0.1:5432/testdb
      APP_ENV: test

    steps:
    - uses: actions/checkout@v4
    - name: Set up Python
      uses: actions/setup-python@v5
      with:
        python-version: "3.12"
    - name: Install dependencies
      run: pip install -r requirements.txt
    - name: Run tests
      run: pytest

The TypeScript workflow uses actions/setup-node@v4 and npm run test instead.

Never use a mock database in CI

The CI runner is a Linux machine. It can pull the PostgreSQL image. It can run the real database. There is no reason to test against SQLite in the cloud.

Practice

  1. Start the test database. Run docker compose -f docker-compose.test.yml up -d in the Lesson 9 directory.
  2. Run the tests. Run pytest or npm run test. Watch the tests pass.
  3. Break the application. Find the route that creates a bookmark. Delete the code that checks if the user signed in.
  4. Run the tests again. Watch the authorization test fail. The test expected a 401, but the API returned a 201.
  5. Fix the application. Put the check back.
