Caching Python and TypeScript, one idea at a time.

A cache is a copy. You keep the copy somewhere faster than the place that computed the answer, so the next request skips the work. A copy can be wrong. The source changes, and the copy does not know.

The whole lesson in one sentence

A cache is a copy that can be wrong. Name the moment it goes stale before you add it.

How the two languages sit together

The Python project is Code/Lesson_10_code/. The TypeScript project is Code/js/Lesson_10_code/. Both extend the bookmarks API from Lesson 9 with two caches: one in the HTTP layer, one in Redis.

Step 1 · The cheapest cache costs nothing to run

Before you add Redis, add the cache that already exists. A browser and a proxy can each keep a copy of a response for you, at no cost, if you tell them how long the copy stays good. Two headers do this: Cache-Control and ETag.

Cache-Control: max-age=30 tells the client to reuse its copy for 30 seconds without a new request to the server. After 30 seconds, the client asks again, but it does not have to download the whole answer. It sends the ETag it stored, in a header named If-None-Match. If the server computes the same ETag, the answer has not changed, and it sends back 304 Not Modified with no body.

Code/Lesson_10_code/main.py

@app.get("/bookmarks/{bookmark_id}")
async def get_bookmark(bookmark_id: int, request: Request, response: Response):
    async with app.state.pool.connection() as conn:
        cur = await conn.cursor(row_factory=dict_row).execute(
            "SELECT id, url, title, visit_count, user_id FROM bookmarks WHERE id = %s",
            (bookmark_id,),
        )
        row = await cur.fetchone()
    if row is None:
        raise HTTPException(status_code=404, detail="bookmark not found")

    etag = hashlib.sha256(json.dumps(row, sort_keys=True).encode()).hexdigest()[:16]
    response.headers["Cache-Control"] = "max-age=30"
    response.headers["ETag"] = etag

    if request.headers.get("if-none-match") == etag:
        return Response(status_code=304, headers=dict(response.headers))
    return row

The ETag is a hash of the fields the client can see. Two requests for the same row get the same hash. A write that changes title or visit_count changes the hash on the next read, so the client downloads the new answer.

Run it, and watch the second request come back empty.

$ curl -i localhost:8000/bookmarks/500
HTTP/1.1 200 OK
cache-control: max-age=30
etag: bc910b5231e857b6
content-length: 110

{"id":500,"url":"https://example.com/article/500","title":"Article number 500","visit_count":0,"user_id":null}

$ curl -i -H "If-None-Match: bc910b5231e857b6" localhost:8000/bookmarks/500
HTTP/1.1 304 Not Modified
cache-control: max-age=30
etag: bc910b5231e857b6

110 bytes became zero. No query ran for the second request that mattered: the row lookup still happens, because this server computes the ETag from the row, but the client never receives a body it already has. A proxy in front of the server can skip the lookup entirely, once it has seen the ETag.

Step 2 · TypeScript: the same ETag

Code/js/Lesson_10_code/src/server.ts

app.get('/bookmarks/:id', route(async (req, res) => {
  const id = Number(req.params.id);
  const { rows } = await pool.query(
    'SELECT id, url, title, visit_count, user_id FROM bookmarks WHERE id = $1',
    [id],
  );
  const row = rows[0];
  if (!row) {
    res.status(404).json({ detail: 'bookmark not found' });
    return;
  }

  const etag = createHash('sha256').update(JSON.stringify(row)).digest('hex').slice(0, 16);
  res.set('Cache-Control', 'max-age=30');
  res.set('ETag', etag);

  if (req.headers['if-none-match'] === etag) {
    res.status(304).end();
    return;
  }
  res.json(row);
}));
Register the specific route first

Both frameworks match routes in the order you add them. /bookmarks/search must come before /bookmarks/{bookmark_id}, or the string "search" reaches the handler that expects an integer id.

Step 3 · Redis, for a copy the database does not need to remake

An ETag still asks the server a question on every request. Redis answers without asking the server at all: the process that holds the cached value is not the process that runs the query. Add it in front of the search endpoint, which Lesson 5 already gave a database index.

Code/Lesson_10_code/main.py

@app.get("/bookmarks/search")
async def search_bookmarks(q: str, skip: int = 0, limit: int = Query(default=10, le=100)):
    cache_key = f"search:{q}:{skip}:{limit}"
    cached = await app.state.redis.get(cache_key)
    if cached is not None:
        return {"source": "cache", "results": json.loads(cached)}

    async with app.state.pool.connection() as conn:
        cur = await conn.cursor(row_factory=dict_row).execute(
            SEARCH_SQL, (f"{q}%", limit, skip)
        )
        rows = await cur.fetchall()

    await app.state.redis.set(
        cache_key, json.dumps(rows, default=str), ex=SEARCH_CACHE_TTL_SECONDS
    )
    return {"source": "database", "results": rows}

Every response says where it came from: "database" or "cache". Say this in your own responses too, while you learn the mechanism. Remove it once you trust the cache.

Step 4 · Measure the hit and the miss

Do not guess whether a cache is worth the complexity. Measure it. Delete the cache key, request the search, then request it again five times without deleting the key.

Code/Lesson_10_code/cache_bench.py

$ python cache_bench.py
--- 1. miss against hit -----------------------------------
miss (database each time): [5.613, 3.603, 2.918, 1.908, 1.612]
hit  (Redis each time):    [0.872, 0.818, 1.120, 1.969, 1.473]
average miss: 3.131 ms, average hit: 1.251 ms, 2.5x faster

The database was already fast: the index from Lesson 5 answers this query in about 3 ms end to end, over a local TCP connection. Redis is still 2.5 times faster. A key lookup in memory skips SQL parsing and a B-tree read, even on a small tree. The TypeScript run shows the same shape:

Code/js/Lesson_10_code/src/cacheBench.ts

$ node src/cacheBench.ts
--- 1. miss against hit -----------------------------------
miss (database each time): [51.213, 5.803, 6.709, 5.977, 6.775]
hit  (Redis each time):    [3.568, 3.185, 3.087, 3.321, 3.341]
average miss: 15.296 ms, average hit: 3.301 ms, 4.6x faster

The first Node.js miss cost 51.2 ms, far more than the rest. The pool opened its first connection to PostgreSQL inside that request; the Python process had already opened its connections when uvicorn started, in the code from Lesson 7. Drop that one outlier and the remaining four average 6.3 ms — the same order of magnitude as Python, and still slower than every Redis hit.

A cache is not a fix for a slow query

This query did not need Redis to be fast; migration 0003 already made it fast. Redis removes a network round trip and a small amount of CPU work for a query the same client repeats. Choose a database index first. Choose a cache when the same expensive read happens again and again before the underlying row changes.

Step 5 · The observable failure: a stale read

A cache with a TTL can answer with an old copy. Insert a row directly with SQL, bypassing the API entirely, and search for it while the cache entry from an earlier search is still inside its 30 second TTL.

$ python cache_bench.py
--- 2. the stale read ---------------------------------------
before insert: {'source': 'database', 'results': []}
inserted a matching row directly in PostgreSQL, bypassing the API
right after insert (within the 30s TTL): {'source': 'cache', 'results': []}
waiting 31s for the cache entry to expire ...
after the TTL: {'source': 'database', 'results': [{'id': 200010, 'url': 'https://example.com/cache-demo', 'title': 'Cache demo row'}]}

The row exists in PostgreSQL from the moment the INSERT commits. The search endpoint denies that it exists for up to 30 more seconds, because it never asked the database again. No error appears anywhere. The response is 200, and the answer is wrong.

A TTL is a choice, not a bug

Two ways exist to keep a cache honest: delete the entry on every write that could affect it, or give every entry a short TTL and accept a window of staleness. This lesson uses a TTL, because it needs no write path to know which cache keys its change touches. Choose the TTL from how wrong an answer your feature can tolerate, and for how long.

Practice

  1. Start Redis. Run docker run -d --name redis-bookmarks -p 6379:6379 redis:7-alpine.
  2. Start the API. Run uvicorn main:app --port 8000 or npm start.
  3. Request the same bookmark twice. Copy the ETag from the first response into If-None-Match on the second. Confirm the 304.
  4. Run the bench program. Run python cache_bench.py or node src/cacheBench.ts. Read your own numbers, not the ones printed here.
  5. Shorten the TTL. Change SEARCH_CACHE_TTL_SECONDS to 5. Run the stale read demonstration again and confirm the wait is shorter.
