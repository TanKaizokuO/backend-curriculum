Observability Python and TypeScript, one idea at a time.

You cannot debug what you cannot see. A print statement answers one question: did this line run. It does not answer how often, how slow, or which request. This lesson builds the three tools that do: a log line, a metric, and a trace.

The whole lesson in one sentence

You cannot debug what you cannot see. A log line, a metric, and a trace answer different questions.

How the two languages sit together

The Python project is Code/Lesson_11_code/. The TypeScript project is Code/js/Lesson_11_code/. Both extend the bookmarks API from Lesson 10. observability.py and observability.ts hold the new wiring; every route file imports it and calls it.

Step 1 · The observable failure: five requests, one line

Start the Lesson 10 API, unchanged. Send five requests for the same search, at the same time, from five separate terminals. Read the server's own log.

INFO:     127.0.0.1:45138 - "GET /bookmarks/search?q=Observability+opening+demo HTTP/1.1" 200 OK
INFO:     127.0.0.1:45148 - "GET /bookmarks/search?q=Observability+opening+demo HTTP/1.1" 200 OK

INFO:     127.0.0.1:45176 - "GET /bookmarks/search?q=Observability+opening+demo HTTP/1.1" 200 OK

Five lines. Every line is the same text, apart from a client port number nobody asked for. Three questions have no answer here:

  • How long did each request take? The log names no duration.
  • Which of the five requests, if any, hit the database? The log names no cache result.
  • Which client received which response? The port number is not a request id. It does not appear in the response, so a caller who reports "my search was slow" cannot point back to one of these five lines.

The rest of this lesson answers all three questions, for every request, from now on.

Step 2 · A log line answers "what happened, for this one request"

A structured log line is one JSON object per request, not a sentence. A JSON line is a line a program can parse; a sentence built with an f-string is a line only a human can parse, and only by reading it. Give every request an id at the top, and read that id back at the bottom.

Code/Lesson_11_code/observability.py

import contextvars

request_id_var: contextvars.ContextVar[str] = contextvars.ContextVar(
    "request_id", default="-"
)


def new_request_id() -> str:
    return uuid.uuid4().hex[:16]


def log_event(**fields) -> None:
    # One JSON line. `fields` is the whole message — no free text to grep by luck.
    record = {"ts": round(time.time(), 3), "request_id": request_id_var.get(), **fields}
    logger.info(json.dumps(record, default=str))

contextvars.ContextVar is Python's answer to a problem `async def` creates: many requests run inside the same process, interleaved at every await, so a plain module-level variable would leak one request's id into another's log line. A context variable holds one value per running task, not one value per process.

A middleware sets the id once, at the top of every request, and reads it back at the bottom to write the log line.

Code/Lesson_11_code/main.py

@app.middleware("http")
async def observe_request(request: Request, call_next):
    token = request_id_var.set(new_request_id())
    start = time.perf_counter()
    response = await call_next(request)
    duration_s = time.perf_counter() - start
    route = request.scope.get("route")
    route_path = route.path if route else request.url.path

    response.headers["X-Request-Id"] = request_id_var.get()
    log_event(
        level="info",
        method=request.method,
        path=route_path,
        status=response.status_code,
        duration_ms=round(duration_s * 1000, 2),
    )
    request_id_var.reset(token)
    return response

One question from Step 1 is already answered: this was the request that reached the database. The other four found an answer already in the cache, written by whichever request finished first.

Read the route after routing, not before

request.scope["route"] exists only once Starlette has matched a route, so the middleware reads it after call_next, not before. Group /bookmarks/17 and /bookmarks/42 under the route template /bookmarks/{bookmark_id}, not under each id. The next section explains why this choice matters for a metric, not only for a log line.

Step 3 · TypeScript: the same request id

Python threads the id through contextvars. Node has no built-in equivalent to Python's async def task, so it uses AsyncLocalStorage, which solves the same problem: one stored value per chain of await calls, not one per process.

Code/js/Lesson_11_code/src/observability.ts

import { AsyncLocalStorage } from 'node:async_hooks';

export const requestIdStorage = new AsyncLocalStorage<string>();

export function logEvent(fields: Record<string, unknown>): void {
  const record = {
    ts: Math.round(Date.now() / 10) / 100,
    request_id: requestIdStorage.getStore() ?? '-',
    ...fields,
  };
  process.stdout.write(`${JSON.stringify(record)}\n`);
}

Code/js/Lesson_11_code/src/server.ts

app.use((req: Request, res: Response, next: NextFunction) => {
  const requestId = randomUUID().replaceAll('-', '').slice(0, 16);
  requestIdStorage.run(requestId, () => {
    const start = performance.now();
    res.setHeader('X-Request-Id', requestId);
    res.on('finish', () => {
      const durationS = (performance.now() - start) / 1000;
      const routePath = req.route ? `${req.baseUrl}${req.route.path}` : req.path;
      requestCount.labels(req.method, routePath, String(res.statusCode)).inc();
      requestLatency.labels(req.method, routePath).observe(durationS);
      logEvent({
        level: 'info',
        method: req.method,
        path: routePath,
        status: res.statusCode,
        duration_ms: Math.round(durationS * 1000 * 100) / 100,
      });
    });
    next();
  });
});

Same shape as the Python version, in Node's vocabulary: req.route only exists once Express has matched a route, so res.on('finish', ...) reads it after the handler ran, not before.

Step 4 · A metric answers "how often, and how slow"

A log line describes one request. A metric describes every request, without keeping one line per request forever. A counter only goes up; a histogram sorts every observed duration into buckets, so you can ask "how many requests took under 25 ms" without reading a single log line.

Code/Lesson_11_code/observability.py

from prometheus_client import CONTENT_TYPE_LATEST, Counter, Histogram, generate_latest

REQUEST_COUNT = Counter(
    "http_requests_total",
    "HTTP requests, by method, route, and status code.",
    ["method", "route", "status"],
)

REQUEST_LATENCY = Histogram(
    "http_request_duration_seconds",
    "HTTP request duration in seconds, by method and route.",
    ["method", "route"],
)

CACHE_RESULT = Counter(
    "bookmark_search_cache_total",
    "Search cache lookups, by result.",
    ["result"],  # hit | miss
)

Code/Lesson_11_code/main.py

@app.get("/metrics")
async def metrics():
    return Response(content=generate_latest(), media_type=CONTENT_TYPE_LATEST)

Every route template gets its own label value, never a raw id. This is why Step 2's warning matters: a metric with one label value per bookmark id would grow one time series for every row ever requested, and never stop growing. A route template is bounded — one series per route, for the life of the process.

Step 5 · TypeScript: the same metrics

Code/js/Lesson_11_code/src/observability.ts

import { Counter, Histogram, Registry } from 'prom-client';

export const registry = new Registry();

export const requestCount = new Counter({
  name: 'http_requests_total',
  help: 'HTTP requests, by method, route, and status code.',
  labelNames: ['method', 'route', 'status'] as const,
  registers: [registry],
});

export const requestLatency = new Histogram({
  name: 'http_request_duration_seconds',
  help: 'HTTP request duration in seconds, by method and route.',
  labelNames: ['method', 'route'] as const,
  registers: [registry],
});

Code/js/Lesson_11_code/src/server.ts

app.get('/metrics', (_req: Request, res: Response) => {
  res.set('Content-Type', registry.contentType);
  registry.metrics().then((body) => res.send(body));
});

prom-client is the same shape as prometheus_client: a Counter and a Histogram, registered once, read through one endpoint. Both libraries also add process metrics — memory, open file descriptors, garbage-collector pauses — with no extra code; they appear in the same curl output, unlabelled by route.

Step 6 · A trace answers "where did the time go, inside this one request"

A log line and a metric both treat one request as one event. A search request in this API does two things in sequence: it asks Redis, and, on a miss, it asks PostgreSQL. Neither the log line nor the metric says which part took the time. A trace does: one span for the whole request, a child span for the database call.

Code/Lesson_11_code/observability.py

from opentelemetry import trace
from opentelemetry.sdk.resources import Resource
from opentelemetry.sdk.trace import TracerProvider
from opentelemetry.sdk.trace.export import ConsoleSpanExporter, SimpleSpanProcessor

provider = TracerProvider(resource=Resource.create({"service.name": "bookmarks-api"}))
provider.add_span_processor(SimpleSpanProcessor(ConsoleSpanExporter()))
trace.set_tracer_provider(provider)
tracer = trace.get_tracer("bookmarks")

SimpleSpanProcessor prints a span the instant it ends, to the terminal running uvicorn. A production deploy swaps in an OTLP exporter that ships spans to Jaeger or a vendor, on a batch timer instead of one at a time — everything else in this file stays the same. Console output keeps this lesson runnable with no extra container.

Code/Lesson_11_code/main.py

with tracer.start_as_current_span("pg_query") as span:
    span.set_attribute("db.system", "postgresql")
    span.set_attribute("db.statement", SEARCH_SQL.strip())
    async with app.state.pool.connection() as conn:
        cur = await conn.cursor(row_factory=dict_row).execute(
            SEARCH_SQL, (f"{q}%", limit, skip)
        )
        rows = await cur.fetchall()
    span.set_attribute("db.rows_returned", len(rows))

This span only opens on a cache miss — a cache hit never runs the block above. Request a fresh search once and read the two spans it printed, oldest first.

Both spans share one trace_id. pg_query's parent_id is http_request's own span_id — that one field is what makes it a child, not a second, unrelated event. Read a trace outside in: the outer span is the whole request; the inner span is the part of it that talked to PostgreSQL. Whatever time the outer span reports and the inner span does not account for happened somewhere else — in this handler's own Python, or waiting on Redis.

Step 7 · TypeScript: the same trace

Code/js/Lesson_11_code/src/observability.ts

import { trace } from '@opentelemetry/api';
import { Resource } from '@opentelemetry/resources';
import { NodeTracerProvider } from '@opentelemetry/sdk-trace-node';
import { ConsoleSpanExporter, SimpleSpanProcessor } from '@opentelemetry/sdk-trace-base';

const provider = new NodeTracerProvider({
  resource: new Resource({ 'service.name': 'bookmarks-api-ts' }),
});
provider.addSpanProcessor(new SimpleSpanProcessor(new ConsoleSpanExporter()));
provider.register();

export const tracer = trace.getTracer('bookmarks');
Starting a span does not activate it

The first version of this middleware called tracer.startSpan('http_request') and never entered it into the active context. Every child span opened inside the request handler then started its own, unrelated trace — same symptom as Python without ContextVar: the wiring runs, and the nesting silently never happens. The fix is context.with(trace.setSpan(context.active(), span), () => next()): it makes span the active span for everything next() goes on to run, so a later tracer.startActiveSpan('pg_query', ...) finds it and attaches as a child. Read a trace you did not check for nesting with suspicion — a flat trace is not evidence that nothing has children, only that nothing was told to.

Step 8 · The observable payoff: diagnose a stale read with no source open

Lesson 10 showed a stale read by printing what each request returned. This time, diagnose the same failure from the log line, the metric, and the trace alone — the three tools this lesson just built, read from a second terminal, without opening main.py.

Now read the server's own terminal for the same five steps, and only that.

{"request_id": "ea07ea66749a43b8", "event": "search_cache", "result": "miss", ...}   # pg_query span opened
{"request_id": "cbf7eaf3b1e049fb", "event": "search_cache", "result": "hit", ...}    # no pg_query span
{"request_id": "5349a3c23fd146f5", "event": "search_cache", "result": "hit", ...}    # no pg_query span
{"request_id": "0f88a0900e294a87", "event": "search_cache", "result": "miss", ...}   # pg_query span opened, db.rows_returned: 1

Line by line, without reading main.py once:

  1. Request ea07ea66... misses the cache and opens a pg_query span. The database has not seen the row yet, so it returns nothing.
  2. Request cbf7eaf3... hits the cache. No pg_query span opens — this request never asked PostgreSQL anything.
  3. Between steps 2 and 4, a row is inserted directly with SQL. No request logs this; it did not go through the API.
  4. Request 5349a3c2... hits the cache again, still inside the 30 s TTL. No pg_query span. Three independent signals now agree that this response never touched the database: the log line says hit, bookmark_search_cache_total did not move for the miss label, and the trace has no pg_query span. Yet the row from step 3 exists in PostgreSQL right now.
  5. Request 0f88a090..., after the TTL, misses the cache, opens a pg_query span, and reports db.rows_returned: 1. The row was there the whole time; the cache was the only thing that did not know.

This is the same conclusion Lesson 10 reached by printing response bodies. Here it comes from three tools built for exactly this question, against a server whose source was never opened — the position you are actually in against a deployed service.

What this lesson does not cover

No SaaS observability vendor, no long retention policy, no alerting rule. Those are real decisions a team makes once it already has the three primitives this lesson built. Learn the primitives first; a vendor dashboard is a view onto the same log lines, metrics, and spans, not a different kind of tool.

Practice

  1. Start the dependencies. pg-bookmarks on port 55432, and docker run -d --name redis-bookmarks -p 6379:6379 redis:7-alpine.
  2. Start the API. Run uvicorn main:app --port 8000 or node src/server.ts.
  3. Fire the five-request demo yourself. Use a query you have not searched before, so the first request is a genuine miss. Confirm one X-Request-Id matches one slow log line.
  4. Read /metrics raw. Run curl localhost:8000/metrics before you ever open Grafana or Prometheus itself. Find your own five requests in the histogram buckets.
  5. Run the diagnosis program. Run python diagnose.py or node src/diagnose.ts. Watch the server's terminal, not this program's own output, while it runs.
  6. Break the nesting on purpose. In the TypeScript project, remove the context.with(...) wrapper around next() and replace it with a plain call to next(). Request a fresh search and confirm the pg_query and http_request spans now print with two different traceId values. Put the wrapper back.
  7. Stop Redis. Run docker stop redis-bookmarks, then request /bookmarks/search again. Read the error in the log line, the status code in the metric, and the span's status. Start Redis again before you continue.
  8. Widen the request id. Add request_id as a label on bookmark_search_cache_total and explain, in one sentence, why this change is a mistake in production even though it compiles and runs.
