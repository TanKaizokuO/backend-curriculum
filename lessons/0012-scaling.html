Scaling Python and TypeScript, one idea at a time.

When one process cannot answer fast enough, you start a second process and split the traffic. The moment you do, every assumption about local state breaks. Your memory is no longer the truth.

The whole lesson in one sentence

Add a second instance and every assumption about local state breaks.

How the two languages sit together

The Python project is Code/Lesson_12_code/. The TypeScript project is Code/js/Lesson_12_code/. Both run two API instances behind a round-robin proxy to prove what breaks.

Step 1 · The load balancer

Lesson 2 built a routing table by hand to show how a framework works. This is the same mechanism for a load balancer. Before you configure a real one like Nginx or Envoy, look at the raw mechanism. A reverse proxy accepts a connection from the client, picks a backend from a list, opens a connection to that backend, and copies bytes between the two.

Code/Lesson_12_code/round_robin_proxy.py

async def handle(client_reader, client_writer):
    host, port = next(_next_backend)
    backend_reader, backend_writer = await asyncio.open_connection(host, port)
    await asyncio.gather(
        pump(client_reader, backend_writer),
        pump(backend_reader, client_writer),
    )

This proxy picks the next backend in a cycle for each new connection. It does no TLS termination, no health checks, and no retries — Lesson 15 adds those. This minimal proxy is enough to prove the failure mode of local state.

Step 2 · The observable failure: the local rate limit

To stop a brute-force attack against passwords, you limit how many times an IP address can attempt a login. The simplest way is a dictionary in memory that counts attempts.

Code/Lesson_12_code/rate_limit.py

_local_attempts: dict[str, list[float]] = {}

def local_limiter(client_ip: str) -> bool:
    """Return True if the request may proceed."""
    now = time.monotonic()
    window_start = now - LOGIN_ATTEMPT_WINDOW_SECONDS
    attempts = [t for t in _local_attempts.get(client_ip, []) if t > window_start]
    attempts.append(now)
    _local_attempts[client_ip] = attempts
    return len(attempts) <= LOGIN_ATTEMPT_LIMIT

This looks correct, and against one instance, it is. Run the bench script against port 8020 directly. It asks for 14 logins, and the sixth attempt hits the limit and fails.

$ python bench_rate_limit.py --base-url http://127.0.0.1:8020
attempt  1 -> 200
attempt  2 -> 200
attempt  3 -> 200
attempt  4 -> 200
attempt  5 -> 200
attempt  6 -> 429
...
first 429 at attempt 6

Now start a second API instance on port 8021 and point the bench script at the proxy on port 8022. The proxy sends the first request to 8020, the second to 8021, and so on. The limit is 5 attempts, but the script reaches attempt 10 before it fails.

$ python bench_rate_limit.py --base-url http://127.0.0.1:8022
attempt  1 -> 200
attempt  2 -> 200
...
attempt  9 -> 200
attempt 10 -> 200
attempt 11 -> 429

first 429 at attempt 11

The limit doubled silently. The _local_attempts dictionary lives inside the process memory. The instance on 8020 counts 5 attempts, and the instance on 8021 counts a completely separate 5 attempts. N instances multiply your limit by N.

Step 3 · The fix: shared state

If you want a limit of 5, every instance must read from the same counter. Lesson 10 added Redis to cache search results. Redis also supports atomic counters.

Code/Lesson_12_code/rate_limit.py

async def redis_limiter(redis: Redis, client_ip: str) -> bool:
    key = f"login_attempts:{client_ip}"
    count = await redis.incr(key)
    if count == 1:
        await redis.expire(key, LOGIN_ATTEMPT_WINDOW_SECONDS)
    return count <= LOGIN_ATTEMPT_LIMIT

INCR on a missing key creates it at 1 and increments it atomically. Two instances that execute this at the exact same millisecond get a distinct, correct next count — one gets 5, the other gets 6. Switch both instances to the redis backend and the proxy bench shows the correct failure at attempt 6.

$ RATE_LIMIT_BACKEND=redis uvicorn main:app --port 8020
$ RATE_LIMIT_BACKEND=redis uvicorn main:app --port 8021
$ python bench_rate_limit.py --flush --base-url http://127.0.0.1:8022
...
attempt  5 -> 200
attempt  6 -> 429
---headers on the 6th---
HTTP/1.1 429 Too Many Requests
retry-after: 60

{"detail":"too many login attempts, try again later"}

Step 4 · TypeScript: the same fix

The TypeScript twin behaves identically. A local Map breaks across multiple instances. The Redis counter fixes it. The only difference is the interface type to satisfy the compiler without pulling in every bundled Redis module.

Code/js/Lesson_12_code/src/rateLimit.ts

interface AtomicCounterStore {
  incr(key: string): Promise<number>;
  expire(key: string, seconds: number): Promise<boolean>;
}

export async function redisLimiter(redis: AtomicCounterStore, clientIp: string): Promise<boolean> {
  const key = `login_attempts:${clientIp}`;
  const count = await redis.incr(key);
  if (count === 1) {
    await redis.expire(key, LOGIN_ATTEMPT_WINDOW_SECONDS);
  }
  return count <= LOGIN_ATTEMPT_LIMIT;
}

Step 5 · Connection limits and backpressure

The database has a hard limit on how many clients it accepts at once, named max_connections. Two instances that each size their own connection pool without regard to that ceiling can ask for more connections than the database will ever hand out.

The Python psycopg_pool waits in a queue when the pool is empty. If the queue timeout is long (30 seconds), an oversubscribed database causes requests to queue until they eventually succeed, but very slowly. Under a spike of 100 requests to a database with 15 available connections, the bench program shows the result:

=== BROKEN (max_size=10 each, timeout=30s) — spike load ===
100 requests across 2 instances
status counts: {'200': 100}
wall time: 10.12s
latency  : min 1.24s  p50 6.08s  p90 8.92s  max 10.12s

Every request succeeded, but the median request took 6 seconds. This is slow failure, which looks like success to the load balancer but looks broken to the user.

The fix is backpressure: a pool sized strictly smaller than the database limit, and a short timeout (3 seconds). Requests that cannot get a connection fail fast.

=== FIXED (max_size=7 each, timeout=3s) — spike load ===
100 requests across 2 instances
status counts: {'200': 22, '503': 78}
wall time: 4.10s
latency  : min 1.25s  p50 3.07s  p90 3.08s  max 4.09s

Most requests failed, but they failed in 3 seconds instead of hanging for 10, and they returned a 503 Service Unavailable with a Retry-After header. This is honest backpressure.

Node.js pools fail differently

The pg.Pool in Node.js has no built-in queue timeout. It fails immediately when the database refuses the connection. In the TypeScript project, the broken config failed 25% of requests instantly with a raw Postgres 53300 error, rather than hanging. The TypeScript code wraps the pool in a custom timeout to match Python's queue-wait behavior, but the raw connection refusal still happens first when oversubscribed.

Step 6 · Read replicas and replication lag

Scaling reads means adding a second database that receives a stream of changes from the primary database. The application sends writes (INSERT, UPDATE) to the primary, and reads (SELECT) to the replica.

But the replica is a copy, and a copy can fall behind. If you write to the primary and immediately read from the replica, you may get a stale answer. The bench program pauses WAL replay on the replica to simulate this.

$ python replica_lag_bench.py
--- 2. a paused replica is a stale replica ----------------------
paused WAL replay on the replica
inserted bookmark 18 on the primary
replica sees it while paused: False  <- stale read
resumed WAL replay
replica sees it now: True  <- caught up

Do not write code that assumes replication is instant. If a user edits their own profile, the redirect must read from the primary, or they will see their old profile and think the save failed.
