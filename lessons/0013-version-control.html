Version control A graph, not a list.

Git does not store a list of changes. It stores a full snapshot at every commit, and each commit points back to the commit before it. History is a graph you can walk, not a list you scroll.

The whole lesson in one sentence

A commit is a snapshot with a parent. History is a graph, not a list.

How the two languages sit together

Git has no per-language mechanism. The demo repository is Code/Lesson_13_code/, and it rebuilds itself on every run of demo.sh. The TypeScript twin, Code/js/Lesson_13_code/, repeats only the merge conflict. The failure does not change with the language, so the rest need not repeat.

Step 1 · An object, by hand

Lesson 2 built a router by hand before FastAPI hid it behind a decorator. Do the same here. git commit is three lower-level commands wearing one name. Run them one at a time, in an empty repository.

Code/Lesson_13_code/demo.sh

$ echo "hello backend" > file.txt
$ git hash-object -w file.txt
09537d4111e1e6b0250401496c7fd93ca8f575ee

git hash-object -w takes the content of file.txt, hashes it, and writes the result into .git/objects under that hash. This is a blob: file content, with no filename and no path attached to it.

$ git cat-file -p 09537d4111e1e6b0250401496c7fd93ca8f575ee
hello backend
$ git update-index --add --cacheinfo 100644 09537d4111e1e6b0250401496c7fd93ca8f575ee file.txt
$ git write-tree
de5083fe1c0eeeeac0fc1779f626346b35561a71
$ git cat-file -p de5083fe1c0eeeeac0fc1779f626346b35561a71
100644 blob 09537d4111e1e6b0250401496c7fd93ca8f575ee	file.txt

git update-index tells the staging area — Git's name for it is the index — that file.txt now points at that blob. git write-tree reads the index and writes a tree object. Each line names one blob, or one nested tree for a directory, and one filename. A tree is a frozen directory listing.

$ git commit-tree de5083fe1c0eeeeac0fc1779f626346b35561a71 -m "first commit"
c98ebfe374164c272c801b9ee85ef1823a0e49ac
$ git cat-file -p c98ebfe374164c272c801b9ee85ef1823a0e49ac
tree de5083fe1c0eeeeac0fc1779f626346b35561a71
author dev <dev@example.com> 1787695703 +0530
committer dev <dev@example.com> 1787695703 +0530

first commit

A commit object names one tree, an author, a committer, and a message. Every commit after the first also names one or more parent lines. This first commit has no parent line; the next commit points at this one.

Same content, same hash

Every object's name is the SHA-1 hash of its own content. Commit two files with identical content and Git stores one blob, referenced twice. Edit a file back to text it held three commits ago and Git reuses the old blob rather than storing the bytes again.

Step 2 · A branch is a pointer, not a copy

A commit is immutable once written. A branch is not a commit — it is a 41-byte text file that names one.

$ git update-ref refs/heads/main c98ebfe374164c272c801b9ee85ef1823a0e49ac
$ cat .git/refs/heads/main
c98ebfe374164c272c801b9ee85ef1823a0e49ac
$ cat .git/HEAD
ref: refs/heads/main

refs/heads/main holds one commit hash: the tip of the branch. HEAD holds one line that names the current branch. A new commit moves refs/heads/main to point at it; git checkout -b writes one new file of this shape. Neither operation copies the project, so branching costs the same whether the repository holds ten files or ten million.

Step 3 · The observable failure: two branches edit the same handler

Two developers each start from the same commit. Alice adds a cache read to get_bookmark. Bob, on his own branch, adds a log line to the same function.

$ git log --all --oneline --graph
* 2eef24b cache get_bookmark reads
| * b522325 log get_bookmark reads
|/
* 0f7613d add get_bookmark handler
* c98ebfe first commit

Neither branch knows the other exists. Bob merges his branch into Alice's.

$ git merge bob-logging -m "merge bob-logging into alice-caching"
Auto-merging handler.py
CONFLICT (content): Merge conflict in handler.py
Automatic merge failed; fix conflicts and then commit the result.

Git merges a file line by line. Both edits landed on the same two lines of the same function, so Git cannot pick one side without asking. It writes both sides into the file, marked, and stops.

handler.py — during the conflict

def get_bookmark(bookmark_id: int):
<<<<<<< HEAD
    cached = cache.get(f"bookmark:{bookmark_id}")
    if cached is not None:
        return cached
=======
    log.info("fetching bookmark", bookmark_id=bookmark_id)
>>>>>>> bob-logging
    row = db.execute(
        "SELECT id, url, title FROM bookmarks WHERE id = %s",
        (bookmark_id,),
    )
    if row is None:
        raise HTTPException(status_code=404)
    cache.set(f"bookmark:{bookmark_id}", row, ttl=30)
    return row

The text between <<<<<<< HEAD and ======= is Alice's line. The text between ======= and >>>>>>> bob-logging is Bob's line. Git does not choose. A person edits the file, keeps both changes in the right order, deletes the three marker lines, and stages the result.

Step 4 · Merge: both parents survive

$ git add handler.py
$ git commit -m "merge bob-logging into alice-caching"
$ git log --oneline --graph
*   ce43e8f merge bob-logging into alice-caching
|\
| * b522325 log get_bookmark reads
* | 2eef24b cache get_bookmark reads
|/
* 0f7613d add get_bookmark handler
* c98ebfe first commit

The new commit's own object shows the shape of a merge: two parent lines, not one.

$ git cat-file -p HEAD
tree 440342f8e7e723e94769963fc927795eccf6fe34
parent 2eef24b9164e8a83033ca69012ea225ead69e5e1
parent b522325f2ca74aa72ab6ae194ef95bc294cc2cb9
author dev <dev@example.com> 1787695703 +0530
committer dev <dev@example.com> 1787695703 +0530

merge bob-logging into alice-caching

Alice's commit and Bob's commit both stay in the graph, exactly as each of them wrote it. The merge commit only adds a new node that points at both. History branches, then joins, and keeps the full record of the split.

Step 5 · Rebase: the same conflict, replayed

Rebase answers the same problem a different way. Instead of joining two lines of history, it moves one branch's commits onto the tip of the other, one at a time.

$ git checkout bob-logging -b bob-logging-rebase
$ git rebase alice-caching
Auto-merging handler.py
CONFLICT (content): Merge conflict in handler.py
error: could not apply b522325... log get_bookmark reads

The conflict is the same, for the same reason: both edits still touch the same two lines. A person resolves it the same way: edit the file, remove the markers, and stage the result. One more command tells the rebase to continue.

$ git add handler.py
$ git rebase --continue
[detached HEAD dafcb5f] log get_bookmark reads
Successfully rebased and updated refs/heads/bob-logging-rebase.
$ git log --oneline --graph
* dafcb5f log get_bookmark reads
* 2eef24b cache get_bookmark reads
* 0f7613d add get_bookmark handler
* c98ebfe first commit

The history is one straight line. There is no merge commit. There was never a second branch to join — Bob's commit was rewritten to sit directly on top of Alice's. Rebase kept Bob's message and his final content, but not his commit's identity.

bob's commit before the rebase: b522325
bob's commit after the rebase:  dafcb5f
Rebase changes the hash

A commit's hash is a hash of its own content, including its parent. Give a commit a new parent and you get a new commit with a new hash. Git does not edit the old commit; it replaces it with the new one. If anyone else already has b522325 in their history, their copy and the rebased copy are now two different commits with the same message. Never rebase a commit that a branch other people build on already carries.

Step 7 · The index sits between the working file and the commit

You edit a file. That change does not touch any commit yet — it only changes the file on disk. git add copies the file's current content into a new blob and points the index at it. git commit then writes a tree from the index, never straight from disk.

$ echo v2 > f.txt
$ git status --short
 M f.txt
$ git diff
-v1
+v2
$ git add f.txt
$ git diff --staged
-v1
+v2
$ git diff

Before git add, git diff shows the change: working file against the index. After git add, git diff shows nothing, because the index now matches the working file. git diff --staged shows the same change instead: index against the last commit. A commit only ever records what was staged, even if the working file changes again right after.

Step 8 · The failure: a force-push erases an approved commit

A commit reaches origin/main after review. A teammate later resets their local branch by one commit — a mistaken rebase, an over-eager reset --hard. They push with --force, which tells the remote to accept the new tip without checking that it descends from the old one.

$ git log --oneline -1
0f7613d add get_bookmark handler          # reviewed, on origin/main

$ git reset --hard HEAD~1
$ git log --oneline -2
c98ebfe first commit

$ git push --force origin main
$ git ls-remote origin main
c98ebfe1cd1b... refs/heads/main           # the approved commit is gone

The remote branch now points at c98ebfe. Nothing on origin still names 0f7613d. A teammate who pulls main right now gets a repository with no trace that the handler was ever added.

Step 9 · The rescue: git reflog

Git does not delete a commit the moment it stops being reachable. An unreachable commit only becomes eligible for garbage collection, and that collection runs on a schedule, not right away. Every local repository keeps its own private log of where HEAD pointed, called the reflog.

$ git reflog -3
c98ebfe HEAD@{0}: reset: moving to HEAD~1
0f7613d HEAD@{1}: reset: moving to 0f7613df1566b67ea4b944a2fa527dac790c2a4a
0f7613d HEAD@{2}: checkout: moving from bob-logging-rebase to main

HEAD@{1} names the exact commit the mistaken reset removed. Reset back to it, then force-push again to overwrite the bad state with the good one.

$ git reset --hard 0f7613d
$ git push --force origin main
$ git ls-remote origin main
0f7613df1566b67ea4b944a2fa527dac790c2a4a refs/heads/main   # restored
The reflog is local, not shared

This rescue only works on the machine where the commit was made. The reflog is not part of the repository's objects and is never pushed or cloned. If the developer who ran the mistaken reset does not still have their local clone, this rescue has nothing to read from. This is why branch protection, not memory of the reflog, is the real fix — see the next section.

Step 10 · Pull requests and branch protection

A pull request is a proposed set of commits, shown as one diff against the target branch, before it merges. GitHub, GitLab, and Bitbucket all implement the same idea under different names.

  • A reviewer reads the diff, not the finished file. A diff shows exactly what changed and why one line matters more than the surrounding ones.
  • CI runs against the pull request's commits, so a broken build is visible before the merge, not after.
  • Branch protection is a repository setting that blocks a direct push to main. It separately blocks a force-push to main, even from an administrator, by default. It requires a pull request, at least one approval, and passing checks first.

Turn branch protection on for main and the failure in Step 8 cannot happen there. The remote refuses the force-push outright, so the reflog rescue is never needed.

Practice

  1. Run the demo. From Code/Lesson_13_code, run ./demo.sh. Read the transcript against this page and find every commit's parent line.
  2. Cause your own conflict. Make two branches from one commit, edit the same two lines of the same file on each, and merge one into the other. Resolve it by hand.
  3. Rebase instead. Repeat the last step with git rebase in place of git merge. Compare git log --graph for both outcomes.
  4. Lose a commit, then find it. Commit something, git reset --hard HEAD~1, then use git reflog to get it back without typing the commit message from memory.
  5. Turn on branch protection. On a real GitHub repository you own, protect main: require a pull request, and block force-pushes. Try to push directly to main and read the rejection.
