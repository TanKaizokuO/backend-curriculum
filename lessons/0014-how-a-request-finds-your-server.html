How a request finds your server A name becomes an address through caches you do not control.

Every request in this course so far started with a socket already open to a known IP address. A real client never gets an IP address first. It gets a name — bookmarks-api.example.com — and it must turn that name into an address before it can open a socket at all. That step is DNS, and it happens outside your server, in servers and caches you do not own.

The whole lesson in one sentence

A name becomes an address through caches you do not control.

How the two languages sit together

DNS is a packet format on UDP, not a language feature, so the raw mechanism ports directly: dns_query.py and dnsQuery.ts build the same header and parse the same answer. Read the Python steps first. The TypeScript section at the end is recognition, not new material.

Step 1 · A name is not an address

Lesson 1 opened a TCP socket straight to an IP address typed by hand. Every lesson since has run against 127.0.0.1 or a container on the same machine, so the address was already known. A real client starts from a name, not an address, and asks a separate system to convert one into the other: the Domain Name System, DNS.

The tool for this is normally dig, and the library for this is normally socket.getaddrinfo. Both hide the same packet. Build the packet by hand once, the way Lesson 1 built an HTTP request by hand, and the rest of the lesson has nothing left to take on faith.

Step 2 · The query, by hand

A DNS message starts with a fixed twelve-byte header, then a question. The header names a random id — echoed back in the answer, so the client can match a reply to its own request — and counts of how many questions, answers, and other records follow.

Code/Lesson_14_code/dns_query.py

def build_query(name: str, qtype: int) -> bytes:
    query_id = random.randint(0, 0xFFFF)
    flags = 0x0100  # RD=1: "please recurse for me"
    header = struct.pack(">HHHHHH", query_id, flags, 1, 0, 0, 0)
    question = encode_name(name) + struct.pack(">HH", qtype, 1)  # class IN
    return header + question

A name in the question is not a string. It is a sequence of length-prefixed labels: example.com becomes one byte holding 7, the bytes example, one byte holding 3, the bytes com, and a final zero byte. The length before each label is why one label cannot exceed 63 bytes and a full name cannot exceed 255.

$ python3 dns_query.py example.com A
id=0xdb65 rcode=0 answers=2
example.com.	241	IN	A	172.66.147.243
example.com.	241	IN	A	104.20.23.154

The reply repeats the id, so the client can tell this answer belongs to this question. rcode=0 means no error. Each answer line names the record: the domain, a number of seconds, the class (IN, for Internet — the only class in use today), the record type, and the value. The number is the TTL, and Step 6 depends on it.

Step 3 · Record types answer different questions

A domain can hold more than one kind of record, and each type answers a different question. The same script, run against real domains, shows four more.

$ python3 dns_query.py example.com AAAA
id=0x15d5 rcode=0 answers=2
example.com.	103	IN	AAAA	2606:4700:10::6814:179a
example.com.	103	IN	AAAA	2606:4700:10::ac42:93f3

$ python3 dns_query.py www.github.com CNAME
id=0x98f0 rcode=0 answers=1
www.github.com.	3600	IN	CNAME	github.com

$ python3 dns_query.py google.com MX
id=0x0c99 rcode=0 answers=1
google.com.	8	IN	MX	10 smtp.google.com

$ python3 dns_query.py example.com TXT
id=0x9ded rcode=0 answers=2
example.com.	219	IN	TXT	v=spf1 -all
example.com.	219	IN	TXT	_k2n1y4vw3qtb4skdx9e7dxt97qrmmq9
  • A maps a name to an IPv4 address. AAAA does the same for IPv6. A name can hold more than one of each; a resolver picks one, and Step 6's cache remembers only the ones it picked.
  • CNAME maps a name to another name, not an address. www.github.com holds no address of its own — a client must resolve github.com next to finish the job. A name with a CNAME record may hold no other record type at that name.
  • MX names the mail server for a domain, plus a preference number. A lower number is tried first.
  • TXT holds arbitrary text. Domain owners use it to prove control of the domain to a third party, or to publish a mail policy such as v=spf1, without adding a new record type for every new purpose.

Step 4 · The walk from root to authoritative

The query in Step 2 went to one resolver and got a final answer. That resolver did not know the answer in advance. It walked a chain of servers, each one narrower than the last, and this lesson's copy of that walk uses one dig call per step so each server's answer is visible on its own.

A root server knows nothing about example.com. It knows which servers handle every top-level domain — .com, .org, and the rest — and nothing more.

$ dig @198.41.0.4 example.com A +noall +authority
com.			172800	IN	NS	l.gtld-servers.net.
com.			172800	IN	NS	j.gtld-servers.net.
com.			172800	IN	NS	h.gtld-servers.net.
# … 10 more .com servers, not shown

A TLD server — one of the .com servers just named — knows nothing about the record itself. It knows which servers are authoritative for example.com: the ones the domain's owner actually configured.

$ dig @192.5.6.30 example.com A +noall +authority
example.com.		172800	IN	NS	hera.ns.cloudflare.com.
example.com.		172800	IN	NS	elliott.ns.cloudflare.com.

The authoritative server holds the actual record and answers it directly.

$ dig @108.162.192.162 example.com A +noall +answer
example.com.		300	IN	A	104.20.23.154
example.com.		300	IN	A	172.66.147.243

The address matches Step 2's answer, because Step 2's resolver did this exact walk on its behalf. Root, TLD, and authoritative servers each answered without recursing further — dig against any of them directly reports WARNING: recursion requested but not available — because none of the three is meant to serve a client. A client talks to one more kind of server instead, covered next.

Step 5 · The recursive resolver does the walk for you

Step 2's single query never touched a root or TLD server directly. It went to a recursive resolver — usually the one your operating system or your ISP hands you by default, or a public one such as 1.1.1.1 — and that resolver ran the whole three-step walk on your behalf, then cached the result.

This is why the second query for the same name comes back faster than the first, and why it is safe to ask the same resolver thousands of times a day: the walk in Step 4 runs once, and every later request within the TTL reads the cached answer instead.

Step 6 · TTL — the observable failure

The TTL is the number of seconds a resolver may keep an answer before asking again. A short TTL means a change to the record reaches every client fast, at the cost of asking the authoritative server more often. A long TTL — a real DNS provider might set 86400 seconds, a full day, on a record that rarely changes — means fewer queries, at the cost of every cache serving the old answer for up to that long after the record changes.

Build the smallest version of both sides to see this happen in seconds instead of a day. toy_dns_server.py is a one-record authoritative server; it rereads zone.json on every query, the way an operator's change reaches a real authoritative server the moment it saves. caching_resolver.py is a stub resolver with its own TTL-keyed cache — the same shape as Step 5's resolver, small enough to read in one sitting.

Code/Lesson_14_code/caching_resolver.py

def resolve(name: str) -> str:
    cache = load_cache()
    now = time.time()
    entry = cache.get(name)
    if entry and entry["expires_at"] > now:
        return entry["ip"]  # cache hit — no packet sent
    ip, ttl = query_authoritative(name)
    cache[name] = {"ip": ip, "expires_at": now + ttl}
    save_cache(cache)
    return ip
$ # zone.json: bookmarks-api.local -> 10.0.0.5, ttl=5
$ python3 caching_resolver.py bookmarks-api.local
cache miss: queried authoritative, bookmarks-api.local -> 10.0.0.5 (ttl=5s)

$ python3 caching_resolver.py bookmarks-api.local
cache hit: bookmarks-api.local -> 10.0.0.5 (5.0s left on TTL)

$ # operator changes zone.json: bookmarks-api.local -> 10.0.0.9
$ python3 caching_resolver.py bookmarks-api.local
cache hit: bookmarks-api.local -> 10.0.0.5 (4.9s left on TTL)   # stale — the fix is live, the answer is not

$ sleep 6
$ python3 caching_resolver.py bookmarks-api.local
cache miss: queried authoritative, bookmarks-api.local -> 10.0.0.9 (ttl=5s)   # fresh
The record is correct the instant it changes. The answer is not.

The authoritative server in this transcript answered 10.0.0.9 on the very query right after the change. The resolver still returned 10.0.0.5 for the next 4.9 seconds, because its cached entry had not expired. Scale the TTL from 5 seconds to 86400, and a caller changing an A record can wait a full day for every cache in the world to notice. A migration that depends on DNS switching instantly is a migration that will fail for some fraction of users for as long as the old TTL allows.

Step 7 · The address, not the name, is what opens the socket

Lesson 1's socket connected straight to an IP address. Every step above exists to produce exactly that address before the socket in Lesson 1 opens. curl --resolve makes the boundary explicit: give it a name, a port, and an address, and it skips its own name lookup and connects to the address supplied — the same address caching_resolver.py just returned.

$ python3 caching_resolver.py bookmarks-api.local
cache miss: queried authoritative, bookmarks-api.local -> 127.0.0.1 (ttl=5s)

$ curl --resolve bookmarks-api.local:8020:127.0.0.1 http://bookmarks-api.local:8020/healthz
200

Nothing about the request itself changed. Lesson 12's API never learns that its caller found it by name instead of by a hardcoded address — DNS finishes its job before the TCP handshake in Lesson 1 even starts.

TypeScript: the same packet, the same failure

The packet format does not depend on the language reading it. dnsQuery.ts builds the identical header and question over Node's dgram socket in place of Python's; toyDnsServer.ts and cachingResolver.ts reproduce Step 6 exactly.

Code/js/Lesson_14_code/src/dnsQuery.ts

function buildQuery(name: string, qtype: number): Buffer {
  const id = Math.floor(Math.random() * 0xffff);
  const header = Buffer.alloc(12);
  header.writeUInt16BE(id, 0);
  header.writeUInt16BE(0x0100, 2); // RD = 1
  header.writeUInt16BE(1, 4); // 1 question
  // … the same length-prefixed labels as dns_query.py, then type + class
}
$ node dnsQuery.ts example.com A
id=0x75a7 rcode=0 answers=2
example.com.	218	IN	A	104.20.23.154
example.com.	218	IN	A	172.66.147.243
$ # zone.json: bookmarks-api.local -> 10.0.0.5, ttl=5

$ node cachingResolver.ts bookmarks-api.local

Practice

  1. Run the demo. From Code/Lesson_14_code, run ./demo.sh. It needs no database and no Docker — only a network connection.
  2. Query a domain you own, or one you use daily. python3 dns_query.py <name> A, then compare the TTL to how often you would guess that domain's address changes.
  3. Read the raw wire format. Run dig +short bookmarks-api.local A against nothing — it will fail, because bookmarks-api.local only exists inside toy_dns_server.py's zone.json, never in real DNS. Confirm you understand why: a name only resolves through a server that has agreed to answer for it.
  4. Shorten a TTL, then watch it matter. Edit zone.json's ttl to 1, rerun the four-query sequence from Step 6, and time how much narrower the stale window gets.
  5. Run the Lesson 12 API by name. Start uvicorn main:app --port 8020 from Code/Lesson_14_code with its database running, point zone.json's IP at 127.0.0.1, resolve it with caching_resolver.py, and hit /healthz with curl --resolve using the address it returned.
