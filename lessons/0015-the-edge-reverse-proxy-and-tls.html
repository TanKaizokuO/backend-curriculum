The edge: reverse proxy and TLS The process that answers port 443 is not your application.

Lesson 14 turned a name into an address. The address still points at a socket, and every socket in this course so far has belonged to your application. In production it does not. A separate process answers the connection first, decides what to do with it, and only then — if at all — talks to your application. That process is the edge.

The whole lesson in one sentence

The process that answers port 443 is not your application.

How the two languages sit together

A reverse proxy is a protocol handler, not a language feature, so the raw mechanism ports directly: tls_proxy.py and tlsProxy.ts terminate the identical TLS handshake and rewrite the identical headers. Read the Python steps first. The TypeScript section at the end is recognition, not new material.

Step 1 · An origin behind an edge

This lesson needs a small server that reports exactly what it received, so a proxy's effect on a request is visible instead of assumed. origin.py answers two routes: GET /whoami returns the socket address and headers it saw, and POST /upload returns how many bytes it read. It never terminates TLS and never sees the outside network directly — every request in this lesson reaches it through a proxy.

$ python3 origin.py
origin listening on http://127.0.0.1:8030 (plain HTTP, no TLS)

$ curl -s http://127.0.0.1:8030/whoami
{
  "socket_peer": "127.0.0.1",
  "host_header": "127.0.0.1:8030",
  "x_forwarded_for": null,
  "x_forwarded_proto": null,
  "x_real_ip": null
}

Called directly, the origin sees exactly what Lesson 1's raw socket always saw: a peer address and a set of headers, nothing more. The three forwarding headers are absent because nothing added them yet. Every step below changes one thing about this picture.

Step 2 · TLS termination, by hand

Lesson 12 built a reverse proxy that copied bytes between a client and a backend and looked at neither. Before Nginx, build the version that also ends TLS at the proxy: the client's encrypted session stops here, and the hop onward to origin.py is plain HTTP, the same protocol Lesson 1 read by hand.

Code/Lesson_15_code/tls_proxy.py

try:
    tls_sock = _base_context.wrap_socket(raw_sock, server_side=True)
except ssl.SSLError as exc:
    print(f"tls_proxy: handshake with {client_addr[0]} failed: {exc}")
    raw_sock.close()
    return

head, already_read_body = _read_request_head(tls_sock)  # plain HTTP bytes, decrypted

ssl.SSLContext.wrap_socket is the whole mechanism: it takes a plain TCP socket already accepted by socket.accept(), and returns a socket that decrypts on read and encrypts on write. Everything after that line — reading a request line, reading headers up to the blank line, forwarding to origin.py — is exactly the parsing Lesson 2 wrote for a server with no TLS at all.

Step 3 · The observable failure: a certificate nobody signed

A certificate proves an identity only if something the client already trusts vouches for it — normally a public certificate authority. A name like bookmarks-api.local can never get one; no public CA signs a certificate for a name it cannot verify belongs to you. The only option is a self-signed certificate: one the server signs with its own key, vouching for itself.

$ ./generate_certs.sh
wrote certs/bookmarks-api.local.crt (CN=bookmarks-api.local)
wrote certs/admin.bookmarks-api.local.crt (CN=admin.bookmarks-api.local)

$ curl -v https://bookmarks-api.local:8443/whoami \
    --resolve bookmarks-api.local:8443:127.0.0.1
* SSL certificate problem: self-signed certificate

curl refuses the connection before it sends a single byte of the request. This is correct behaviour, not a bug in the demo: curl trusts only the certificate authorities in its own CA bundle, and nothing signed this certificate. Tell curl to trust this one file explicitly, and the same request completes.

$ curl -s --cacert certs/bookmarks-api.local.crt \
    https://bookmarks-api.local:8443/whoami \
    --resolve bookmarks-api.local:8443:127.0.0.1
{
  "socket_peer": "127.0.0.1",
  "host_header": "bookmarks-api.local:8443",
  "x_forwarded_for": "127.0.0.1",
  "x_forwarded_proto": "https",
  "x_real_ip": null
}
A production certificate removes one step, not the proof

A certificate from a public CA such as Let's Encrypt works without --cacert, because curl's CA bundle already trusts that CA. It does not remove the check — it only means the check passes without extra help from the caller. A self-signed certificate skips the check by telling the client to trust one specific file, which works for a demo and for two servers you control, and fails for the public internet.

Step 4 · SNI: choosing a certificate before the request exists

Lesson 1's reference card named virtual hosting: many domains share one IP address, and the Host header tells a plain HTTP server which one a request is for. TLS breaks that trick, because the Host header lives inside the encrypted request — and the server must pick a certificate before it can decrypt anything. SNI, Server Name Indication, solves this by sending the requested hostname in clear text, inside the handshake itself, before any encryption starts.

Code/Lesson_15_code/tls_proxy.py

def _select_certificate(tls_socket, server_name, _ctx):
    matched = server_name in _contexts
    served = server_name if matched else DEFAULT_HOSTNAME
    print(f"tls_proxy: SNI asked for {server_name!r} -> serving cert for {served!r}")
    tls_socket.context = _contexts[served]

_base_context.sni_callback = _select_certificate

One process, one port, two certificates. The hostname the client sends during the handshake — before the HTTP request line exists — decides which one it gets.

$ openssl s_client -connect 127.0.0.1:8443 -servername bookmarks-api.local </dev/null 2>/dev/null \
    | openssl x509 -noout -subject
subject=CN = bookmarks-api.local

$ openssl s_client -connect 127.0.0.1:8443 -servername admin.bookmarks-api.local </dev/null 2>/dev/null \
    | openssl x509 -noout -subject
subject=CN = admin.bookmarks-api.local

Same port, same process, two different certificates, chosen entirely by the name sent before any HTTP bytes moved.

Step 5 · Forwarding headers: giving back what termination took away

Look again at Step 2's transcript. socket_peer is still 127.0.0.1 — the proxy's own address, from the origin's point of view — and x_forwarded_for is now 127.0.0.1 too, because in this demo the client and proxy share a machine. In production those two values differ: TLS termination means the origin's TCP connection comes from the proxy, never from the real client, so the origin's own idea of "who sent this" is now wrong unless something restores it.

Code/Lesson_15_code/tls_proxy.py

headers = [line for line in lines[1:]
           if not line.lower().startswith((b"x-forwarded-for:", b"x-forwarded-proto:"))]
headers.append(f"X-Forwarded-For: {client_addr[0]}".encode())
headers.append(b"X-Forwarded-Proto: https")

Two things matter in that line. First, the proxy strips any X-Forwarded-For the client already sent before adding its own — otherwise a client could claim any address it liked, and the origin would believe it. Second, X-Forwarded-Proto tells the origin the outside protocol was HTTPS even though the hop it actually sees is plain HTTP — the origin has no other way to know, since TLS ended one hop back.

Step 6 · The observable failure: an unbounded body

Nothing in Step 2's mechanism limits how large a request body can be. An origin that reads the whole body before checking anything can be made to allocate memory for a body of any size a client cares to send. The proxy checks Content-Length before it reads or forwards a single byte of the body.

Code/Lesson_15_code/tls_proxy.py

if content_length > MAX_BODY_BYTES:
    response = (
        b"HTTP/1.1 413 Content Too Large\r\n"
        b"Content-Length: " + str(len(body)).encode() + b"\r\n"
        b"Connection: close\r\n\r\n" + body
    )
    tls_sock.sendall(response)
    return  # the origin never sees this connection
$ curl -s --cacert certs/bookmarks-api.local.crt -X POST --data "small" \
    https://bookmarks-api.local:8443/upload --resolve bookmarks-api.local:8443:127.0.0.1
{"received_bytes": 5}

$ python3 -c "print('x' * 2000)" > /tmp/big.txt
$ curl -s -o /dev/null -w "%{http_code}\n" --cacert certs/bookmarks-api.local.crt \
    -X POST --data-binary @/tmp/big.txt \
    https://bookmarks-api.local:8443/upload --resolve bookmarks-api.local:8443:127.0.0.1
413

A 2001-byte body against a 1024-byte limit gets 413 from the proxy. origin.py's log shows nothing for this request — the rejection never reached it.

Step 7 · The abstraction: Nginx does the same four jobs, declared

tls_proxy.py proved the mechanism behind TLS termination, SNI, forwarding headers, and a body limit. A real edge does not hand-roll any of them — it configures a proxy that already implements all four, correctly, under real load. nginx.conf states the same four jobs from Steps 2 through 6 as configuration.

Code/Lesson_15_code/nginx.conf

http {
  client_max_body_size 1k;                    # Step 6, one line

  server {
    listen 443 ssl;
    server_name bookmarks-api.local;          # Step 4: SNI picks this block

    ssl_certificate     /etc/nginx/certs/bookmarks-api.local.crt;
    ssl_certificate_key /etc/nginx/certs/bookmarks-api.local.key;

    location / {
      proxy_pass http://127.0.0.1:8030;
      proxy_set_header X-Forwarded-For $remote_addr;    # Step 5
      proxy_set_header X-Forwarded-Proto $scheme;
    }
  }

  server { # a second block, for admin.bookmarks-api.local, same shape }
}

Every transcript from Steps 3 through 6 repeats, unchanged, against Nginx instead of tls_proxy.py.

TypeScript: the same handshake, the same headers

TLS is a protocol, not a language feature, so tlsProxy.ts terminates the identical handshake with Node's tls module in place of Python's ssl module. SNICallback is Node's name for the hook Python calls sni_callback; it runs at the same point in the handshake and does the same job.

Code/js/Lesson_15_code/src/tlsProxy.ts

const server = tls.createServer({
  SNICallback: (servername, callback) => {
    const matched = contexts.has(servername);
    const served = matched ? servername : defaultHostname;
    callback(null, contexts.get(served)!);
  },
  // cert / key for the initial handshake before SNI resolves
}, (clientSocket) => { /* parse the request head, add X-Forwarded-*, forward it */ });

Practice

  1. Run the demo. From Code/Lesson_15_code, run ./demo.sh. It needs python3, curl, openssl, and Docker.
  2. Inspect a real certificate. Run openssl s_client -connect example.com:443 -servername example.com </dev/null 2>/dev/null | openssl x509 -noout -issuer -dates and compare the issuer to certs/bookmarks-api.local.crt's: one names a certificate authority, the other names the certificate itself.
  3. Break the forwarding headers on purpose. Comment out the two lines in tls_proxy.py that add X-Forwarded-For and X-Forwarded-Proto, rerun a request, and read what the origin now believes about the client.
  4. Lower the body limit until it hurts. Set client_max_body_size to 10 in nginx.conf, restart the container, and send a normal JSON body from Lesson 3's bookmarks API through it.
  5. Run the Lesson 12 / 14 API behind the proxy. Point ORIGIN_PORT in tls_proxy.py (or proxy_pass in nginx.conf) at 8020, start that API, and hit /healthz through HTTPS instead of plain HTTP.
