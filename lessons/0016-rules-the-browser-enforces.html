Rules the browser enforces CORS and CSP are instructions to the browser. They protect the user, not the server.

Every lesson so far tested a server with curl or a raw socket. Neither one enforces same-origin rules, so neither one can show what this lesson is about. curl sends whatever bytes you tell it to and prints whatever comes back. A browser does not: it decides for itself, after your server has already answered, whether the calling page is allowed to read that answer at all. This lesson needs a real browser, because a real browser is the thing enforcing the rule.

The whole lesson in one sentence

CORS and CSP are instructions to the browser. They protect the user, not the server.

How the two languages sit together

CORS, CSP, and cookie attributes are protocol rules, read by the browser, not by either server language. api.py and api.ts answer with the identical headers, and static/index.html is the same file in both projects. Read the Python steps first. The TypeScript section at the end runs the same page against the same browser and gets the same result.

Step 1 · Two origins on the loopback interface

An origin is a scheme, a host, and a port, taken together. Change any one of the three and the browser treats it as a different origin, even on the same machine. This lesson needs two: static_site.py serves a page from http://127.0.0.1:8051, and api.py answers on http://127.0.0.2:8040 — a different loopback address, so the two count as different origins without needing a domain name or /etc/hosts entry.

Code/Lesson_16_code/static/script.js

const API = "http://127.0.0.2:8040";
const res = await fetch(`${API}/bookmarks`);

Nothing about this line looks dangerous — it is the same fetch() every earlier lesson used. What changes is where the page making the call was loaded from.

Step 2 · The observable failure: a 200 the page never sees

Start both servers and open http://127.0.0.1:8051/ in a browser. Click "Load bookmarks". The button calls GET /bookmarks — a simple request in the Fetch standard's terms, since it uses an allowed method and adds no headers beyond the safelisted ones, so the browser sends it immediately, with no preflight. The server answers. The page still shows an error.

$ curl -s http://127.0.0.2:8040/bookmarks
{
  "bookmarks": [
    { "id": 1, "title": "MDN: same-origin policy" },
    { "id": 2, "title": "MDN: CORS" }
  ]
}

curl gets a normal 200, because curl enforces no same-origin rule at all. The browser's own console, on the same request from the same server, reads differently:

Access to fetch at 'http://127.0.0.2:8040/bookmarks' from origin
'http://127.0.0.1:8051' has been blocked by CORS policy: No
'Access-Control-Allow-Origin' header is present on the requested resource.
Failed to load resource: net::ERR_FAILED

api.py's own log for this request reads "GET /bookmarks HTTP/1.1" 200 - — the server did the work and sent the full response over the wire. The browser received it, read the headers, found no Access-Control-Allow-Origin, and threw the body away before any of the page's own JavaScript could touch it. fetch()'s promise rejects with a plain TypeError: Failed to fetch; the specific reason lives only in the console, by design — a script is not allowed to learn why a cross-origin read failed.

Step 3 · The observable failure: a request that never leaves

Click "Log in". This button calls POST /login with a JSON body, which is not a simple request — Content-Type: application/json is not on the safelist, so the browser sends a preflight request first: an OPTIONS asking the server's permission before it sends the real one.

$ curl -sD - -o /dev/null -X OPTIONS http://127.0.0.2:8040/login \
    -H "Origin: http://127.0.0.1:8051" \
    -H "Access-Control-Request-Method: POST" \
    -H "Access-Control-Request-Headers: content-type"
HTTP/1.1 204 No Content
Content-Length: 0
Connection: close

No Access-Control-* header comes back, so a real browser stops here. The console names the exact step that failed, distinct from Step 2's:

Access to fetch at 'http://127.0.0.2:8040/login' from origin
'http://127.0.0.1:8051' has been blocked by CORS policy: Response to
preflight request doesn't pass access control check: No
'Access-Control-Allow-Origin' header is present on the requested resource.

api.py's log shows only the OPTIONS request, never a POST. The real request was never sent at all — a failed preflight cancels it before it exists, the same way Lesson 15's oversize-body check stopped a request before the origin ever saw it.

Step 4 · The fix: answer both questions the browser is asking

A browser sends two different questions across these two requests: "is this origin allowed?", and, before a non-simple request, "is this method and these headers allowed?" api.py answers both, only for the one origin this demo trusts.

Code/Lesson_16_code/api.py

def _cors_headers(self, for_preflight: bool) -> None:
    origin = self.headers.get("Origin")
    if origin not in ALLOWED_ORIGINS:
        return
    # Echo the one calling origin back, never "*" — a wildcard cannot
    # carry Access-Control-Allow-Credentials, and login needs credentials.
    self.send_header("Access-Control-Allow-Origin", origin)
    self.send_header("Access-Control-Allow-Credentials", "true")
    self.send_header("Vary", "Origin")
    if for_preflight:
        self.send_header("Access-Control-Allow-Methods", "GET, POST")
        self.send_header("Access-Control-Allow-Headers", "Content-Type")
Never echo credentials onto a wildcard

MDN's CORS reference states it plainly: a credentialed response must name one origin, never *. A server that both accepts cookies and answers every origin with * would let any site on the internet read a signed-in user's data by asking on their behalf. Checking Origin against an explicit allow-list, the way api.py does, is the only safe way to combine credentials with more than one trusted caller.

With CORS_ALLOW=on, both transcripts change. The preflight now answers, and the real requests both succeed in a real browser:

$ curl -sD - -o /dev/null -X OPTIONS http://127.0.0.2:8040/login \
    -H "Origin: http://127.0.0.1:8051" \
    -H "Access-Control-Request-Method: POST" \
    -H "Access-Control-Request-Headers: content-type"
HTTP/1.1 204 No Content
Access-Control-Allow-Origin: http://127.0.0.1:8051
Access-Control-Allow-Credentials: true
Access-Control-Allow-Methods: GET, POST
Access-Control-Allow-Headers: Content-Type
Access-Control-Max-Age: 600

$ curl -s http://127.0.0.2:8040/bookmarks -H "Origin: http://127.0.0.1:8051"
{ "bookmarks": [ ... ] }   # now with Access-Control-Allow-Origin on the response

In the browser, "Load bookmarks" now shows the two bookmarks, and "Log in" shows {"logged_in": true}. Both buttons call the same code as Steps 2 and 3; only the server's headers changed.

Step 5 · The observable failure that CORS headers do not fix

POST /login sets a cookie:

Set-Cookie: session=demo-session-token; HttpOnly; SameSite=Lax; Path=/

Click "Who am I?" right after logging in. It calls GET /whoami with credentials: "include", so the browser should attach any cookie it has for 127.0.0.2:8040. The response says otherwise:

GET /whoami ->
{
  "origin_header": "http://127.0.0.1:8051",
  "cookie_header": null,
  "logged_in": false
}

The login two clicks ago reported success. This request, to the same server, from the same page, has no memory of it. CORS is not the problem — the CORS headers are correct, and the request reached the server. Something else decided this cookie should not exist for this caller.

Step 6 · SameSite: a second, separate boundary

CORS asks about origin — scheme, host, and port, all three. Cookies ask about site — scheme and registrable domain, ignoring port. Lesson 15's two hostnames, bookmarks-api.local and admin.bookmarks-api.local, were different origins and different sites. Two ports on the same 127.0.0.1 would have been different origins but the same site — which is exactly why this lesson put the API on 127.0.0.2 instead: the cookie failure in Step 5 only shows up across a genuine cross-site boundary.

A cookie with no SameSite attribute defaults to Lax. MDN's cookies guide states the rule this demo just proved: browsers already withhold a cross-site cookie by default as a privacy measure, and SameSite=Lax reinforces the same restriction for the cookie's own site. The Set-Cookie from Step 5 arrived on a cross-site response, so the browser never kept it at all — not "kept it but withheld it", never stored it:

> await page.cookies('http://127.0.0.2:8040')
[]

COOKIE_SAMESITE=None asks for the opposite of Lax: send this cookie on cross-site requests too. Restart api.py with it set, log in again, and the cookie still does not appear in the store. MDN's rule again: SameSite=None requires the Secure attribute, and a cookie missing it is rejected outright. This demo runs on plain HTTP — the same choice origin.py made in Lesson 15 — so Secure is not present, and the browser drops the cookie before it is ever stored. Finishing this step for real needs Lesson 15's TLS proxy in front of both origins; it is this lesson's closing practice step, not part of the demo, so this lesson stays on plain HTTP throughout.

HttpOnly, checked separately

Set-Cookie above also carries HttpOnly. Logging in directly against http://127.0.0.2:8040 — same origin, no cross-site question involved — stores the cookie and sends it back on the next request, but document.cookie on that same page reads "". The server sees cookie_header: "session=demo-session-token"; the page's own JavaScript sees nothing. HttpOnly is unrelated to CORS or SameSite — it hides a cookie from script on every origin, including the one that set it, which is why a session cookie should always carry it.

Step 7 · CSP: a policy about a page's own content, not about origins

CORS and SameSite both govern a browser's dealings with another origin. Content-Security-Policy governs something narrower: what a page is allowed to load and run, stated by that page's own server, independent of any other origin's cooperation. static/index.html ships one inline script on purpose:

Code/Lesson_16_code/static/index.html

<script>window.__inlineRan = true;</script>

With no CSP header, it runs, and the page reports "Inline script executed: yes". Restart static_site.py with CSP_MODE=on, which adds one header to the HTML response:

Content-Security-Policy: default-src 'self'

Reload the page. It reports "Inline script executed: no", and the console names exactly what happened:

Executing inline script violates the following Content Security Policy
directive: "default-src 'self'". Either the 'unsafe-inline' keyword, a
hash ('sha256-...'), or a nonce ('nonce-...') is required to enable
inline execution. Note also that 'script-src' was not explicitly set, so
'default-src' is used as a fallback. The action has been blocked.

script.js, loaded from <script src="script.js">, still runs — it is same-origin, so 'self' allows it. Only the inline snippet is refused. This is the whole value of the policy: it does not ask whether the code is correct, only whether it arrived the way the policy trusts code to arrive. An attacker who manages to inject <script>steal(document.cookie)</script> into this page — the classic reflected-XSS payload — gets refused by the same rule, without the server ever having to detect the injection at all.

default-src is a fallback for every fetch directive, including connect-src

default-src 'self' does not only govern scripts. Point "Load bookmarks" at the API origin while this CSP header is active, and the request is refused before it leaves the page at all — a second, independent block on top of anything CORS allows, because connect-src was never set and falls back to default-src too. Fixing CORS on the server does not help; the page's own policy needs connect-src 'self' http://127.0.0.2:8040 before the request is allowed to leave.

TypeScript: the same policy, the same browser, the same result

CORS, cookies, and CSP are read by the browser, not by either server language, so api.ts and staticSite.ts answer with headers identical to the Python versions, and src/static/ is the same three files unchanged — HTML, CSS, and client JavaScript need no port at all.

Code/js/Lesson_16_code/src/api.ts

function corsHeaders(req, res, forPreflight: boolean): void {
  const origin = req.headers.origin;
  if (!origin || !ALLOWED_ORIGINS.has(origin)) return;
  res.setHeader("Access-Control-Allow-Origin", origin);
  res.setHeader("Access-Control-Allow-Credentials", "true");
  if (forPreflight) {
    res.setHeader("Access-Control-Allow-Methods", "GET, POST");
    res.setHeader("Access-Control-Allow-Headers", "Content-Type");
  }
}
$ node src/api.ts &
api listening on http://127.0.0.2:8040 (CORS_ALLOW=false, COOKIE_SAMESITE=Lax)

$ curl -sD - -o /dev/null -X OPTIONS http://127.0.0.2:8040/login \
    -H "Origin: http://127.0.0.1:8051" \
    -H "Access-Control-Request-Method: POST" \
    -H "Access-Control-Request-Headers: content-type"
HTTP/1.1 204 No Content
Content-Length: 0
Connection: close        # same missing headers as api.py, Step 3

Opened in the same headless Chromium the Python steps used, http://127.0.0.1:8051/ against api.ts with CORS_ALLOW=on reproduces Step 5's exact failure — login answers {"loggedIn": true}, and the very next whoami call still reports cookieHeader: null. Nothing about the language changed the outcome, because nothing about the language enforced the rule in the first place: the browser did.

Practice

  1. Run the demo. From Code/Lesson_16_code, run ./demo.sh. It needs python3 and curl, and prints every header transcript in this lesson.
  2. Watch it fail in your own browser. Start api.py and static_site.py with no environment variables, open http://127.0.0.1:8051/, open the browser's console, and click all three buttons. Read the exact wording of each error before reading it here again.
  3. Break the fix on purpose. With CORS_ALLOW=on, comment out Access-Control-Allow-Credentials in api.py, restart it, and reload. "Load bookmarks" still works; "Log in" now fails differently — read what the console says changed.
  4. Finish the SameSite=None cookie with real TLS. Put api.py behind Code/Lesson_15_code/tls_proxy.py on a certificate for a 127.0.0.2-reachable hostname, serve static_site.py over HTTPS the same way, set COOKIE_SAMESITE=None, and confirm the cookie in Step 6 finally survives a cross-site whoami.
  5. Let CORS and CSP both pass. With CSP_MODE=on, add connect-src 'self' http://127.0.0.2:8040 to the policy in static_site.py, restart, and confirm "Load bookmarks" works again while the inline script stays blocked.
