The JavaScript Event Loop JavaScript runs one line at a time on one thread. The event loop decides which queued line runs next.

You already met the failure this lesson explains. Lesson 8 measured ten slow password hashes that blocked the event loop for 1.7 seconds — every other request waited, on one thread, with no error. This lesson shows the mechanism that made that true, and the two separate queues, a timer and a promise, that decide the order your callbacks run in.

The whole lesson in one sentence

All synchronous code runs first. Then the event loop drains the whole microtask queue. Only then does it run one task from a macrotask queue, such as a timer. It repeats this cycle for as long as the program runs.

1. The call stack runs one thing at a time

A JavaScript engine has one call stack. The call stack holds the function that runs now, and the functions that called it. The engine takes one line, runs it to completion, and only then takes the next line. No other code interrupts a running function.

This is why a function does not need a lock to protect a shared variable inside one process. Two functions never run at the same instant. Lesson 6 needed a lock for PostgreSQL rows because two separate database connections truly run at the same time. One JavaScript process never does.

2. The observable failure: three lines print out of order

Run this script. Read the order of the four console.log calls before you read the order of the four lines below the code.

console.log('A: first line');
setTimeout(() => console.log('B: setTimeout callback'), 0);
Promise.resolve().then(() => console.log('C: promise callback'));
console.log('D: last line');
$ node demo1.js
A: first line
D: last line
C: promise callback
B: setTimeout callback

Line B has a delay of 0. It still prints last. The delay you write is not a promise about when the callback runs. It is the earliest time the callback becomes eligible to run. Line C has no delay in the code at all, and it still prints after every synchronous line and before the timer. Two separate rules produced this order, and you need both to predict it.

3. Three places a callback can wait: the stack, the microtask queue, the macrotask queue

A callback that is not running yet waits in one of two queues:

  • The microtask queue. Holds callbacks from a resolved or rejected Promise, from queueMicrotask, and from await.
  • The macrotask queue (also called the task queue). Holds callbacks from setTimeout, setInterval, and completed I/O, such as a finished file read or an arrived network response.

The event loop follows one rule, on every pass:

  1. Run the synchronous code already on the call stack, to the end.
  2. Take every callback out of the microtask queue and run each one to the end. A microtask that queues another microtask extends this step — the queue must run empty before the next step starts.
  3. Take exactly one callback from the macrotask queue and run it to the end.
  4. Go back to step 2.

This rule explains Section 2's output. Lines A and D are synchronous code: they run in step 1, in the order written. Line C is a microtask: it runs in step 2, before the loop is allowed to touch the macrotask queue at all. Line B is a macrotask: it waits for step 3, which is always last.

The microtask queue is drained fully, on every pass

Step 2 does not run one microtask and move on. It runs microtasks until none remain, even ones added by other microtasks while it runs. A macrotask never starts while a microtask is still queued.

4. process.nextTick runs before every other microtask, in Node

Node adds a third queue that browsers do not have: process.nextTick. Node drains the nextTick queue completely, then drains the promise microtask queue, on every pass — nextTick always wins the race against a promise, regardless of the order you wrote them in.

process.nextTick(() => console.log('nextTick callback'));
Promise.resolve().then(() => console.log('promise callback'));
queueMicrotask(() => console.log('queueMicrotask callback'));
console.log('synchronous line');
$ node demo2.js
synchronous line
nextTick callback
promise callback
queueMicrotask callback

queueMicrotask and a promise's .then share one queue, so they run in the order you queued them. nextTick is a second, earlier queue. A library that overuses process.nextTick can starve promise callbacks the same way Section 8 starves a timer — the reason Node's own documentation recommends queueMicrotask for new code and reserves nextTick for cases that truly need to run before any promise.

5. setImmediate and setTimeout(0), inside real I/O

At the top of a script, the order of setTimeout(fn, 0) and setImmediate(fn) is not guaranteed — it depends on how long the process took to start. Inside an I/O callback, the order is fixed. Node's event loop has phases, and the check phase, where setImmediate callbacks run, always comes before the next pass reaches the timers phase.

const fs = require('fs');
fs.readFile(__filename, () => {
  setTimeout(() => console.log('timeout'), 0);
  setImmediate(() => console.log('immediate'));
});
$ node demo3.js
immediate
timeout

Node's full phase order, one pass of the loop: timers (due setTimeout/setInterval callbacks), pending callbacks (a few deferred system-level ones), poll (retrieve new I/O events, run their callbacks), check (setImmediate), close callbacks. The queued file-read callback runs during poll; the loop reaches check next, in the same pass, so setImmediate always wins from inside an I/O callback specifically.

6. async/await is the same queue, with different-looking syntax

An async function always returns a Promise. await pauses the function and schedules the rest of it as a microtask, the moment the awaited value settles. It changes nothing about the two queues from Section 3 — it only changes how the code reads.

async function foo() {
  console.log('foo: before await');
  await null;
  console.log('foo: after await');
}
console.log('script: start');
foo();
console.log('script: end');
$ node demo5.js
script: start
foo: before await
script: end
foo: after await

Calling foo() runs it synchronously up to the await. The line after await does not run next — it goes to the microtask queue, and script: end runs first, because it is still on the call stack from step 1. Nothing here differs from a plain .then() chain. async and await are syntax over the same two queues, not a third mechanism.

7. Blocking the event loop: the failure with no error message

A callback that does not finish holds the call stack, and step 1 never ends. Every other queued callback — a timer, a network response, a second user's request — waits for it, silently. No exception fires.

console.log('scheduling a timer for 0ms');
const scheduledAt = Date.now();
setTimeout(() => {
  console.log(`timer ran after ${Date.now() - scheduledAt}ms`);
}, 0);

const blockUntil = Date.now() + 300;
while (Date.now() < blockUntil) {
  // busy loop: blocks the single thread on purpose
}
console.log('busy loop finished');
$ node demo4.js
scheduling a timer for 0ms
busy loop finished
timer ran after 300ms

The timer's due time passed after roughly 0 ms. It did not run at 0 ms. It ran at 300 ms, the exact length of the busy loop, because the call stack never emptied until the loop finished. This is the exact mechanism behind Lesson 8's measurement: ten synchronous bcrypt hashes at roughly 170 ms each held the stack for 1.7 seconds, and every other request — each one a queued callback — waited the whole time.

A flooded microtask queue blocks the loop the same way

Step 2 must run empty before step 3 starts. A microtask that queues another microtask, forever, blocks every timer and every I/O callback exactly like a synchronous busy loop does — the callback keeps returning, but the queue it feeds never empties. Scheduling 2,000,000 microtasks ahead of one due timer delayed that timer from its usual 1 ms to 76 ms, measured. A true infinite chain would delay it forever.

8. Keep the event loop free

  • Move CPU-heavy work off the one thread: a worker_threads worker in Node, or a Web Worker in a browser. The work still finishes; it stops blocking every other callback while it runs.
  • If you cannot move the work, break it into chunks and yield between chunks with setImmediate or setTimeout(fn, 0). This lets a queued timer or I/O callback run between chunks, at the cost of total wall-clock time for the chunked work itself.
  • Prefer the asynchronous version of a Node API (fs.readFile) over the synchronous one (fs.readFileSync) on any path a server request can take. The synchronous call blocks the stack for its full duration, on the one thread every other request shares.
  • An unbounded recursive queueMicrotask or process.nextTick call is a bug, not a feature — Section 7 showed why. Reach for setImmediate when you need to defer work without starving the timer and I/O phases.
