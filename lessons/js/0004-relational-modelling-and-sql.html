Relational modelling + SQL Your data lives longer than your process.

Your Express API works. But every bookmark dies when you stop the server process. Today you give the API permanent storage. You will complete these tasks: design a normalised schema; write SQL queries on a PostgreSQL server; enforce data constraints in the database; write a migration runner script in JavaScript; and connect PostgreSQL to Express with the pg library. At the end, you restart the server. Your data stays in the database.

The one idea

The whole lesson in one sentence

A relational schema is a set of rules that your data must not break. You store each fact once, constraints prevent invalid states, and SQL declares schema rules and questions about your data.

The database is not a place to store raw JavaScript objects. The database is the final check for correctness. It is also the only component in your stack that retains correct data after your Node.js process crashes.

Step 0 · Start PostgreSQL with Docker

Do not use SQLite for this lesson. Real production servers use PostgreSQL. Use Docker to start a PostgreSQL 17 container:

$ docker run -d --name pg-bookmarks \
    -e POSTGRES_USER=learner \
    -e POSTGRES_PASSWORD=lesson4 \
    -e POSTGRES_DB=bookmarks \
    -p 55432:5432 \
    postgres:17

$ docker exec -it pg-bookmarks psql -U learner -d bookmarks
psql (17.10)
Type "help" for help.

bookmarks=#

Port 55432 prevents a port collision with local PostgreSQL servers. Set the connection string in your shell environment:

$ export DATABASE_URL="postgresql://learner:lesson4@localhost:55432/bookmarks"

Step 1 · Examine an unnormalised model

Consider a single table that holds tags inside a text column:

the wrong table schema

CREATE TABLE bookmarks_bad (
    id     SERIAL PRIMARY KEY,
    url    TEXT,
    title  TEXT,
    tags   TEXT
);

INSERT INTO bookmarks_bad (url, title, tags) VALUES
  ('https://expressjs.com/',              'Express',        'javascript, web, api'),
  ('https://www.postgresql.org/docs/',   'Postgres docs',  'sql, database'),
  ('https://nodejs.org/',                 'Node.js',        'javascript, runtime');

Querying this table for the tag web with LIKE '%web%' creates problems:

Text matching fails for list items

A query like LIKE '%web%' matches substrings inside words. A tag named webassembly matches '%web%' even when the bookmark does not have the tag web. Storing lists as comma-separated text disables relational operations.

Step 2 · Design a normalised schema

Model the entity relationship properly. A bookmark has many tags. A tag belongs to many bookmarks. This relationship is many-to-many. Create a join table named bookmark_tags:

  bookmarks                bookmark_tags                 tags
  ─────────                ─────────────                 ────
  id        ◀──────────────  bookmark_id
  url                        tag_id       ──────────────▶  id
  title                                                    name
  created_at                 PK (bookmark_id, tag_id)

the normalised schema

CREATE TABLE bookmarks (
    id          BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    url         TEXT NOT NULL UNIQUE,
    title       TEXT,
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE tags (
    id    BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    name  TEXT NOT NULL UNIQUE
);

CREATE TABLE bookmark_tags (
    bookmark_id  BIGINT NOT NULL REFERENCES bookmarks(id) ON DELETE CASCADE,
    tag_id       BIGINT NOT NULL REFERENCES tags(id)      ON DELETE CASCADE,
    PRIMARY KEY (bookmark_id, tag_id)
);

CREATE INDEX bookmark_tags_tag_id_idx ON bookmark_tags (tag_id);
  • BIGINT GENERATED ALWAYS AS IDENTITY — SQL-standard auto-increment integer key.
  • PRIMARY KEY — Unique identifier for each row.
  • url TEXT NOT NULL UNIQUE — Prevents duplicate URLs at the database layer.
  • REFERENCES ... ON DELETE CASCADE — Enforces referential integrity and deletes junction rows automatically when a bookmark is deleted.
  • PRIMARY KEY (bookmark_id, tag_id) — Composite primary key that prevents duplicate tag assignments.

Step 3 · Database constraints

Constraints stop illegal database modifications. Test constraint enforcement in psql:

bookmarks=# INSERT INTO bookmarks (url, title)
            VALUES ('https://expressjs.com/', 'Express again');
ERROR:  duplicate key value violates unique constraint "bookmarks_url_key"
DETAIL:  Key (url)=(https://expressjs.com/) already exists.

The database rejects invalid rows before JavaScript code processes them.

Step 4 · Query data with SQL JOIN

Use SQL JOIN clauses to combine rows from bookmarks, bookmark_tags, and tags:

SELECT b.id, b.url, b.title, b.created_at,
       coalesce(array_agg(t.name ORDER BY t.name)
                FILTER (WHERE t.name IS NOT NULL), '{}') AS tags
FROM bookmarks b
LEFT JOIN bookmark_tags bt ON bt.bookmark_id = b.id
LEFT JOIN tags t           ON t.id = bt.tag_id
GROUP BY b.id
ORDER BY b.id DESC;

array_agg combines related tag names into a PostgreSQL array. coalesce handles bookmarks with zero tags and returns an empty array.

Step 5 · Write a migration runner in JavaScript

Database migrations track schema changes in version control. Save migrations in migrations/0001_create_bookmarks.sql and migrations/0002_create_tags.sql.

Write migrate.js to run unapplied migrations in alphabetical order:

migrate.js

const fs = require('fs');
const path = require('path');
const { Client } = require('pg');

const DSN = process.env.DATABASE_URL;
const MIGRATIONS_DIR = path.join(__dirname, 'migrations');

async function migrate() {
  const client = new Client({ connectionString: DSN });
  await client.connect();

  try {
    await client.query(`
      CREATE TABLE IF NOT EXISTS schema_migrations (
        version     TEXT PRIMARY KEY,
        applied_at  TIMESTAMPTZ NOT NULL DEFAULT now()
      );
    `);

    const res = await client.query('SELECT version FROM schema_migrations');
    const applied = new Set(res.rows.map(r => r.version));

    const files = fs.readdirSync(MIGRATIONS_DIR).sort();
    for (const file of files) {
      if (!file.endsWith('.sql')) continue;
      const version = path.parse(file).name;
      if (applied.has(version)) {
        console.log(`skip    ${version}`);
        continue;
      }

      const sql = fs.readFileSync(path.join(MIGRATIONS_DIR, file), 'utf8');
      await client.query('BEGIN');
      try {
        await client.query(sql);
        await client.query(
          'INSERT INTO schema_migrations (version) VALUES ($1)',
          [version]
        );
        await client.query('COMMIT');
        console.log(`applied ${version}`);
      } catch (err) {
        await client.query('ROLLBACK');
        throw err;
      }
    }
  } finally {
    await client.end();
  }
}

migrate().catch(err => {
  console.error('Migration failed:', err);
  process.exit(1);
});

Step 6 · Parameterised queries prevent SQL injection

Do not build SQL statements with string concatenation. String concatenation enables SQL injection attacks.

sql_injection_demo.js

const { Client } = require('pg');

async function main() {
  const client = new Client({ connectionString: process.env.DATABASE_URL });
  await client.connect();

  const userInput = "' OR '1'='1";

  // NEVER DO THIS: vulnerable to SQL injection
  const naive = `SELECT id, title FROM bookmarks WHERE title = '${userInput}'`;
  console.log('naive SQL :', naive);

  // DO THIS: parameterised query
  const safeRes = await client.query(
    'SELECT id, title FROM bookmarks WHERE title = $1',
    [userInput]
  );
  console.log('safe  rows:', safeRes.rows);

  await client.end();
}

In Node.js pg, positional parameters ($1, $2) transmit parameters separately from SQL text. The database engine treats parameters strictly as data values, preventing injection.

Step 7 · Connect Express to PostgreSQL with pg.Pool

Use a connection pool (pg.Pool) in Express to handle concurrent database connections efficiently. Wrap write operations in transactions (BEGIN, COMMIT, ROLLBACK).

server.js

const express = require('express');
const { Pool } = require('pg');

const DSN = process.env.DATABASE_URL;
const pool = new Pool({ connectionString: DSN });
const app = express();
app.use(express.json());

app.post('/bookmarks', async (req, res, next) => {
  const { url, title = null, tags = [] } = req.body || {};
  if (!url) {
    return res.status(400).json({ detail: 'URL is required' });
  }

  const client = await pool.connect();
  try {
    await client.query('BEGIN');
    const bRes = await client.query(
      'INSERT INTO bookmarks (url, title) VALUES ($1, $2) RETURNING id, url, title, created_at',
      [url, title]
    );
    const bookmark = bRes.rows[0];

    for (const name of tags) {
      const tRes = await client.query(
        'INSERT INTO tags (name) VALUES ($1) ON CONFLICT (name) DO UPDATE SET name = EXCLUDED.name RETURNING id',
        [name]
      );
      const tagId = tRes.rows[0].id;
      await client.query(
        'INSERT INTO bookmark_tags (bookmark_id, tag_id) VALUES ($1, $2) ON CONFLICT DO NOTHING',
        [bookmark.id, tagId]
      );
    }
    await client.query('COMMIT');
    res.status(201).json({ ...bookmark, tags });
  } catch (err) {
    await client.query('ROLLBACK');
    if (err.code === '23505') {
      return res.status(409).json({ detail: 'URL already bookmarked' });
    }
    next(err);
  } finally {
    client.release();
  }
});

app.listen(8000, () => {
  console.log('Bookmark API listening on http://127.0.0.1:8000');
});

The handler opens a transaction with BEGIN. If any operation fails, the handler catches the exception, rolls back changes with ROLLBACK, and returns status code 409 when the database reports duplicate key violation code 23505.

Check your understanding

1. Why must tag associations be stored in a junction table like bookmark_tags rather than a comma-separated text column?

Correct! Relational schemas separate entities to enforce foreign keys, prevent text parsing errors, and optimize query indexes.

2. How do parameterised queries in Node.js pg prevent SQL injection?

Correct! Positional placeholders ($1) send user data separately from the SQL statement, preventing parameter string contents from altering SQL syntax.
