Why is this slow? Measure first. The database will tell you the truth if you ask it.

Your API stores data in PostgreSQL. With forty rows, every endpoint returns quickly. Today you load 200 000 rows into the database and inspect slow execution paths. You use EXPLAIN to analyze two performance failures: sequential table scans and N+1 query loops. At the end, you measure performance before and after optimization.

The whole lesson in one sentence

You cannot fix slowness you have not measured. Ask PostgreSQL for a query plan with EXPLAIN (ANALYZE, BUFFERS) and read the execution statistics.

Step 0 · Load test data into PostgreSQL

Populate your database with 200 000 bookmarks. Copy seed.sql to the PostgreSQL container and run it with psql:

$ docker cp seed.sql pg-bookmarks:/seed.sql
$ docker exec pg-bookmarks psql -U learner -d bookmarks -f /seed.sql
INSERT 0 200000
INSERT 0 40
INSERT 0 585000
Run ANALYZE after large updates

ANALYZE updates table statistics for the query planner. Without updated statistics, PostgreSQL makes execution decisions based on outdated row counts, producing invalid plan estimates.

Step 1 · Observe a sequential scan

Query one bookmark by title inside psql using EXPLAIN (ANALYZE, BUFFERS):

bookmarks=# EXPLAIN (ANALYZE, BUFFERS)
bookmarks-# SELECT id, url FROM bookmarks WHERE title = 'Article number 137000';

 Seq Scan on bookmarks  (cost=0.00..5068.00 rows=1 width=42)
                        (actual time=6.759..9.797 rows=1 loops=1)
   Filter: (title = 'Article number 137000'::text)
   Rows Removed by Filter: 199999
   Buffers: shared hit=2568
 Execution Time: 9.846 ms

To return one row, PostgreSQL inspected all 200 000 rows and discarded 199 999 rows. That execution step is a sequential scan (Seq Scan).

Step 2 · Read the query plan

The output of EXPLAIN (ANALYZE, BUFFERS) displays the query plan and execution measurements:

  • Seq Scan — PostgreSQL reads the table sequentially from start to finish.
  • Rows Removed by Filter — Displays the number of examined rows rejected by filter conditions.
  • Buffers — Measures the number of 8 kB memory pages accessed during query execution.
  • Execution Time — Total query execution duration in milliseconds.

Step 3 · Add a B-tree index

Create a B-tree index on the title column to remove the sequential scan:

bookmarks=# CREATE INDEX bookmarks_title_idx ON bookmarks (title);
bookmarks=# ANALYZE bookmarks;
bookmarks=# EXPLAIN (ANALYZE, BUFFERS)
bookmarks-# SELECT id, url FROM bookmarks WHERE title = 'Article number 137000';

 Index Scan using bookmarks_title_idx on bookmarks
        (cost=0.42..8.44 rows=1 width=42) (actual time=0.054..0.056 rows=1 loops=1)
   Index Cond: (title = 'Article number 137000'::text)
   Buffers: shared hit=1 read=3
 Execution Time: 0.085 ms
Performance result

Execution duration drops from 9.846 ms to 0.085 ms. Accessed pages drop from 2568 pages to 4 pages. The query plan uses an Index Scan.

Step 4 · Fix prefix search with text_pattern_ops

Run a prefix search query using LIKE 'Article number 1370%':

bookmarks=# EXPLAIN (ANALYZE, BUFFERS)
bookmarks-# SELECT id, title FROM bookmarks WHERE title LIKE 'Article number 1370%';

 Seq Scan on bookmarks  (cost=0.00..5068.00 rows=2020 width=29)
                        (actual time=0.098..11.767 rows=111 loops=1)
   Filter: (title ~~ 'Article number 1370%'::text)
   Rows Removed by Filter: 199889

The standard B-tree index does not support pattern matching under locale collations. Apply migration 0003_add_title_search_index.sql using the text_pattern_ops operator class:

CREATE INDEX bookmarks_title_pattern_idx
    ON bookmarks (title text_pattern_ops);

Run the prefix search query again. The query planner uses bookmarks_title_pattern_idx for fast index range scans.

Step 5 · Eliminate N+1 queries in Express

The N+1 problem occurs when an application executes 1 initial query followed by N secondary queries in a loop.

The slow handler — N+1 query loop

app.get('/bookmarks/slow', async (req, res, next) => {
  try {
    const skip = parseInt(req.query.skip, 10) || 0;
    const limit = parseInt(req.query.limit, 10) || 10;
    const { rows } = await pool.query(
      'SELECT id, url, title, created_at FROM bookmarks ORDER BY id LIMIT $1 OFFSET $2',
      [limit, skip]
    );

    for (const row of rows) {
      const { rows: tags } = await pool.query(
        'SELECT t.name FROM tags t JOIN bookmark_tags bt ON bt.tag_id = t.id WHERE bt.bookmark_id = $1 ORDER BY t.name',
        [row.id]
      );
      row.tags = tags.map(r => r.name);
    }
    res.json(rows);
  } catch (err) {
    next(err);
  }
});

Replace the loop with a single aggregated query using LEFT JOIN and array_agg:

The fast handler — single aggregated query

const LIST_SQL = `
SELECT b.id, b.url, b.title, b.created_at,
       coalesce(array_agg(t.name ORDER BY t.name)
                FILTER (WHERE t.name IS NOT NULL), '{}') AS tags
FROM bookmarks b
LEFT JOIN bookmark_tags bt ON bt.bookmark_id = b.id
LEFT JOIN tags t           ON t.id = bt.tag_id
GROUP BY b.id
ORDER BY b.id DESC
OFFSET $1 LIMIT $2
`;

app.get('/bookmarks', async (req, res, next) => {
  try {
    const skip = parseInt(req.query.skip, 10) || 0;
    const limit = parseInt(req.query.limit, 10) || 10;
    const { rows } = await pool.query(LIST_SQL, [skip, limit]);
    res.json(rows);
  } catch (err) {
    next(err);
  }
});

Step 6 · Simulate network latency with slow_link.js

Run n_plus_1.js to benchmark N+1 query execution against a single aggregated query:

$ export DATABASE_URL="postgresql://learner:lesson4@localhost:55432/bookmarks"
$ node n_plus_1.js
N+1               14.2 ms    101 queries   100 rows
single query       1.1 ms      1 queries   100 rows

the join is 13x faster

Start slow_link.js in a terminal to add 1 ms latency to database connections on port 55433. Run n_plus_1.js over port 55433 to observe network round-trip costs:

$ node slow_link.js &
$ export DATABASE_URL="postgresql://learner:lesson4@localhost:55433/bookmarks"
$ node n_plus_1.js
N+1              215.4 ms    101 queries   100 rows
single query       3.2 ms      1 queries   100 rows

the join is 67x faster

Network latency makes the N+1 loop 67 times slower than a single SQL query.

Check your understanding

1. What does EXPLAIN (ANALYZE, BUFFERS) show that bare EXPLAIN does not?

Correct! ANALYZE executes the query and compares actual row counts, timings, and buffer page reads against planner estimates.

2. Why does the N+1 query problem degrade performance over real network connections?

Correct! Performing N database requests incurs N individual round-trip network delays, multiplying latency overall.
