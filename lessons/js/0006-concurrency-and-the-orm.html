Concurrency + the ORM (JS) A transaction protects you from a crash, not from another transaction.

In JS Lesson 5, you measured query execution times using EXPLAIN and fixed sequential scans. Today you handle concurrent database updates in Node.js. Multiple web server instances or concurrent async handlers can read and overwrite the same database row at the same time. You will observe lost updates, apply three SQL concurrency patterns, and evaluate how Object-Relational Mapping (ORM) tools handle data consistency.

The whole lesson in one sentence

Concurrent read-modify-write operations overwrite data silently. You must use single atomic SQL statements, explicit row locks, or isolation retry loops to prevent data loss.

Step 0 · Add the visit counter column

Apply migration 0004_add_visit_count.sql to add a visit_count column to the bookmarks table:

ALTER TABLE bookmarks ADD COLUMN visit_count INT NOT NULL DEFAULT 0;

Step 1 · Observe the lost update defect

When two asynchronous handlers read counter value 0 simultaneously, both calculate 0 + 1 = 1 in JavaScript memory. Both write 1 back to PostgreSQL. Two visits occurred, but the stored count increases by only 1.

Naive read-modify-write in Node.js

const { rows } = await pool.query('SELECT visit_count FROM bookmarks WHERE id = $1', [id]);
const count = parseInt(rows[0].visit_count, 10);
await pool.query('UPDATE bookmarks SET visit_count = $1 WHERE id = $2', [count + 1, id]);

Run lost_update.js with 20 workers executing 10 increments each (200 total increments):

$ node lost_update.js
Running concurrency benchmarks (20 workers x 10 increments = 200 total)...

Strategy: 1. Naive (Read-Modify-Write in JS)
  Expected count : 200
  Final count    : 13
  Lost updates   : 187
  Elapsed time   : 141 ms
Silent data corruption

The application completed with exit code 0. PostgreSQL raised no errors. However, 187 updates were lost due to concurrent state overwrites.

Step 2 · Fix 1 — Single atomic SQL statement

Perform calculation directly inside PostgreSQL using a single atomic update statement:

UPDATE bookmarks SET visit_count = visit_count + 1 WHERE id = $1 RETURNING visit_count;

PostgreSQL locks the targeted row during statement execution, preventing concurrent writes from overwriting intermediate values:

Strategy: 2. Single Statement (Atomic UPDATE)
  Expected count : 200
  Final count    : 200
  Lost updates   : 0
  Elapsed time   : 121 ms

Step 3 · Fix 2 — Pessimistic locking (SELECT FOR UPDATE)

If your application must execute business logic before saving, lock the row during selection using FOR UPDATE:

await client.query('BEGIN');
const { rows } = await client.query('SELECT visit_count FROM bookmarks WHERE id = $1 FOR UPDATE', [id]);
const count = parseInt(rows[0].visit_count, 10);
await client.query('UPDATE bookmarks SET visit_count = $1 WHERE id = $2', [count + 1, id]);
await client.query('COMMIT');
Strategy: 3. SELECT FOR UPDATE (Pessimistic Lock)
  Expected count : 200
  Final count    : 200
  Lost updates   : 0
  Elapsed time   : 225 ms

Step 4 · Fix 3 — Optimistic concurrency (REPEATABLE READ + retry loop)

Set isolation level to REPEATABLE READ. When concurrent modifications occur, PostgreSQL aborts conflicting transactions with error code 40001 (serialization_failure). Your Node.js code catches this error and retries:

Strategy: 4. REPEATABLE READ (Optimistic Retry)
  Expected count : 200
  Final count    : 200
  Lost updates   : 0
  Elapsed time   : 568 ms
  Total retries  : 600

Step 5 · Evaluate ORM abstractions

Object-Relational Mapping libraries map database rows to JavaScript objects. Changing an object property (e.g. bookmark.visitCount += 1) and calling save() recreates the naive read-modify-write defect unless atomic updates or locking are explicitly specified.

Check your understanding

1. Why does a standard database transaction not prevent lost updates in read-modify-write operations?

Correct! READ COMMITTED guarantees queries see committed data, but does not block other transactions from modifying rows between your SELECT and UPDATE statements.

2. Which approach fixes the lost update problem with minimum execution latency?

Correct! Atomic updates process modifications entirely inside PostgreSQL in a single database round-trip without locks or retries.
