Reading a Query Plan Compressed reference for PostgreSQL 17. Behaviour verified against PostgreSQL 17.10; claims cite Using EXPLAIN and Operator Classes.

The command

EXPLAIN (ANALYZE, BUFFERS) <your query>;
  • EXPLAIN alone — the plan the planner intends. Does not run the query.
  • ANALYZE — runs the query and adds what really happened.
  • BUFFERS — adds page counts. The measurement that does not move when the machine is busy.
ANALYZE really executes

On INSERT, UPDATE, or DELETE it changes your data. Wrap it: BEGIN; EXPLAIN (ANALYZE) DELETE …; ROLLBACK;

Anatomy of one node

 Seq Scan on bookmarks  (cost=0.00..5068.00 rows=1 width=42)
 └ node type  └ table    └ PLANNER ESTIMATE ────────────────┘
                        (actual time=6.759..9.797 rows=1 loops=1)
                        └ REALITY ────────────────────────────────┘
   Filter: (title = 'Article number 137000'::text)
   Rows Removed by Filter: 199999      ← work done then discarded
   Buffers: shared hit=2568            ← 8 kB pages: hit=cache read=disk
 Planning Time: 0.348 ms
 Execution Time: 9.846 ms              ← the number you report
FieldMeans
cost=start..totalArbitrary planner units, not milliseconds. 1.0 ≈ one sequential page read. Only ever compare it with another plan for the same query.
rows= (in cost)The estimate. rows= in actual is the truth. A large gap means stale statistics — run ANALYZE.
width=Estimated average bytes per row.
actual time=first..lastMilliseconds to the first row, then to the last. Per loop.
loops=NThe node ran N times. Multiply actual time by loops for the real total.
Rows Removed by FilterRows read and thrown away. The first line to look at.
Buffers: shared hit/read8 kB pages from cache / from disk. The stable measure of work.

Read the plan from the inside out. The most indented node runs first and passes rows up to its parent.

Node types you will meet

NodeWhat it doesRead it as
Seq ScanReads every row of the table.Fine on a small table. On a large one with a selective WHERE, a missing or unusable index.
Index ScanWalks the index, then fetches each matching row from the table.What you usually want for a few rows.
Index Only ScanAnswers entirely from the index; never touches the table.Best case. Happens when the index contains every column the query needs.
Bitmap Index Scan + Bitmap Heap ScanCollects row locations, sorts them, then reads the table in physical order.Chosen when many rows match. Not a problem — it is the planner avoiding thousands of random reads.
Nested LoopFor each row on the left, look up matching rows on the right.Good when the left side is small. If loops= is large and the inner side is a Seq Scan, that is the plan-level N+1.
Hash JoinBuilds a hash table from one side, probes it with the other.Normal for joining two large sets.
Sort / top-N heapsortOrders rows. top-N means it only kept the N needed by LIMIT.Check Sort Method: external merge Disk means it spilled — consider more work_mem or an index in that order.
Gather / Parallel …Several worker processes split the scan.Often a sign the planner expects a lot of work. Parallel is not the same as fast.

Indexes: the rules that matter

  • You get some for free. PRIMARY KEY and UNIQUE each create a B-tree index. REFERENCES does not — foreign key columns are unindexed until you say so. Check with \d tablename.
  • Leftmost columns only. An index on (a, b, c) serves a · a, b · a, b, c. It does not serve b, c, or b, c. Order the columns by which one you filter on first.
  • Selectivity decides the payoff. An index earns in proportion to what it skips. Matching 1 row in 200 000 is a 100× win; matching 1 row in 30 is often no win at all. Do not index a boolean.
  • Text needs the right operator class. A default text index is sorted by locale collation and cannot serve LIKE 'abc%' unless the database uses the C locale. Use CREATE INDEX … ON t (col text_pattern_ops), which also serves =. It does not serve ORDER BY col in dictionary order.
  • Leading wildcards are hopeless. LIKE '%abc%' cannot use a B-tree at all. That is full-text search or a trigram (pg_trgm) index.
  • Every index taxes every write. Measured on 200 000 rows: 1 index → 251 ms and 22 MB; 4 indexes → 1533 ms and 50 MB. Add an index for a measured query, not in advance.
  • Find the useless ones. SELECT * FROM pg_stat_user_indexes ORDER BY idx_scan; — an index with idx_scan = 0 is pure cost.

Diagnosis order

  1. Reproduce with realistic data volume. Forty rows tell you nothing.
  2. Measure more than once. Take a median. One sample is noise.
  3. Count the queries first. One query per row in a loop is N+1, and no amount of indexing fixes it. The fix is one query with a join.
  4. Then EXPLAIN (ANALYZE, BUFFERS) the slowest single query. Look at Rows Removed by Filter, then buffers, then estimate-vs-actual.
  5. \d the table. See what indexes already exist before adding one.
  6. Change one thing. Re-run the same EXPLAIN. Compare time and buffers.
Two questions, two different tools

"Why is this query slow?" → EXPLAIN (ANALYZE, BUFFERS).
"Why is this endpoint slow when every query is fast?" → count the queries. EXPLAIN can never show you an N+1, because each of the N is individually fine.

psql commands for this work

\d tablename        columns, indexes, constraints, and what references it
\di                 list all indexes
\timing on          time every statement
\x                  expanded output — worth it for pg_stat_* rows
\e                  edit the last query in $EDITOR
-- table and index sizes, largest first
SELECT relname, pg_size_pretty(pg_total_relation_size(relid))
FROM pg_stat_user_tables ORDER BY pg_total_relation_size(relid) DESC;

-- indexes nobody uses
SELECT relname, indexrelname, idx_scan
FROM pg_stat_user_indexes ORDER BY idx_scan;
